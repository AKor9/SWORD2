## 0. Принятые решения

| # | решение | почему |
|---|---|---|
| 1 | **Переносится логика, а не текст кода.** Код SWORD переписывается под новую архитектуру там, где это нужно; алгоритмы, константы и порядок вычислений сохраняются. Что ложится как есть — переносится как есть | логика отлажена (рэгдолл, MM, кровь, разрез); держаться за старую форму кода — значит тащить старую архитектуру |
| 2 | **Живой рэгдолл не переносится ни в каком виде.** Живой боец — только кинематический. Из рэгдолл-кода берётся только то, что нужно трупам, отрубленным частям и обломкам | ветка мертва (арена без скелета не стартует), но держит ~⅓ кода `Fighter`/`DuelArena` |
| 3 | **Сначала прототип без механик, затем фичи по одной.** Прототип — как можно быстрее; механики и модули добавляются по одному | быстрый видимый результат; каждый шаг маленький и проверяемый |
| 4 | **Приёмка фичи: автоматический контроль ведёт Claude, в игре подтверждает пользователь.** Следующая фича — после подтверждения | машина проверяет тесты и числа, человек — поведение в игре |

Подсистемы (физика, анимация, GPU-симуляции, рендер) владеют своими данными в своей раскладке; в ECS — только хэндлы | так устроены Unreal (Mass + Chaos), Unity DOTS, Bevy: игровой код расширяется легко, горячие циклы — максимально быстрые |
| 6 | **Свой минимальный архетипный ECS** (`Sword.Engine.Ecs`), API по образцу Arch | проект — хобби для изучения; API как у Arch — чтобы при нужде заменить |
| 7 | **Масштаб не фиксируем, но и не закрываем.** Делаем hero-уровень (десятки бойцов с полной точностью); архитектура не должна мешать LOD-уровням и GPU-толпе (1 000–10 000) | цель — выжать максимум из железа; решение о массовых сражениях — потом |
| 8 | **Зависимости только вниз.** Движок не знает игру и пекарню; проверяется сборкой и тестом | «взрослая» архитектура под большой проект |
| 9 | **Модуль либо есть, либо нет.** Без модуля его функции в игре нет; кода, который работает только в отсутствие модуля, нет (раздел 10) | запасной путь — второй код, который гниёт незаметно: работает только тогда, когда на него никто не смотрит |
| 10 | **Симуляция отделена от клиента физически — по сборкам.** Сборки симуляции не ссылаются на клиентские ни прямо, ни транзитивно; `Game.Headless` собирается только из них и идёт без окна и D3D12 | детерминизм, тесты без видеокарты, реплеи; изоляция проверяется обычным графом ссылок проектов |
| 11 | **Реактивные системы наравне с непрерывными.** То, что случается (появление бойца, смерть, смена оружия, попадание, отруб, смена настроек), обрабатывает реактивная система по срабатыванию; при переносе такие места SWORD переписываются на реактивные | не гонять каждый тик проверку того, что случается редко; у каждой реакции явная причина |
| 12 | **Движок рассчитан на работу ИИ-агентов (Claude, GPT и других).** Агент запускает игру и её симуляцию без окна, управляет временем, читает состояние мира и подсистем, отправляет команды, снимает кадры — через один протокол (MCP) и структурированные ответы (раздел 8). Каждая фича даёт агенту способ увидеть своё состояние | автоматический контроль фич (решение 4) ведёт агент; отладка по данным, а не по догадкам; воспроизводимые сессии |

## 2. Принципы

1. **Зависимости только вниз.** Движок не знает игру и пекарню. Игра не знает пекарню. Модули видят только контракты
   игры (`Game.Contracts`), но не её устройство и не друг друга.
2. **Подсистема владеет своими данными — и только ими.** Физика владеет телом, но не «обломком»; ECS хранит хэндлы.
   Синхронизация — явными шагами Push/Pull в известных стадиях.
3. **Явные стадии, барьеры и журналы.** Порядок систем задают объявленные зависимости (`After/Before`), а не порядок
   строк; события и срабатывания видны по чётким правилам (раздел 5).
4. **Модуль либо есть, либо нет.** Ядро публикует факты и заявки (события, компоненты), модули действуют по ним;
   ядро никогда не спрашивает модуль и не ждёт ответа. То, без чего игра не имеет смысла (ввод, рендер, проходы
   клинка, урон, смерть и рэгдолл), — ядро в одной реализации, не модуль и не выключается.
5. **Реагировать на то, что случилось, а не опрашивать.** Редкие события — реактивные системы; каждый тик работают
   только непрерывные процессы.
6. **Симуляция авторитетна и детерминирована.** Представление (рендер, GPU-симуляции, UI) только читает её; обратная
   связь с GPU не влияет на игровую логику; случайность не зависит от порядка обхода и потоков.
7. **Устойчивый кадр без аллокаций.** Компоненты — `unmanaged struct`; пулы; цель — 0 выделенных байтов на тик
   после прогрева.
8. **Одна правда для CPU и GPU.** Общие структуры и константы — из одного источника (генерация или проверка при старте).
9. **Не фиксировать до первого потребителя.** Размеры, форматы и механизмы — гипотезы, пока нет потребителя и замера.
10. **Каждый шаг — работающая программа и проверка.** Никакого «большого взрыва».
11. **Наблюдаемо для машины.** Всё, что движок сообщает, — структурированные данные со стабильными именами
    (компоненты, системы, стадии, события, модули, ручки, команды); отчёты, метрики и логи — в JSON рядом
    с человекочитаемым текстом; ошибки — со стабильными кодами. Что нельзя наблюдать, нельзя проверить. Каждое
    изменение кода проверяется на то, хватает ли агенту инструментов (раздел 8).
12. **Соглашения репозитория** (переносятся в `AGENTS.md` SWORD2): CRLF во всех текстовых файлах; каждая механика —
    модуль с md-документом (назначение, настройки, зависимости, ограничения, известные ошибки).

**Симуляция и клиент разделены по сборкам.** Клиентская сборка (`*.Client`) заводится только там, где у кода есть
представление: у ядра игры — всегда, у модулей — по надобности (Blood и Innards — только клиент, FootPlacement —
только симуляция). `Game.Headless` ссылается только на сборки симуляции, поэтому «без окна и D3D12» проверяется
обычным графом ссылок проектов, без разбора IL.

**Одна композиция симуляции.** Список ядра и модулей симуляции живёт только в `Sword.Game.Bootstrap`; `Game.App`
и `Game.Headless` вызывают его одинаково, поэтому игра и её прогон без окна не могут разойтись составом.
`-p:Without<Модуль>=true` действует здесь. Клиентские модули добавляет только `Game.App`.

`Content.swpak` (442 МБ) и сырьё — вне git; путь к паку — в конфиге. До переноса пекарни игра читает эталонный пак
SWORD (этап 0): формат пака не меняется. Пак закреплён — `Content.reference.swpak` (вне git, только для чтения):
описание — `tests/reference/reference.json`, целостность — `tools/scripts/reference.ps1 -Check` (шаг `reference` в `verify.ps1`).

**Запрещено:**
- `engine/*` → `game/*`, `tools/*`; `game/*` → `tools/*`;
- сборки симуляции (Runtime, Sword.Game, модули симуляции) → Client, Render, Rhi, Ui, Platform — ни прямо, ни транзитивно;
- Physics, Animation, Ecs, Formats, Content, Geometry, Ui → Rhi, Render, Platform, Client;
- модуль → `Sword.Game`, `Sword.Game.Client` и другие модули; `Sword.Game` → модули;
- Platform.Win32 — только из exe;
- сборки агента (Engine.Agent, Engine.Agent.Client, Game.Agent) — только из exe; ядро игры и модули о них не знают:
  своё состояние они отдают через контракты Runtime (`IStateContributor`, раздел 7), а не через агента;
  сборки агента вправе напрямую зависеть от нижележащих Ecs, Runtime и Introspection, когда их публичные контракты
  непосредственно используют эти типы (подтверждено на точке 1е);
- Engine.Client → Ecs — разрешённая граница только для чтения: Extract читает мир через `SimulationLink`
  (`WorldReader`), исполнения симуляции клиент не получает (подтверждено на точке 1е);
- сборка без агента (`-p:WithoutAgent=true`, как для DevTools) не содержит ни одной сборки агента;
- сборки DevTools (Engine.DevTools, Game.DevTools) — только из exe (и друг из друга); сборка без них
  (`-p:WithoutDevTools=true`) не содержит ни одной (тест ссылок exe под условием, шаг `verify.ps1` `without-devtools`);
- сборки `Vortice.*` — только у Rhi и Render (временный список исключений **может только сокращаться**).

**Как проверяется:**
1. У каждого проекта два свойства: слой (`SwordLayer = Engine | Game | Tool | Test` — по папке, в
   `Directory.Build.props`) и сторона (`SwordSide = Neutral | Simulation | Client` — в `.csproj`); цель MSBuild
   в `Directory.Build.targets` роняет сборку при недопустимой `ProjectReference`: SWORD001 — слой, SWORD002 —
   сторона, SWORD003 — сторона не задана. Слой и сторона пишутся и в метаданные сборки (`AssemblyMetadata`).
2. `Sword.Architecture.Tests` — по графу `ProjectReference` из `SWORD.slnx` и `.csproj`: матрица выше
   (`ArchitectureRules.Matrix`), транзитивное замыкание сборок симуляции без клиентских, модули не видят друг друга
   и ядро игры, `Vortice.*` только у Rhi и Render и с `PrivateAssets=compile` (типы D3D12 не утекают к ссылающимся),
   Platform.Win32, сборки агента и DevTools — только из exe, каждый проект — в решении.
3. Тест на сам тест: `RuleTests` строят заведомо запрещённые графы и требуют нарушения; заготовки
   `tests/fixtures/forbidden-references/SWORD00N-*` обязаны уронить сборку своим кодом (`verify.ps1`).

## 5. Sword.Engine.Ecs

Свой минимальный архетипный ECS, API по образцу Arch. Размеры и механизмы ниже — стартовые гипотезы:
фиксируются замером, а не заранее.

### Модель

| понятие | устройство |
|---|---|
| сущность | `readonly record struct Entity(int Index, int Generation)`; удаление увеличивает поколение — висячий хэндл распознаётся |
| компонент | `unmanaged struct`; ссылки запрещены ограничением `where T : unmanaged` |
| тег | тип без полей; колонку не занимает (пустой `struct` в C# весит 1 байт — тег распознаётся при регистрации по отсутствию полей) |
| реактивный компонент | помечен `[Reactive]`; меняется только командой `Set<T>` — так каждое изменение попадает в журнал `Changed<T>`. Прямая запись `Write<T>()` в него — исключение в Debug. Частые данные (`Transform`) реактивными не делаются |
| причина записи | в записях команд и событий с v0 есть слот `CauseId`; в диагностическом режиме туда пишутся причина, родитель, стадия, регистрация системы и источник (`[CallerFilePath]`/`[CallerLineNumber]` у методов команд) — для `state.why` (раздел 8); вне режима слот пуст и ничего не стоит |
| регистрация | явная, при сборке мира, в детерминированном порядке (по полному имени типа). ID не зависят от порядка первого обращения к `ComponentType<T>`; незарегистрированный компонент — ошибка |
| стабильные имена | ID компонентов нигде не сохраняются: сейвы, реплеи и ассеты ссылаются на стабильные имена |
| архетип, чанк | набор компонентов → чанки SoA (колонка на компонент); строки плотные, удаление — перенос последней строки. Размер чанка — настройка (старт 16 КБ), не контракт |
| версии изменений | `Write<T>()` помечает версию всего столбца в чанке, даже если данные не менялись: грубо, но надёжно — хватает для Push «только изменённое» |
| ресурсы | синглтоны мира: `World.Resource<T>()`; замена — `SetResource`, попадает в журнал `ResourceChanged<T>` |
| хуки | `OnAdd<T>/OnRemove<T>` — только время жизни ресурсов подсистем (выделить и освободить хэндл тела, позы); вызываются на барьере, структуру мира не меняют, повторный вход запрещён |

### Системы: непрерывные и реактивные

| вид | когда исполняется | что получает | для чего |
|---|---|---|---|
| непрерывная | каждый тик в своей стадии | запрос по компонентам | то, что идёт всегда: движение, анимация, физика, проходы клинков, ИИ |
| реактивная | в своей стадии, только если с её прошлого запуска были срабатывания | только затронутые сущности или события | то, что случается: появление бойца, смерть, смена оружия, попадание, отруб, смена настроек |

| срабатывание | когда появляется |
|---|---|
| `Added<T>` | компонент добавлен (командой, на барьере) |
| `Removed<T>` | компонент снят или сущность удалена; запись хранит последнее значение `T` |
| `Changed<T>` | существующий реактивный компонент заменён командой `Set<T>`; при отключённых проверках ошибочный `Add<T>` уже существующего компонента также даёт `Changed<T>` |
| `Event<E>` | записано событие `E` |
| `ResourceChanged<T>` | ресурс заменён (ручки, настройки, уровень) |

```csharp
// Регистрируется в стадии Settle: смерти из Resolve и Aftermath к ней уже прошли барьер.
sealed class DeathToRagdollSystem : IReactiveSystem<Added<Dead>>
{
    public void Setup(SystemSetup s)
    {
        s.Label(GameLabels.DeathToRagdoll);
        s.Query().With<Kinematic>();                 // идемпотентна: уже переведённых не трогает
        s.Removes<Kinematic>();
        s.Writes<BodyMode>();
    }

    public void React(in SystemContext ctx, ReadOnlySpan<Added<Dead>> died)   // только умершие с прошлого запуска
    {
        foreach (var e in died) { /* перевести тело в рэгдолл по позе прошлого тика */ }
    }
}
```

- Реактивная система — обычная система: стадия, метка, `After/Before`, объявленный доступ. В v0 у неё одно
  срабатывание; нужно два — две системы.
- Непрерывная система тоже может читать журнал (`ctx.Journal<Event<Hit>>()`) своим курсором. Дополнительный журнал
  реактивной системы (`HitApplySystem`: `StrikeBlocked` при срабатывании по `StrikeContact`) — контекст срабатывания:
  в тике срабатывания видны его записи с её прошлого места в тике, записи тиков без срабатывания пропускаются.
- Реактивная система без срабатываний стоит одну проверку длины журнала.
- Журнал заводится только для срабатываний, на которые кто-то подписан.
- Одну систему можно зарегистрировать в двух стадиях (у каждой регистрации свой курсор) — тогда она обязана быть
  идемпотентной. Так `DeathToRagdoll` повторяет два вызова `SettleDeaths` за тик в SWORD (раздел 9).
- **Идентичность регистрации** — `(Stage, SystemLabel, RegistrationId)`. Метка уникальна внутри стадии; повторная
  регистрация того же типа получает свой `RegistrationId` (`DeathToRagdoll@Gameplay`, `DeathToRagdoll@Settle`).
  По ней ведутся курсоры журналов, граф `After/Before`, профайлер, токены модулей и ответы агенту.

### Порядок стадий производителя и потребителя

`After`/`Before` задают порядок систем внутри стадии, но **барьера между ними не вставляют**. Поэтому правило:

```
стадия(производитель) <  стадия(потребитель)  → реакция в том же тике
стадия(производитель) >= стадия(потребитель)  → реакция в следующем тике — ошибка сборки мира,
                                                 если потребитель не объявил NextTickOk<T>()
```

Производители объявляют, что порождают (`Emits<E>`, `Adds<T>`, `Removes<T>`, `Sets<T>`, `SetsResource<T>`;
в Debug необъявленное — исключение), потребители — срабатывания; **при сборке мира планировщик проверяет каждую пару
по правилу выше**. Пример: ранняя регистрация `DeathToRagdoll@Gameplay` стоит раньше производителей `Dead` из
Resolve и Aftermath и объявляет `NextTickOk<Added<Dead>>()` — задержки там нет по смыслу, эти смерти в том же тике
уже обработала `DeathToRagdoll@Settle`, которой разрешение не нужно.

Сущность создаётся командой **сразу с окончательным набором компонентов**: реактивная настройка по `Added<Fighter>`
не добавляет компоненты, на которые в той же стадии кто-то реагирует. Общая логика двух реакций (первое оружие при
появлении бойца и смена оружия потом) — одна функция, которую зовут обе системы, а не цепочка срабатываний.

### Создание сущностей: черновики

API создания **одинаков при последовательном и параллельном исполнении** — системам v0 не придётся меняться:

```csharp
EntityDraft piece = ctx.Commands.Create();                  // черновик: живой сущности ещё нет
ctx.Commands.Add(piece, new PartOf { Owner = victim });
ctx.Commands.Add(piece, transform);
ctx.Commands.Emit(new LimbDetached { Part = piece.Ref, … });  // поле Part имеет тип Entity; piece.Ref — отложенное значение
```

- **Тип поля не меняется — меняется значение.** В компонентах и событиях ссылки на сущности — всегда поля типа
  `Entity`. `EntityDraft.Ref` даёт отложенное значение `Entity`: особая кодировка (отрицательный индекс — номер черновика,
  поколение — номер буфера), которую нельзя спутать с живой сущностью.
- **Разрешитель** генерируется при регистрации типа компонента или события: он знает все поля `Entity`, включая вложенные
  структуры (иная форма хранения ссылок — ошибка регистрации). На барьере он заменяет отложенные значения настоящими
  `Entity` **до** того, как компонент или событие станут видны. Применяется к `Add<T>`, `Set<T>` и `Emit<T>`.
- Черновик живёт до ближайшего барьера. Команды и события **своего** буфера могут на него ссылаться; живую сущность
  до барьера получить нельзя.
- В Debug — исключение: черновик чужого `CommandBuffer`; обращение к `World` с неразрешённым отложенным значением;
  отложенное значение, записанное в компонент мимо команд.
- Индексы сущностей назначаются при проигрывании в детерминированном порядке буферов — от числа потоков не зависят.
- Вне исполнения систем (начальная сборка мира, тесты) — `World.CreateImmediate()`.

### Стадии, барьеры, журналы

```
стадия   системы по порядку; каждая пишет события и команды в свои локальные буферы
барьер   1) проигрывание CommandBuffer: порядок системы в стадии → порядок задачи → порядок записи;
            черновики → Entity, разрешитель заменяет отложенные значения в Add/Set; записи Added/Removed/Changed
            в журналы; хуки
         2) слияние событий в том же порядке; разрешитель заменяет отложенные значения в событиях из Emit
         3) следующая стадия видит структурные изменения и новые записи журналов
```

- События и срабатывания — журналы. У каждого потребителя (системы, клиента) свой курсор: **каждую запись каждый
  потребитель видит ровно один раз** — записи стадий раньше него в этом тике и позже него в прошлом тике. Системам
  той же стадии запись видна со следующего тика.
- Запись живёт один полный оборот тика: к следующему барьеру той же стадии её прочли все потребители. Что нужно
  дольше — копируется в своё состояние.
- Деактивированный потребитель журнал не держит; при повторной активации его курсор ставится на конец журнала —
  прошлое не проигрывается.
- Порядок записей стабилен и не зависит от числа потоков.
- `CommandBuffer` проигрывается **на каждом барьере**, а не в конце тика.
- В конце каждого тика журналы читает **шаг экспорта Runtime** — служебная стадия `runtime.export` после барьера
  последней стадии игры (End), поэтому в экспорт тика попадают записи всех его стадий, включая End. Он копирует
  записи тика в очередь кадра клиента с номером тика (`TickId` — кадр из трёх тиков получает события всех трёх, кадр
  без тиков — ничего); историю для агента (`ObservationHistory`, раздел 8) снимает наблюдатель владельца после тика — из журналов по возрасту записей, без своего курсора (решено на точке 3в). Других внешних курсоров у журналов нет: клиент и
  агент получают копии и на освобождение памяти симуляции не влияют. Команды тика становятся событиями в служебной
  стадии `runtime.commands` до первой стадии игры — их видят все стадии игры, включая Begin, в том же тике.
- Сущность, созданная командой, становится живой на барьере (раздел «Создание сущностей: черновики»).

**Нормализация на барьере.** События (`Event<E>`) не склеиваются: сколько записали, столько и прочтут. Срабатывания
компонентов сводятся по паре (сущность, `T`) — сравнивается состояние до барьера и после него:

| до барьера → после | запись в журнале |
|---|---|
| нет `T` → есть `T` | один `Added<T>` — сколько бы `Set<T>` ни было после добавления |
| есть `T` → нет `T` | один `Removed<T>` со значением на момент снятия |
| есть → есть, значение заменено (один или несколько `Set<T>`; при отключённых проверках — и ошибочный `Add<T>` существующего) | один `Changed<T>` с итоговым значением |
| есть → есть, снят и добавлен заново | `Removed<T>` (старое значение), затем `Added<T>` |
| нет → нет (добавлен и снят на одном барьере) | ничего: для потребителей компонента не было; хуки при этом отработали оба |
| сущность удалена | `Removed<T>` по каждому компоненту, на который есть подписка, со значениями на момент удаления |
| сущность создана и удалена на одном барьере | ничего |

**Граничные тесты журналов** (обязательны для v0):
- производитель в той же или более поздней стадии — запись видна в следующем тике; без `NextTickOk` — ошибка
  сборки мира;
- производитель в предыдущей стадии — запись видна в текущем тике;
- черновик: отложенные значения в `Add`, `Set` и `Emit` разрешаются на барьере, включая вложенные структуры;
  черновик чужого буфера и обращение к миру с неразрешённым значением — исключение в Debug; одинаковые индексы при
  любом числе потоков;
- `Added<T>` и `Removed<T>` на одном барьере; снят и добавлен заново;
- два `Set<T>` до одного барьера — один `Changed<T>` с итоговым значением;
- удаление сущности — последнее значение `T` в `Removed<T>`;
- `deactivate` → `activate`: старые записи не воспроизводятся;
- одна система в двух стадиях: каждая регистрация видит запись один раз, действие выполняется один раз;
- экспорт тика в очередь кадра клиента и в `ObservationHistory` при кадрах с 0 и 3 тиками.

### Порядок и планировщик

- Порядок внутри стадии — **явные `After`/`Before`** по меткам систем. Порядок регистрации — только правило развязки
  для независимых систем, не контракт. Цикл зависимостей — ошибка при сборке мира.
- Метки систем ядра игры (`GameLabels.StrikeDetection` и т. п.) лежат в `Game.Contracts`: модуль встаёт до или после
  системы ядра, не видя её типа.
- Объявления чтения/записи — не про порядок, а про параллельность и проверку доступа (в Debug обращение
  к необъявленному — исключение).
- Параллельность внутри системы — `ForEachChunkParallel` поверх `Core.Jobs`; между системами — группы без конфликтов.
  Включается флагом после замера, без правки систем.

### Объём

| версия | что входит |
|---|---|
| v0 (прототип) | сущности, регистрация, архетипы и чанки, запросы `Read/Write/With/Without`, `CommandBuffer`, ресурсы, стадии и барьеры, `After/Before`, **журналы и реактивные системы** (`Added`, `Removed`, `Changed` через `Set` — при отключённых проверках и через ошибочный `Add` существующего, поэтому планировщик считает `Add` возможным производителем `Changed`, `Event`, `ResourceChanged`) с нормализацией на барьере, черновики сущностей, объявления производителей и проверка порядка стадий, идентичность регистрации, слот `CauseId` в записях, граничные тесты журналов; исполнение последовательное |
| v1 (по мере надобности) | хуки времени жизни ресурсов (к физике — сделаны на 5а), проверка доступа в Debug, версии изменений для Push, параллельные чанки и группы систем |
| нет | отношения, префабы, сериализация мира, управляемые компоненты, несколько миров, отслеживание изменений у всех компонентов подряд — пока нет потребителя |

### Цели производительности (BenchmarkDotNet)

- проход `Read` + `Write` по чанкам медленнее сырого цикла по `Span<T>` той же раскладки не более чем на 20–30 %
  на той же машине;
- создание, удаление и перенос между архетипами через `CommandBuffer`, запись и чтение журналов — без аллокаций
  в устойчивом режиме.

### Переходный паттерн

Где логику SWORD сразу разложить по компонентам рискованно, допустим **управляемый объект в пуле + хэндл
в компоненте** (`AnimatorRef { int Slot }` → аниматор бойца). Это инструмент, а не норма: у каждого такого пула
в md-документе фичи записан план растворения.

## 6. Подсистемы

Общий договор подсистемы:
- владеет своими данными — и только ими — в своей раскладке; наружу — хэндлы (индекс + поколение);
- тикается целиком, пачкой, с явными входами и выходами;
- тестируется и замеряется без мира ECS и без игры;
- получает настройки готовыми объектами при композиции — конфиг не читает;
- связь с ECS — только системами Push (ECS → подсистема) и Pull (подсистема → ECS + события) в своей стадии;
- отдаёт своё состояние как участник `IStateContributor` и приносит свои инварианты (раздел 8);
- API подсистемы, которую будут оптимизировать (Physics, Animation), допускает две реализации в одном процессе —
  для дифференциального прогона эталона и кандидата (раздел 8).

```
Entity ──┬─ Transform, PrevTransform          (ECS)
         ├─ Health, CombatState, FighterCommand
         ├─ BodyRef      → Physics.ArticulationHandle   (данные в физике; хуки держат время жизни)
         └─ PoseRef      → Animation.PoseSlot           (данные в пуле поз)
RenderWorld (клиент): инстансы отрисовки по Entity — заводятся и освобождаются по журналам Added/Removed
```

Системы Push/Pull в v1 живут в игре: она определяет компоненты. Появится второй потребитель — вынесем
в интеграционные сборки движка.

### Physics (`Sword.Engine.Physics`)

- **Владеет:** телами (капсулы), сочленениями (рэгдолл: суставы, пределы), контактами. Земля — `HeightField` из Geometry.
- **API:** `CreateBody`, `CreateArticulation` (набор тел и суставов), `SetKinematicTarget` (поза из анимации),
  `SetMode(Kinematic | Simulated)`, `ApplyImpulse`, `Step(dt, substeps)`, запросы (`Raycast`, `SweepCapsule`,
  `Overlap`), поток событий контактов.
- **Откуда логика:** `Sword.Physics` + физическое из игры: `DuelArena` (`SolveContacts`, `Collide`, `GroundEnd`,
  `PushOut`, `PrevOverlap`, `SolveContactVelocities`, трение, подшаги), `DuelArena.ContactVelocity`,
  `KinematicContacts`, `Fighter.Joints` и суставная часть `Fighter.Muscles` для трупа (`SolveConstraints`,
  `RelaxJointVelocities`, `PostVelocity`), `Body`, `RagTrace` (как диагностика физики).
- **Не физика:** клинок (это капсула, которую игра проводит `SweepCapsule`); что такое обломок, сколько ему жить
  и сколько их может быть (`Debris`, `DebrisLife`, `MaxDebris`) — политика игры: сущность с `BodyRef` и `Lifetime`;
  что считать ударом, пороги отруба, реакция на попадание — тоже игра.
- **Раскладка:** сначала логика SWORD за API хэндлов (сверка сценами рэгдолла); SoA и острова — отдельным шагом
  с микробенчмарком и дифференциальным прогоном против первой реализации, которая остаётся эталоном в тестах.
- **Инварианты:** конечность координат, живые хэндлы, энергия рэгдолла не растёт скачком за подшаг — последнее
  проверяется внутри шага в диагностическом режиме.

### Animation (`Sword.Engine.Animation`)

- **Владеет:** скелетами, библиотекой клипов, **пулом поз** (батчи по скелету), состояниями смешивания и MM.
- **API:** `AllocPose(skeleton)`, запросы проигрывания и смешивания, `Tick(jobs)` — сэмплинг всех активных поз пачкой
  (параллельно по батчам, SIMD); выход — позы в модельном пространстве, корневое движение, контакты стоп.
- **Откуда логика:** `Sword.Anim` (`AnimLibrary`, `SkeletalClips`, `AnimMath`, `LegIk`, `FootLock`, `FootPlacement`,
  `FootContacts`, `ContactDetector`, `Loco/*` — движковый Motion Matching). `IGround` → `HeightField`. `SwordBody` →
  игра. `LocoAudit` → `Game.DevTools`.
- **Остаётся в игре:** `FighterAnimator` (машина состояний боя), выбор ударов, окна ударов — это правила игры.
- **Motion Matching (этап 8):** механизм — в подсистеме, без знания игры и контента (`Pose2`, кинематика клипов, контакты стоп,
  схема признаков — вход, база с графом переходов, поиск, запрос, модель предсказания траектории, история корня, проигрыватели за
  хэндлами; переход — инерциализация заданием пула); политика контента (имена клипов GASP, отбор, правило продолжения, веса) — в
  модуле Locomotion. База строится из клипов при загрузке, один раз на процесс, неизменяема; пак и пекарня её не хранят.
- **Наблюдателям — только вид:** данные подсистем вне ECS (пул поз) видны только видом для чтения (`IReadView` в ECS,
  `WorldReader.View`; `IAnimationView` в `Game.Contracts` — не стратегия, ядро его не спрашивает); у каждой симуляции
  свой пул поз, задания он исполняет пачкой в Animation; общие ассеты анимации (`Skeleton`, `ClipLibrary`, `ActionTable`)
  неизменяемы — наружу только `ReadOnlySpan`; ассеты бойца грузит exe (`CharacterAssets`) и отдаёт в
  `Sword.Game.Bootstrap` готовыми — Bootstrap контент не видит (редакции Р10–Р11).

### Geometry (`Sword.Engine.Geometry`)

- Примитивы и пересечения (отрезок–отрезок из `Xpbd.SegSeg` и подобное).
- `HeightField` — **одна правда о рельефе**: игра строит поле высот из описания уровня; физика и IK читают его на CPU,
  шейдеры — те же узлы структурированным буфером. Дублирование `Terrain.cs` / `sim_common.hlsli` исчезает. Поле линейно
  между узлами: вертикальные уступы (подступенки пирамиды) физика получает явными примитивами рядом с полем, а не
  из него. **Уточнено на этапе 7:** симуляция (постановка живых с этапа 1, физика трупов с этапа 7) читает аналитическую
  функцию рельефа игры, физика — через свой интерфейс земли `IGround` (реализует игра: гладкий рельеф и ярусы пирамиды
  точными ящиками); `HeightField` — рендеру.
- Пространственные структуры (хэш-сетка, позже BVH) — общий тип, но **у каждого владельца свой экземпляр** со своим
  размером ячейки: широкая фаза физики, ИИ, проходы клинков.

### Render (`Sword.Engine.Render`)

- **Рендер-граф v0:** проходы объявляют читаемые и записываемые ресурсы (импортированные или временные); граф ставит
  барьеры сам и выделяет временные цели из пула. **Одна graphics-очередь**: `PassKind.Compute` — dispatch на ней же.
  Ресурсы — текстуры и структурированные буферы; буферы, чьё содержимое переживает кадр (состояние GPU-симуляций), —
  хранилища `GpuStorage`, импортируемые в кадр. Цели создаются с оптимальным значением очистки и чистятся только им.
  Проверка — GPU-тесты графа на настоящем устройстве с GPU-валидацией (точка 1б).
  Порядок — порядок регистрации (без переупорядочивания и отсечения). Отдельная compute-очередь, межочередные fence
  и async compute — вместе с первой GPU-симуляцией (была кровь, этап 12 — отложена, решение 15; теперь — первый потребитель); алиасинг
  памяти — позже.
- **Фазы кадра:** `Simulation` (compute) → `Opaque` → `Composite` → `Transparent` → `Ui` → `Debug`. Заменяют
  `ISceneOpaque`/`ISceneComposite` и слоты 10–12: у каждого прохода свои константы.
- **GPU-сцена:** буфер инстансов, палитры скиннинга, пул мешей; `SkinnedRenderer` — движковый проход скиннинга.
  Инстанс несёт `Entity` и сегмент тела — для ID-прохода пакета наблюдения `capture.bundle` в диагностическом режиме
  (раздел 8); проверка «граф не читает ресурс до записи» — инвариант клиента.
- **Extract:** рендер читает не ECS, а снимок `RenderWorld`, заполненный клиентом (интерполяция по alpha). Сейчас это
  `ArenaExport` + `SkinnedCharacters.Submit`. Позже снимок позволит рендеру уйти в свой поток.
- **GPU-симуляции** — первоклассная часть клиента:

```csharp
public interface IGpuSimulation
{
    void Create(GpuSimContext ctx);                               // постоянные ресурсы, двойная буферизация состояния
    void AddPasses(RenderGraphBuilder graph, in SimFrame frame);  // compute-шаг на каждый тик кадра
    void OnReadback(ReadOnlySpan<byte> data);                     // только представление и диагностика
}
```

  `SimFrame` — тики кадра (`TickId` от первого до последнего), их dt и заявки. **Каждая заявка CPU (спаун капли,
  частицы) несёт `TickId`**; граф ставит диапазон заявок тика t перед compute-шагом тика t. Асинхронный readback
  (задержка N кадров) никогда не влияет на авторитетную симуляцию. Тела бойцов (`GpuArena.Units/Segs`) — общий ресурс
  только для чтения; его раскладка и ключ в графе — в `Game.Contracts`. Кровь — эталонная реализация этого API;
  **песок — только после неё**.
- **Debug draw:** линии, капсулы, текст в мире — для диагностики фич.
- **UI-проход:** `UiRenderer`, `UiVectorFontGpu`, `ui.hlsl` — из `Sword.Engine.Ui` (`UiPass`, `Renderer.Ui`).

### Ui, Content, Formats, Platform

- **Ui** — без GPU: `UiContext` и виджеты, `UiDrawList`, `UiTextShaper`, данные векторного шрифта. Отрисовка — в Render.
  Виджеты `UiContext` (перенесены на 6е с тестами SWORD) — у панели ручек F3 (`Engine.DevTools/TuningPanel`) и панели
  инвентаря игры (`InventoryPanel`) в слое панелей клиента движка; HUD рисует списком квадов.
  Запекание шрифтов (`UiFontBaker`) — в `Bake.Engine`. Тесты UI идут без видеокарты.
- **Content** — хранилище: пак, источники (`PakSource`, `MemorySource`), поиск пака, загрузка с кэшем и хэндлами,
  крючок горячей перезагрузки. Стабильная ссылка на ассет (`AssetPath`/`AssetId`) — маленький тип в Core: ею
  пользуются Formats и `Game.Data`, не завися от Content.
- **Formats** — двоичные раскладки движка: меш, скелет, клипы, текстуры, шрифты, PNG; чтение **и запись** в одном
  файле с версией формата — их используют и рантайм, и пекарня. Игровые форматы — в `Game.Data`.
- **Platform** — абстракции окна, ввода и диалогов; Win32 — отдельно и без зависимости от UI
  (`UiInputWin32` → адаптер в Client).

## 7. Runtime и Client

### Разделение

| | Runtime (симуляция) | Client (представление) |
|---|---|---|
| что | мир ECS, стадии тика, барьеры, журналы, планировщик, фиксированный тик, модули (часть симуляции), конфиг, ГСЧ, реплеи, хеш состояния | окно, ввод → команды, цикл кадра, Extract, рендер-граф, GPU-симуляции, UI, снимки, бенч кадра, оверлей разработчика |
| зависит от | Core, Diagnostics, Ecs, Content | Runtime, Ecs, Platform, Rhi, Render, Ui |
| нужен GPU | нет | да |
| exe | `Game.Headless` — только `Sword.Game.Bootstrap`: реплеи, сценарии, бенчи симуляции, тесты | `Game.App` — `Sword.Game.Bootstrap` и клиент |

Симуляцию (`Simulation`) создаёт exe через `Sword.Game.Bootstrap` и отдаёт клиенту движка; тики исполняет только он.
Клиентская часть игры видит симуляцию через узкий `SimulationLink` (Engine.Client): мир только для чтения
(`WorldReader` — чтение компонентов и ресурсов-значений, запросы и обход без записи; ни немедленных операций, ни тика,
ни записи колонок), какие команды принимаются (`Accepts<T>`), команды на ближайший тик, время тика, — поэтому
`Sword.Game.Client` не ссылается на Runtime (точка 1в). Проверка — `PublicSurfaceTests.SimulationLink_ReachesOnlyReadOnlyWorld`:
из публичных сигнатур `SimulationLink` транзитивно не достижим ни один изменяющий тип ECS и Runtime.

### Тик (Runtime)

```
Тик — после каждой стадии барьер (раздел 5)
├─ Begin       время тика, Prev* для интерполяции
├─ Intent      команды игрока (из клиента или реплея), ИИ, сценарии → FighterCommand; команды арены → спаун, Set<WeaponSlot>
├─ Gameplay    смерти до физики → рэгдолл; настройка новых бойцов; смена оружия; решения боя, аниматор; Guard: выносливость (отложен — решение 16)
├─ Animation   Push → Animation.Tick → Pull: позы, корневое движение
├─ Movement    корни-контроллеры, постановка стоп (FootPlacement)
├─ PrePhysics  кинематические капсулы по позе
├─ Physics     Push → XPBD, подшаги → Pull
├─ Combat      проходы клинков → StrikeContact
├─ Defense     блок и столкновения клинков (Guard) → StrikeBlocked, Clash — пуста: Guard отложен (решение 16)
├─ Resolve     урон по неотбитым контактам → Hit, Dead, SeverRequested
├─ Dismember   расчленение отвечает на заявки (Cutting) → LimbDetached, обломки — пуста: Cutting отложен (решение 17)
├─ React       отдача и реакции на удары; последствия отруба (маска Severed, кровотечение)
├─ Aftermath   кровопотеря (→ Dead), возрождение, пересборка разбитых, политика обломков
├─ Settle      смерти тика → рэгдолл; «усадка» свежих отрубов (Cutting); статистика
└─ End         хеш состояния; запись реплея
служебные      runtime.commands до Begin: команды тика (игрока, арены, ручек, модулей) → события, их читают системы
               любой стадии игры в том же тике; runtime.export после барьера End: очередь кадра клиента и
               (история агента — наблюдатель после тика). Добавляет Runtime, модулям недоступны
между тиками   точка обслуживания агента: мир согласован, запросы из очереди исполняются здесь (раздел 8)
```

Раскладка повторяет порядок `DuelArena.Tick`:

| SWORD | SWORD2 |
|---|---|
| `Think` (мозги бойцов) | Intent |
| `SettleDeaths()` в начале тика — «умершие до физики» | Gameplay: первая регистрация `DeathToRagdoll` |
| `KinematicBegin`, `ResolveRoots`, `PlaceBodies` | Gameplay → Animation → Movement → PrePhysics |
| подшаги XPBD | Physics |
| `KinematicStrikes`, `ApplyHits` (с отрубом внутри `ApplyHit`) | Combat → Defense → Resolve → Dismember |
| `ApplyReactions`, `KinematicReactions` | React |
| `AfterTick` (кровопотеря), возрождение, пересборка | Aftermath |
| `SettleDeaths()` в конце тика — в том числе умершие от кровопотери и свежие отрубы | Settle: вторая регистрация `DeathToRagdoll`, усадка отрубов модулем Cutting |
| `TickEnded` (модули) | End; затем служебная `runtime.export` → очередь кадра клиента |

Одно намеренное отличие: в SWORD отруб выполняется внутри `ApplyHit`, поэтому второй удар того же тика по той же
части приходится уже по отделённой части. Здесь все удары тика применяются в Resolve, а отрубы — в Dismember; повторная
заявка на уже отделённую часть отклоняется. Случай редкий, записывается как намеренное изменение семантики
(раздел 12). Стадий может стать больше — барьер дешёвый.

### Кадр (Client)

```
Кадр
├─ Platform     сообщения окна, снимок ввода
├─ FrameBegin   GPU, профайлеры, горячая перезагрузка шейдеров
├─ Input        ввод + камера → команда игрока в мировых координатах (раздел «Ввод»)
├─ Simulate     накопитель → N тиков Runtime (≤ MaxTicksPerFrame); прибивка к границе тика для снимков
├─ Extract      журналы Added/Removed → инстансы; интерполяция → RenderWorld; события кадра → заявки GPU-симуляций с TickId
├─ Render       рендер-граф: GPU-симуляции (шаг на тик кадра) → сцена → композит → UI
└─ Present      Present, снимок, бенч кадра; на границе кадра — снимки и GPU-диагностика для агента (FrameId + TickId)
```

### Ввод

Клиент снимает ввод раз в кадр, а Runtime делает за кадр 0, 1 или несколько тиков. Правила:
- удерживаемые действия (движение, блок, цель под курсором) повторяются в каждом тике кадра;
- нажатие и отпускание потребляются **ровно одним тиком** — первым после кадра, в котором случились;
- кадр без тиков: фронт сохраняется до ближайшего тика; кадр из трёх тиков: `AttackPressed` не повторяется трижды;
- направление движения относительно камеры вычисляется в клиенте **до** записи команды: симуляция камеры не знает;
- реплей хранит готовые команды по тикам (`PlayerCommand` — уже в мировых координатах), а не клавиши; `FighterCommand` —
  намерение бойца, его пишет Intent из команды игрока, ИИ или сценария.

Клавиши арены (число врагов PageUp/PageDown, сброс R, смена оружия T, инвентарь 1–9) в SWORD меняют арену прямо
из `Program.cs`; здесь они — `ArenaCommand` из `Game.Contracts` по тем же правилам: фронт — ровно одним тиком,
в реплей — готовой командой. Привязки клавиш к действиям (`Attack`, `Block`, `Dodge`, `Move`, `ToggleHud`…) —
в конфиге.

### Модули

Четыре вида модульности — это разные уровни сложности, в v1 они разведены:

| вид | в v1 | как |
|---|---|---|
| отдельная сборка | да | модуль — сборка симуляции и/или клиентская сборка; подключается к exe статически |
| активация при запуске | да | `modules.<id>.enabled` в конфиге; неактивный модуль не регистрирует ничего |
| сборка без модуля | проверка | конфигурация `-p:Without<Модуль>=true` (как `DisableCutting` в SWORD): exe собирается без ссылок на модуль |
| деактивация на ходу | ограниченно | `deactivate`: системы модуля перестают исполняться, его проходы пропускаются, курсоры отпускают журналы; компоненты и ресурсы остаются. Полная горячая деактивация (удалить компоненты, дождаться fence GPU, освободить проходы и ресурсы) — поздний этап |
| выгрузка сборки | нет | `AssemblyLoadContext` не используется; слово «unload» не используется |

Хост ведёт **регистрационный токен модуля**: какие системы, курсоры журналов, проходы, ручки и строки бенча
принадлежат `ModuleId`. `deactivate` и `activate` работают по токену и, как любое изменение симуляции на ходу,
приходят командой с `TickId` (раздел «Детерминизм»). Проверки `SWORD_*_DISPOSE_AT` из SWORD (освобождение модуля
посреди игры) в v1 заменяет `modules.<id>.deactivateAt`.

Регистрация модулей симуляции — только в `Sword.Game.Bootstrap` (раздел 3); `Game.App` добавляет к ней клиентские.
Ядро (принцип 4) регистрируется тем же построителем, но не как модуль: `Simulation.Build(config, stages, core, modules)` —
без токена модуля и без ключа `modules.<id>`, выключить его нельзя.

```csharp
public interface IModule                          // Engine.Runtime; реализует сборка симуляции модуля
{
    string Id { get; }                            // латиницей: ключ конфига, логи, реестр
    void Configure(SimulationBuilder b);          // настройки, компоненты, системы по стадиям (After/Before), ручки, строки бенча
}

public interface IClientModule                    // Engine.Client; реализует клиентская сборка модуля
{
    string Id { get; }                            // тот же Id, что у симуляции модуля (или свой — у чисто клиентского)
    void ConfigureClient(ClientBuilder b);        // Extract, проходы рендера, GPU-симуляции, шейдеры, HUD
}
```

У модуля один `Id` на обе стороны: `modules.cutting.enabled` включает и `Sword.Game.Cutting`, и
`Sword.Game.Cutting.Client`; клиентская часть активна, только когда активен модуль. Построители узкие:
`SimulationBuilder` знает ECS, стадии, конфиг и ручки; `ClientBuilder` — рендер-граф, GPU-симуляции и UI.

- **Точки расширения** — стадии и метки систем, события и компоненты из `Game.Contracts` (протокол — раздел 9).
- **Стратегий-вопросов нет.** Сейчас ядро спрашивает модуль и ждёт ответа: `DuelArena.DetachStrategy`
  (`ILimbDetachmentStrategy`, `ChainedDetachment`), `DuelArena.Guard` (`IStrikeGuard`), `DuelArena.BodyPlacer`
  (`IBodyPlacer`), `FighterAnimator.SetLocomotion` (`ILocomotionSource`). Такой вопрос требует ответа и без модуля —
  отсюда и росли запасные пути. В `Game.Contracts` таких интерфейсов нет.

### Конфигурация

Живёт в Runtime. Слои, каждый перекрывает предыдущий: значения в коде → `sword.json` (в репозитории) →
`sword.user.json` (вне git) → переменные `SWORD_<СЕКЦИЯ>_<КЛЮЧ>` → ключи `--set секция.ключ=значение`.
Секции — типизированные записи. Подсистемы конфиг не читают: получают готовые объекты настроек при композиции;
ручки (`TuningGroup` из Diagnostics) привязываются к этим объектам там же. **Изменение ручки на ходу — команда
симуляции:** панель F3 ставит её на ближайший тик, в служебной стадии `runtime.commands` она становится событием с
`TickId` и применяется системой ручек в том же тике (для реактивных систем —
`ResourceChanged`) и записывается в реплей. Соответствие ~70 нынешних `SWORD_*` новым ключам составляется по мере
переноса фич; ручки живого рэгдолла не переносятся.

### Диагностика

`Log` с категориями вместо `Console.WriteLine("[sword] …")`, без аллокаций; профайлер CPU по стадиям и системам;
GPU — по проходам графа; счётчики (выделенные байты на тик, сборки GC, ожидание GPU); каналы трасс (обобщение
`RagTrace`, `MM_TRACE`, `HITTRACE`, `FEET_TRACE`).

Действующие правила производительности (приняты на этапах П и 6; полный текст —
[docs/history/stage-p.md](docs/history/stage-p.md), [docs/history/stage-6.md](docs/history/stage-6.md)):
- **Долгие циклы (OSR):** метод, который вызывается раз в тик или кадр и содержит долгий цикл, — тело цикла в отдельный
  метод (иначе многоуровневый JIT заменяет его на ходу — рывок на главном потоке); `AggressiveOptimization` — только
  тонкому методу из вызовов или примитивному циклу без пользы от PGO (корневой `AGENTS.md`; AGENTS.md Runtime, Client,
  Render).
- **Профайлер** (`--profile`, `profile.stages`) симуляцию не трогает: в хеш и реплей не входит, выключенный стоит ~0,
  включается ключом запуска или агентом, а не командой симуляции; GPU-таймстемпы проходов включены всегда. Не делаем:
  стеки вызовов в процессе (рецепт `dotnet-trace`/PerfView — playbook), события ядра ETW, статистику конвейера GPU,
  снимки кучи.
- **Служебные кадры App** не судятся профайлером и не входят в средние, худший кадр и байты итога прогона: все кадры до
  первого сыгранного тика включительно и кадры, в которых точка обслуживания выполнила хотя бы один запрос агента
  («кадры инструментов»; критерий — «выполнял запросы», а не время; аномальный тик такого кадра судится).
- **Машина пользователя:** замеры несут вердикт «код / среда / машина» (`MachineReport`); провал времени из-за фоновой
  нагрузки сообщается пользователю, пределы не ослабляются; время потока пределом бюджета не стало (отдельное решение
  пользователя).

### Детерминизм, реплеи, эталоны

- **Авторитетна только симуляция.** Представление читает её и на неё не влияет; readback с GPU идёт только
  в представление и диагностику.
- **Счётчиковый ГСЧ.** Случайное число — чистая функция `f(главное зерно, поток, TickId, Entity, номер выборки)`
  (хеш-функция уровня Philox/xxHash). Решение конкретного бойца не зависит от порядка обхода, потока исполнения
  и от того, сколько случайных чисел взяли другие системы. У представления свои потоки, в реплей они не входят.
- **Всё, что меняет симуляцию на ходу, — команда с `TickId`:** команды игрока и арены, изменения ручек, деактивация
  и активация модулей. Клиент ставит их на ближайший тик, симуляция в служебной стадии `runtime.commands` делает
  из них события этого тика (их применяют системы стадий игры), реплей записывает.
  Отдельных «тихих» путей изменить симуляцию мимо команд нет.
- **Реплей** хранит: версию сборки (коммит), хеш `Content.swpak`, fixed dt и число подшагов, полный конфиг запуска
  (после всех слоёв), список активных модулей, главное зерно, команды по тикам (игрока, арены, ручек, модулей) и
  **хеш состояния мира каждые K тиков**. При воспроизведении первое расхождение хеша называет тик.
- **Хеш состояния:** сущности — в стабильном порядке (по `Entity`), компоненты — по стабильному имени; хешируются
  **поля**, а не сырые байты структур (padding не участвует); `-0` приводится к `+0`, NaN — к одному значению.
  Функция хеширования полей генерируется при регистрации компонента.
- **Вклад подсистем.** В ECS лежат только `BodyRef` и `PoseRef`, а Runtime не знает ни Physics, ни Animation —
  поэтому зависимость обращена:

```csharp
public interface IStateContributor                        // Engine.Runtime
{
    string Id { get; }                                    // стабильный: "physics", "animation", …
    void AppendHash(ref StateHasher hasher);              // полное авторитетное состояние, в стабильном порядке хэндлов
    void Describe(StateWriter writer, in DescribeQuery q); // то же состояние для людей и агента, с отбором
}
```

  Интеграционные системы игры регистрируют участников: `physics` — тела и сочленения, `animation` — авторитетные
  состояния аниматоров и поз, при необходимости другие. Runtime обходит их по `Id`. В реплей пишется хеш
  **по каждому участнику** — расхождение сразу называет не только тик, но и подсистему. `Describe` описывает ровно
  то, что хешируется: при расхождении агент сравнивает два описания, а не гадает (раздел 8). Нужно к этапу 3.
- **Эталоны SWORD2** (`tests/reference/replays/*.swreplay`) фиксируются после подтверждения фичи пользователем
  (раздел 12). Изменение, которое меняет хеши, перезаписывает их теми же командами с доказательством: участники, которых
  изменение не касается, и траектории бойцов совпали тик в тик (перезаписи этапов 4–6 — `docs/history/stage-*.md`).
- Бенч, сценарии (`IScenario`: сцены рэгдолла, маршруты автопилота), снимок, прибитый к тику, — как в SWORD.

## 8. Агентский доступ

Движок рассчитан на то, что его запускает, наблюдает и отлаживает ИИ-агент — Claude Code, Codex (GPT) или любой
другой MCP-клиент. Агент — такой же пользователь движка, как человек: у человека панели DevTools, у агента —
инструменты MCP, и оба стоят на одном слое интроспекции. Отсюда же автоматический контроль фич (решение 4).

**Агентский API отвечает на проверяемые вопросы, а не выгружает внутренности движка (решение 13):** почему это
случилось, выполняется ли условие, чем отличаются два прогона, что будет, если изменить параметр. Цель — агент как
экспериментатор над движком, а не удалённый оператор панелей.

### Слои

```
агент (Claude, GPT…) ──MCP──► Engine.Agent — хост: реестр инструментов, сеансы, квитанции, артефакты и снимки,
                              │               инструкции сервера
                              ├─ вопросы: условия, инварианты, причинность, история, снимки и сравнения
                              ├─ эксперименты: реплеи, ветвления, перебор параметров, минимизация, дифференциальные прогоны
                              ├─ приёмка: FeatureManifest → feature.verify
                              ├─ Engine.Agent.Client — пакет визуального наблюдения, GPU-время (только в Game.App)
                              └─ Game.Agent — игровые виды и пробы: бойцы, арена, сценарии
человек ──────────── UI ────► Engine.DevTools / Game.DevTools
                                │
                  Engine.Introspection — общая основа: очередь запросов и точка обслуживания; компоненты по
                  стабильным именам и полям; IStateContributor.Describe; ObservationHistory; журнал причинности;
                  язык условий; управление инвариантами (контракт IInvariant и проверка после барьеров — в Runtime);
                  карта архитектуры; управление временем; постановка команд
```

Ядро игры и модули об агенте не знают: своё состояние они отдают через `IStateContributor` (раздел 7), события —
через шаг экспорта в конце тика, проверки — через инварианты и манифесты фич. Runtime не знает ни MCP, ни моделей:
протокол живёт только в `Engine.Agent`.

### Потоковая модель

Главная гарантия агентского слоя: **агент не гоняется с симуляцией и рендером.**

- Обработчик MCP живёт на своём потоке и **никогда напрямую не читает** `World`, Physics, Animation или Render.
- Запрос к симуляции ставится в очередь и исполняется **на потоке симуляции в точке обслуживания** — между тиками,
  после экспорта тика (служебная стадия `runtime.export`), когда мир согласован. `Game.App` обслуживает очередь раз в кадр после шага Simulate (и на паузе),
  `Game.Headless` — после каждого тика (и на паузе). По запросу `time.break` точка обслуживания ставится после
  барьера нужной стадии — останов посреди тика.
- В точке обслуживания данные только **копируются** в ответ; разбор, JSON и отправка — на потоке агента. У точки есть
  бюджет времени на тик; тяжёлые запросы в живом App исполняются только на паузе.
- **Каждый ответ содержит квитанцию** (ниже) — с `TickId`, а при останове посреди тика и со стадией.
- Снимок кадра и GPU-диагностика исполняются **на границе кадра** клиентом и возвращают `FrameId` вместе с `TickId`
  показанного состояния.
- Мутация только **ставит команду на конкретный будущий тик** (по умолчанию — ближайший); в текущий и прошедшие тики
  писать нельзя.
- Панели DevTools читают мир по тем же правилам — через точку обслуживания и Extract, а не напрямую: когда рендер уйдёт
  в свой поток, менять их не придётся.

### Квитанции, артефакты, снимки

- **Квитанция в каждом ответе:** `BuildId`, `ContentHash`, `SessionId`, `TickId`, `Stage`, `FrameId`, `Complete`,
  `Truncated`, `ContinuationToken`, `ArtifactId`. По ней видно, к какому состоянию относится ответ и полон ли он.
- **Большое остаётся на стороне сервера** под `ArtifactId` в `artifacts/agent/<сеанс>/`; в ответе — сводка и путь.
- **`world.snapshot`** сохраняет наблюдательную копию состояния (компоненты по стабильным именам + `Describe`
  подсистем) под `SnapshotId`; **`world.diff(a, b)`** сравнивает два снимка на сервере — модели не нужно передавать
  оба состояния. Это не сериализация для восстановления мира — её в v1 нет (раздел 5).
- **Ответы под бюджет контекста:** сводка, пагинация, лимиты. У MCP-клиентов есть предел размера ответа инструмента —
  ответы проектируются заведомо меньше.
- **Инструкции сервера MCP** — короткие: рекомендуемый порядок расследования, ограничения, стоимость тяжёлых
  инструментов. У инструментов — аннотации: только чтение или мутация, класс стоимости.

### Язык условий: ObservationPredicate

Условия нужны многим инструментам сразу, поэтому язык у них **один** — типизированное JSON-дерево:

```
all:
  - component: Transform
  - field: Transform.Position.Y
    lessThan: -10
```

- Узлы: `all`/`any`/`not`; наличие компонента; сравнения полей (`lessThan`, `between`, `isFinite`…); «событие
  случилось» (тип, отбор по полям, окно тиков); агрегаты по запросу (`count`, `min`, `max`, `sum`, `mean`); наборы
  сущностей; окна тиков; стадия.
- На нём строятся: `time.runUntil(условие)`, `time.break(стадия, условие)`, `watch.add(условие, проекция)`,
  `invariant.define(условие)`, `profile.captureWhen(условие)`, проверки в сценариях и манифестах фич.
- **Произвольного C# нет** — только операции из белого списка. Условие компилируется при установке в быстрый
  исполнитель, его стоимость видна агенту; исполняется на потоке симуляции (в точке обслуживания или после нужного
  барьера), детерминировано и состояние не меняет.

### Инварианты

```csharp
public interface IInvariant                      // Engine.Runtime, как IStateContributor: реализуют игра и модули
{
    string Id { get; }                           // стабильный: "physics.finite", "fighter.deadNotKinematic", …
    InvariantCost Cost { get; }                  // каждый тик, раз в N тиков, по запросу
    InvariantScope Scope { get; }                // сущность, система, подсистема (в т. ч. внутри шага), мир, клиент
    string After { get; }                        // после барьера какой стадии (имя; runtime.export — конец тика)
    void Evaluate(in InvariantContext ctx, ref ViolationSink violations);
}
```

- Инварианты в коде регистрируют подсистемы, игра и модули; агент добавляет свои условиями — `invariant.define`.
- Нарушение — структурированный факт `InvariantViolation { Id, TickId, Stage, Entity?, Details }`: попадает
  в `ObservationHistory`; `time.breakOnInvariant` останавливает симуляцию в точке обслуживания после нарушившего барьера.
- Примеры: все координаты конечны; каждый `BodyRef` указывает на живое тело; одна физическая ручка принадлежит ровно
  одной сущности; мёртвый боец не остаётся кинематическим; энергия рэгдолла не выросла в 100 раз за подшаг; модуль
  после выключения не оставил своих компонентов; рендер-граф не читает ресурс до записи.
- Проверки внутри шага подсистемы (подшаги физики) живут в самой подсистеме и включаются в диагностическом режиме.
- Режимы: в тестах и `verify` — все дешёвые включены; в бенче — выключены (их стоимость меряется отдельно); в игре —
  по конфигу. Исправления после Пд: в живой игре (Sword.exe) тяжёлые — раз в 4 тика (`InvariantCost.Heavy`,
  `SimulationInvariants.LivePeriods`), везде остальном — каждый тик. Инвариант ничего не меняет, его стоимость измеряется.
- Инструменты: `invariant.list`, `invariant.run`, `invariant.enable`, `invariant.define`, `time.breakOnInvariant`.
- Решено на точке 3г: стадия — имя (стадии мира — строки, отдельного `StageId` нет); `InvariantCost` — период в тиках
  (1 — каждый тик, N, 0 — по запросу: сам не включается, включённый явно — каждый тик); Id — части из латиницы, цифр и
  `_` через точку, первой — строчная буква; режим — `sim.invariants` (по умолчанию включены; бенч кадра — выключены);
  `TickId` нарушения — номер тика, в котором нарушено (как у событий); в живой игре `time.breakOnInvariant` встаёт после
  тика нарушения (посреди тика — только Headless, как `time.break`). Базовые: движка — `ecs.finite` (каждый тик),
  `ecs.entityRefs` (по запросу); анимации — `animation.finite`, `animation.settled`, `animation.pool`,
  `animation.owners`; модуля Locomotion — `locomotion.poses`. Поз без владельца ядро не ищет: позы модуля лежат в его
  компонентах — их держит инвариант модуля.

### Причинность: state.why

Агент спрашивает не только «что», но и «почему»:

```
state.why(player, "Health.Value")
→ Health: 100 → 64 · тик 1842 · система HitApply@Resolve
  причина: PlayerCommand.Attack → StrikeContact → Hit → Set<Health>
  источник: HitApplySystem.cs:117
```

- **Диагностический режим** (выключен по умолчанию; включение не меняет хеш состояния): команды, события и записи
  `Set<T>` получают `CauseId`, `ParentCauseId`, `TickId`, стадию, регистрацию системы и источник
  (`[CallerFilePath]`/`[CallerLineNumber]` у методов команд). Записи идут в ограниченный кольцевой `CausalityLog`.
- **Родительская причина** передаётся сама: реактивная система обрабатывает срабатывания, у каждого есть `CauseId`,
  и всё, что она порождает при обработке, получает его родителем (окружение `ctx.Cause` при обходе или явный параметр).
  Корни цепочек — команды игрока, арены и агента.
- **Точность — честно:** для дискретных фактов (команды, события, `Set` реактивных компонентов) цепочка точная;
  для непрерывных чисел (`Transform` из физики) — грубая: какая регистрация системы писала столбец в каком тике.
  На вопрос «почему число такое» отвечают история, `time.break` и дифференциальный прогон.
- **Слот `CauseId` в записях команд и событий есть с ECS v0** (вне диагностического режима пуст) — дооснащать ECS
  не придётся.
- Глубже кольца — `replay.observe` с включённой причинностью.

### Контракт фичи: FeatureManifest и feature.verify

Приёмка фичи (раздел 12) описывается машинным манифестом рядом с её md-документом (`feature.json`):

| поле | что в нём |
|---|---|
| `FeatureId`, `SourceRoots` | имя фичи и где её код |
| `RequiredModules` | с какими модулями она проверяется |
| `Scenarios` | сценарии и их проверки (условия) |
| `Invariants` | инварианты, которые должны держаться |
| `ExpectedMetrics` | метрики с допусками — свои числа (с 7а, решение 14) |
| `VisualViews` | какие пакеты наблюдения снять (ракурс, оверлеи) |
| `PerformanceBudgets` | время стадий и систем, байты на тик — со статистикой повторов; кадр App (с точки 4д) |
| `HumanChecklist` | список «что проверить в игре» для пользователя |

- **`feature.verify(id)`** одним воспроизводимым вызовом: запускает сценарии в `Headless`, проверяет инварианты,
  сравнивает метрики, снимает виды в App, проверяет бюджеты — и выдаёт краткий итог с путями к артефактам.
- **Вердикт независим от агента:** он опирается на инварианты, эталоны и подтверждение пользователя в игре, а не на
  мнение того же агента. Ослабить ожидания манифеста (допуски, инварианты) молча нельзя — только явной правкой,
  в коммите и с сообщением пользователю.
- Решено на точке 3д: манифест — JSON с комментариями (`format: sword-feature`, `version: 1`), строгий разбор (неизвестный
  ключ, тип, ссылка на несуществующий сценарий — ошибка с путём); поля плана — `id`, `sourceRoots`, `requiredModules`,
  `scenarios`, `invariants`, `metrics`, `views`, `budgets`, `checklist`. Сценарий — реплей из репозитория (хеши
  сверяются) или команды по тикам (`{command, fields, from, to}`) на конфиге из кода; каждый сценарий записывается, его
  проверки — условия `ObservationPredicate` после тика (`always`, `never`, `eventually`, `atEnd`, окно `tickId`).
  Инварианты манифеста включаются явно; нарушение любого включённого инварианта — провал. Метрика — поле сущности
  (несколько листьев — длина вектора) после тика или `min/max/mean` окна против `expected ± tolerance`. Бюджет —
  отдельные прогоны как бенч (без инвариантов, записи и сверки хешей), медиана повторов: мс на тик, мс стадий (время от
  барьера до барьера; время систем — отдельный прогон с профайлером, с Па), байты на тик; время проверяется только
  в Release, байты — всегда. Вид — кадр `Sword.exe --replay`
  по записи сценария (App сверяет хеши с Headless); эталонных снимков нет — кадры смотрят глазами. Чек-лист = пункты
  «Что проверить в игре» md фичи (тест). Логика — Introspection (`FeatureVerifier`), инструменты — `feature.list`,
  `feature.verify`, без агента — `Sword.Headless --feature ID|all` (код 4 — провал), `verify.ps1` шаг `features`.
  Манифесты задним числом — `movement`, `control`, `tools` (прототип), `animation`, `determinism`.

### Эксперименты

- **`experiment.fork(реплей, тик, варианты)`** — пересчитать реплей до тика в `Headless` и продолжить ветками
  с вариантами (команды, конфиг, модули, ручки); ветки идут параллельными процессами.
  **`experiment.compare(ветки)`** — метрики, хеши, первое расхождение, разница описаний.
- **`experiment.sweep(параметры)`** — перебор комбинаций в `Headless`; на выходе: время стадий и систем, число
  обработанных сущностей, аллокации и память, хеш результата, статистическая устойчивость (повторы, медиана, разброс)
  и место первого резкого ухудшения масштабирования. Пример:

```
fighters = [100, 1000, 10000]
workers  = [1, 2, 4, 8, 16]
lod      = [hero, hybrid, crowd]
```

  Такие переборы масштабирования осмысленны после параллельного планировщика и LOD-уровней; сам механизм — раньше.
- Основа всего — детерминизм, реплеи и `Headless` как пакетный исполнитель.
- Решено на точке 3д: ветки `experiment.fork` — потоки одного процесса, а не процессы (симуляции независимы, общие только
  неизменяемые ассеты; процессы — когда понадобится изоляция падений); вариант ветки — `set` (конфиг действует с тика 0:
  конфиг собирает симуляцию), `commands` с тика развилки и позже (перебивают команды реплея своего типа), `cut` (команды
  реплея после развилки не идут — `Replay.Head`); «ручка с тика T» — команда ручки (`TuningCommand`, с 6е). Ветка
  записывается с хешем каждого тика и сравнивается с записью базы: команда тика T
  меняет состояние после T+1 тиков. `experiment.compare` — `ReplayDiff` и листья описаний разошедшихся участников на
  первом разошедшемся хеше. `experiment.sweep` — комбинации (до 64) по очереди, повторы, медиана и разброс, мс стадий,
  байты, детерминизм итогового хеша, «резкое ухудшение» — время растёт больше чем в 1,5 раза быстрее числового ключа.

### Минимизатор: replay.minimize

`replay.minimize(условие ошибки)` — дельта-отладка над реплеем: убирает лишние команды, бойцов, модули, ключи
конфига, хвост тиков, части сценария, пока ошибка (условие или инвариант) ещё воспроизводится. Итог — короткий реплей
и его описание `scenario.json`: вместо десятиминутной битвы — «два бойца, 47 тиков, одна команда удара». Отрезать
начало (стартовать посреди боя) можно будет, когда появится сериализация мира.

### Дифференциальное исполнение подсистем

`differential.run(reference, candidate)` — две реализации одного API подсистемы (например, `Physics.Sequential`
и `Physics.ParallelSoA`) получают одинаковые входы; после каждого шага сравниваются положения и скорости, контакты,
решения суставов, события — с допусками, — и производительность. Два режима: пошаговый с пересинхронизацией
(ошибка одного шага) и свободный прогон (накопленное расхождение).

- **Эталонная реализация — не запасной путь** (решение 9): в игре работает одна реализация, эталон живёт в тестах
  и диагностике как оракул для оптимизаций (SoA, SIMD, параллельность).
- **Требование уже сейчас:** API подсистем (Physics, Animation) допускает две реализации в одном процессе.

### Пакет визуального наблюдения: capture.bundle

Вместо голого снимка — пакет: цвет; глубина; ID сущности на пиксель; нормали; векторы движения; отдельные
отладочные оверлеи (капсулы, контакты, проходы клинка, скорости); список видимых сущностей с экранными
прямоугольниками и именами («левое предплечье бойца 17»); камера; `TickId`, `FrameId`. Мультимодальная модель
понимает сцену по данным, а не угадывает по пикселям. Требование к рендеру: инстансы GPU-сцены несут `Entity`
и сегмент тела; ID-проход — в диагностическом режиме.

### Карта архитектуры из живого мира

`architecture.projects`, `ecs.plan`, `ecs.explainSystem`, `ecs.componentUsage`, `render.graph`, `module.graph` —
строятся из фактически собранного мира, а не из документации. Например, `ecs.explainSystem("HitApply")` возвращает:
стадию и порядок, чтение и запись компонентов, порождаемые события, потребляемые журналы, зависимости и `NextTickOk`,
исходный файл (caller info при регистрации), активна ли система в текущей конфигурации. Метаданные у планировщика,
реестра и рендер-графа есть и так — карта почти бесплатна.

### Оценка агентского интерфейса: Sword.Agent.Evals

Удобство для агента — измеряемое свойство, а не ощущение:
- набор типовых неисправностей — **модули-неисправности** `Sword.Game.Faults` (модуль симуляции, включается
  конфигом; каждая неисправность — известная ошибка; в сборку игры не входит);
- ожидаемый диагноз, допустимое число вызовов инструментов, время до локализации, объём возвращённых данных, доля
  ложных выводов, получен ли минимальный реплей;
- прогон — скрипты, запускающие агента (Claude Code, Codex) в неинтерактивном режиме против `Headless`, и подсчёт оценок.

Так выясняется, полезен ли `state.why`, какие ответы слишком многословны, каких агрегатов не хватает, какие
инструменты агент вызывает в неправильном порядке.

### Инструменты

Несколько композиционных инструментов вместо десятков узких: условия, проекции и агрегаты — параметры, а не новые
команды.

| группа | инструменты |
|---|---|
| сеанс | `session.start` (Headless или живой App; конфиг, модули, зерно), `session.status`, `session.stop` |
| время | `time.pause`, `time.resume`, `time.step(n)`, `time.runUntil(тик или условие)`, `time.break(стадия, условие)`, `time.breakOnInvariant`, `time.seek(тик)` |
| мир | `world.types` (типы данных и их поля), `world.query(условие, проекция, агрегаты)`, `entity.get`, `world.snapshot`, `world.diff` |
| история | `watch.add(условие, проекция)`, `watch.remove`, `entity.history`, `events.history` (из `ObservationHistory`), `replay.observe` (глубже кольца) |
| почему | `state.why(сущность, поле)`, `state.describe(id, отбор)`, `state.hash` — по участникам |
| проверки | `invariant.list`, `invariant.run`, `invariant.enable`, `invariant.define` |
| команды | `command.send` — игрока, арены, ручек, модулей; всегда на будущий тик |
| реплеи и эксперименты | `replay.record`, `replay.save`, `replay.load`, `replay.diff`, `experiment.fork`, `experiment.compare`, `experiment.sweep`, `replay.minimize`, `differential.run` |
| приёмка | `scenario.list`, `scenario.run`, `reference.compare`, `feature.verify` |
| устройство | `architecture.projects`, `ecs.plan`, `ecs.explainSystem`, `ecs.componentUsage`, `module.graph`, `render.graph` |
| диагностика | `profile.stages`, `profile.captureWhen(условие)`, `log.tail`, `trace.read` |
| клиент (App) | `capture.bundle`, `gpu.passes` |

### Правила

- **Один протокол — MCP**: его понимают Claude Code, Codex и другие клиенты. Транспорт: stdio для
  `Game.Headless --agent`; для живого `Game.App --agent` — Streamable HTTP на 127.0.0.1 (решено на точке 1е: HTTP
  Claude Code подключает без моста; свой HTTP/1.1 на `TcpListener`, потому что http.sys без прав администратора
  резервирует не всякий адрес). Реализация — свой минимальный JSON-RPC по спецификации MCP (решено на точке 1е:
  официальный SDK тянет хостинг и внедрение зависимостей в exe игры, а нужны четыре метода).
- **По умолчанию — только чтение.** Всё, что меняет симуляцию, — команды с `TickId` (ручки, команды игрока и арены,
  модули); они пишутся в реплей. Сеанс агента воспроизводим и проверяем человеком: вот реплей, вот что агент сделал.
- **Стабильные имена и коды ошибок** — те же, что в ECS, конфиге и журналах; ответ — JSON по схеме инструмента.
- **Отладка держится на детерминизме:** `time.seek`, `replay.diff`, эксперименты и минимизатор работают, потому что
  симуляция детерминирована (раздел 7).
- **Только локально и только при разработке:** выключено по умолчанию, включается ключом `--agent`; сборка
  `-p:WithoutAgent=true` не содержит сборок агента и модулей-неисправностей; сам агент в хеш состояния не входит и мимо
  команд ничего не меняет.
- **Жизнь сервера агента** (6а, 6ж): `Sword.Headless --agent` выходит по концу stdin, по концу родителя и после 15 мин
  без вызовов (`--idle-exit`; клиент переподключает сам); дети инструментов и фоновые запуски `verify.ps1` — в задании
  Windows `KILL_ON_JOB_CLOSE`; сервер собирается с `-nodeReuse:false` (узлы MSBuild не висят).
- **Фича без агентского вида не принимается:** её состояние видно через `IStateContributor.Describe`, её приёмка
  описана манифестом (раздел 12).

### Чего не делаем

- произвольное выполнение C# через MCP;
- прямой доступ агента к памяти ECS;
- правки `AGENTS.md` агентом без просмотра человеком: агент предлагает, человек принимает;
- десятки узкоспециализированных команд вместо нескольких композиционных;
- приёмку фичи только по заключению того же агента — без независимых инвариантов, эталонов и подтверждения в игре;
- модель-специфичные типы внутри Runtime.

### Правило: каждое изменение кода — проверка агентских инструментов

При написании любого кода — фичи, модуля, системы, исправления — отвечаем на вопрос: **сможет ли агент увидеть,
проверить и отладить это изменение уже имеющимися инструментами?** Если нет — вид, инвариант или инструмент
добавляется в том же изменении, а не «потом».

| что появилось в коде | что проверить и, если нужно, добавить |
|---|---|
| новое состояние (компонент, поле подсистемы) | видно ли через `world.query`/`entity.get` по стабильному имени или через `IStateContributor.Describe`; нет — расширить `Describe` |
| новое свойство, которое должно всегда держаться | инвариант (`IInvariant`) с классом стоимости |
| новое событие или факт | стабильное имя; передаётся ли причина (`CauseId`); попадает ли в `ObservationHistory` |
| новая механика с приёмкой | `FeatureManifest`: сценарии, инварианты, метрики, виды, бюджеты, чек-лист |
| новое видимое (эффект, тело, траектория) | оверлей и ID в `capture.bundle` |
| новый способ воздействия (клавиша, ручка, режим) | команда для `command.send` с записью в реплей |
| новая трасса или отладочный вывод | канал для `trace.read`, а не `Console.WriteLine` |
| новая подсистема | участник `IStateContributor`, её инварианты; если её будут оптимизировать — API, допускающий дифференциальный прогон |
| для отладки пришлось писать временный скрипт, лог или выписывать числа руками | сигнал, что инструмента не хватает: превратить это в инструмент, вид или инвариант |

- **Сначала расширять существующее** — `Describe`, инвариант, сценарий, оверлей, условие. Новый инструмент MCP —
  только если существующие не покрывают задачу; у него схема ответа, лимиты, тест и строка в `docs/agent-playbook.md`.
- **Итог анализа записывается всегда**, даже если ничего не понадобилось: в md фичи или модуля — раздел «Агентский
  доступ» (что агент видит и чем, что добавлено); в отчёте о приёмке — «инструменты агента: добавлены …» или
  «не требуются: …, потому что …».
- **Устаревшие инструменты удаляются** вместе с кодом, который они обслуживали.

### Знания агента

- **Корневой `AGENTS.md` короткий:** сборка и проверка (`verify.ps1`), правила слоёв, порядок приёмки фич, правило
  анализа агентских инструментов, ссылки. Его читают Codex и другие агенты.
- **Вложенные `AGENTS.md` рядом с подсистемами и модулями** (`engine/Sword.Engine.Ecs/AGENTS.md`,
  `engine/Sword.Engine.Render/AGENTS.md`, `game/modules/Sword.Game.Cutting/AGENTS.md`…): инварианты подсистемы,
  команды проверки, типичные ошибки — 10–30 строк; подробности — в md модуля.
- **`CLAUDE.md`** подключает `AGENTS.md` (`@AGENTS.md`). Если к тому времени Claude Code не читает `AGENTS.md` сам,
  рядом с каждым вложенным `AGENTS.md` — однострочный `CLAUDE.md` с той же ссылкой.
- **Повторяющиеся процедуры** — skills Claude Code (`.claude/skills/`) и рецепты в `docs/agent-playbook.md` для любых
  агентов: проверить фичу, найти расхождение, минимизировать ошибку, прогнать перебор производительности.
- **`.mcp.json`** — подключение MCP-сервера SWORD для Claude Code; строки подключения для Codex — в `docs/agent-playbook.md`.
- Машинный вывод у скриптов и exe: `verify.ps1 -Json`, бенч и сценарии — `--json`.

## 9. Игра

### Сборки

- **`Game.Contracts`** — всё, что видят модули: стабильные компоненты (`Transform`, `Health`, `CombatState`, `Dead`,
  `Severed`, `WeaponSlot`…), события (`StrikeContact`, `StrikeBlocked`, `Clash`, `Hit`, `SeverRequested`,
  `LimbDetached`), команды (`PlayerCommand`, `ArenaCommand`), намерение бойца (`FighterCommand`), идентификаторы (сегменты тела — сейчас константы `Fighter.Pelvis`,
  `Fighter.FArmL`…), метки систем ядра; раскладки GPU-данных тел (`GpuUnit`, `GpuSeg`) и ключи ресурсов графа —
  чистыми данными, без ссылок на Render. Без логики и без интерфейсов-стратегий.
- **`Sword.Game`** — симуляция: системы и правила. Модули его не видят, поэтому устройство арены им недоступно.
- **`Sword.Game.Client`** — ввод → команды, камера, Extract бойцов и тел, проходы сцены, HUD.
- **`Game.Data`** — игровые форматы (риг, оружие, кровь оружия, анатомия, `actions.json`).

### Системы (в порядке стадий)

Каждая реакция, которая должна произойти в том же тике, стоит в стадии позже своего производителя; задержки на тик
явно помечены `NextTickOk` (раздел 5). И то и другое проверяется при сборке мира.

| стадия | система | вид | откуда логика |
|---|---|---|---|
| Intent | `PlayerCommandSystem`, `EnemyAiSystem`, `BenchAutopilotSystem`, сценарии | непрерывные | `PlayerController`, `EnemyAi`, `BenchAutopilot`, `RagdollScene` (интерфейс `IFighterBrain` уходит) |
| Begin (с 6б; 4а–6а — Intent) | `ArenaCommandSystem` | реактивная: `Event<ArenaCommand>` — спаун и удаление врагов, сброс, меч игрока (`PlayerInventory`, `Set<WeaponSlot>`); Intent видит арену после неё | `SetEnemyCount`, `Reset`, `NextPlayerWeapon`, `EquipPlayerWeapon` (сейчас из `Program.cs`) |
| Gameplay | `DeathToRagdollSystem@Gameplay` | реактивная: `Added<Dead>` — смерти до физики (сценарии, команды); `NextTickOk<Added<Dead>>` для смертей из Resolve и Aftermath | `SettleDeaths()` в начале тика |
| Gameplay | `FighterSetupSystem` | реактивная: `Added<Fighter>` — поза, аниматор, первое оружие (сочленение — хуком `BodyRef`, 5а); боец создан сразу с полным набором компонентов | `Spawn`, `Build`, `PlaceBuilt`, `AttachRig` |
| Gameplay | `BladeSetupSystem` (6б; вместо задуманной `WeaponEquipSystem`) | реактивная: `Added<Fighter>` — клинок по позе постройки без прошлого; смену меча ловит постановка тика (клинок другого меча — без прошлого), окна ударов — одна таблица по мечу по умолчанию | `PlaceBuilt`, `EquipPlayerWeapon` |
| Gameplay | `RootSteerSystem` (этап 2), `CombatDecisionSystem`, `AnimatorInputSystem` (этап 2: вход слоя движения), слой действий аниматора | непрерывные (без `Dead`) | `KinematicSteer`, `PlayerAttackPicker`, `StrikeWindows`, `FighterAnimator` |
| Animation | слои позы (модуль Locomotion — `LegacyLocomotionSystem`), `AnimatorPoseSystem` (прямая кинематика), `AnimationTickSystem` (пул поз исполняет задания пачкой) | непрерывные | `KinematicBegin` (`anim.Tick`) |

| PrePhysics | `KinematicPlacementSystem`, `BladePlacementSystem` (6б: клинок тика и прошлый) | непрерывные | `PlaceBodies` (с клинком `anim.Blade`), `PrepareKinematicContacts` |
| Physics | Push/Pull физики | непрерывные | подшаги `DuelArena.Tick` |
| Combat | `StrikeDetectionSystem` | непрерывная → `StrikeContact` | `KinematicStrikes` |
| Resolve | `HitApplySystem` | реактивная: `Event<StrikeContact>` (+ журнал `StrikeBlocked` из Defense — с Guard, отложен: решение 16) → `Hit`, `Dead`, `SeverRequested` | `ApplyHits`, `ApplyHit` |
| React | `HitReactionSystem`, `ClashReactionSystem` (с Guard — отложен, решение 16) | реактивные: `Event<Hit>`; `Event<Clash>` | `ApplyReactions`, `KinematicReactions` |

| Aftermath | `BleedSystem` | непрерывная по `Bleeding` → `Dead` | `AfterTick` (кровопотеря) |
| Aftermath | `RespawnSystem`, `RebuildSystem` | непрерывные: мёртвые дольше 8 с; тела с нечисловыми координатами | `Spawn`, проверка `IsFinite` в `DuelArena.Tick` |

`DeathToRagdollSystem` зарегистрирована дважды (`@Gameplay` и `@Settle`), как `SettleDeaths` вызывается дважды за тик
в SWORD; она идемпотентна (берёт только бойцов с `Kinematic`), поэтому смерть, уже переведённая в конце прошлого тика,
в начале следующего пропускается.

В клиенте (`Sword.Game.Client`): камера (`RtsCamera`), Extract бойцов и тел (`SkinnedCharacters`, `ArenaExport`,
`GpuArena`; инстансы — по журналам `Added/Removed`), проходы сцены, HUD (`Hud`, `InventoryUi`). Уровень
(`ArenaLayout`, `ArenaWorld`, `Terrain`) — описание, из которого строятся `HeightField` и колонны.

**Цель боя** (пользователь, при разбивке этапа 6): максимально отзывчивый бой — игрок влияет на действия и движение
всегда (антипример — Dark Souls, где анимация отнимает управление). Ошибки SWORD исправляются, каждое отличие
записывается в md фичи; рывок (Пробел) — временное быстрое ускорение без последствий для дальнейшей скорости, во время
рывка — уклонение от ударов.

### Протокол боя без стратегий

Модуль влияет на исход не ответом ядру, а фактом в журнале. У каждого факта — идентификатор, по которому его
сопоставляют: `ContactId` и `RequestId` = (`TickId`, порядковый номер в детерминированном порядке).

```
Combat     StrikeDetection → StrikeContact { ContactId, Attacker, Victim, Part, Point, Dir, Blade, Speed, Kind }
Defense    Guard читает StrikeContact → StrikeBlocked { ContactId, Kind, StaminaCost }, Clash { ContactId, Point }
Resolve    HitApply применяет каждый StrikeContact, для которого нет StrikeBlocked → Hit, Dead, SeverRequested { RequestId, … }
Dismember  Cutting читает SeverRequested → при успехе LimbDetached { RequestId, Victim, Segment, Part }
React      реакции на Hit и Clash; ядро реагирует на LimbDetached: маска Severed, кровотечение
Aftermath  кровопотеря → Dead
Settle     Dead → рэгдолл; Cutting «усаживает» свежие отрубы; статистика
```

Без Guard не появляется `StrikeBlocked` — удар проходит. Без Cutting заявка на отруб остаётся без ответа — конечность
на месте. Это не запасной алгоритм, а естественная обработка фактов: ядро не ждёт ни ответа, ни модуля. Guard и
Cutting отложены (решения 16, 17): стадии Defense и Dismember пока пусты — удары проходят всегда, заявки на отруб
остаются без ответа.

### Контракт расчленения

Пространство `Sword.Game.Cutting` в SWORD (`CutMesh`, `CutSurface`, `DerivedSkinMesh*`, `LimbDetachment`,
`LimbDetachCaptured`, `SkinCut*`) используют ядро арены, кровь и внутренности — это **контракт**, а не часть модуля.
В `Game.Contracts` уходят **только данные и события**: заявка на отруб, событие отделения, компоненты отрубленной
части, описание поверхности среза. Логика — в модуле: отделение и капсулы (`FighterCutter`, `MeshCutter`,
`JointDetachment`) — в `Sword.Game.Cutting`, разрез мешей (`SkinMeshCutter`, `SkinCutMeshes`) — в
`Sword.Game.Cutting.Client`. Точное деление — при переносе модуля (этап 11 — отложен, решение 17).

### Что не переносится (живой рэгдолл)

- `Fighter.Locomotion` (шаги живого: `UpdateFeet`, `UpdateCapture`, `BuildSupport`, выпуклая оболочка опоры);
- мышечный привод живого в `Fighter.Muscles` (`DrivePelvis`, `DampMuscles`, коэффициенты `K*`);
- цели руки и клинка (`HandGoal`, `BladeGoal`, `BladeAngles`) и живая часть `Fighter.BeginTick`;
- ручки живого рэгдолла (`SWORD_MUSCLE`, `SWORD_KARM`, `SWORD_KLEG`, `SWORD_GAIN`, `SWORD_CP_*`…); `tools/ue`.

**Осторожно со смешанным кодом.** `Fighter.BeginTick` сейчас идёт для всех не-кинематических, то есть и для трупов,
и зовёт `UpdateCapture`/`UpdateFeet`. При переносе рэгдолла из смешанного кода берётся только то, что влияет на трупы, —
это часть рэгдолла трупа, а не живого. Приёмка — сцены рэгдолла против чисел SWORD (этап 7).

## 10. Модули игры

Модуль либо есть, либо нет (решение 9). Без модуля его функции в игре нет, и это видно сразу, а не скрыто подменой.

| модуль | сборки | что внутри | без модуля |
|---|---|---|---|
| Guard (отложен — решение 16) | `Sword.Game.Guard` (+ `.Client` — HUD выносливости, когда понадобится) | `AutoGuard`, `BladeGuard`, `BladeClash`, `Stamina` + блок врагов по конусу (`FacingGuard`, сейчас в ядре) | блока нет ни у кого: удары проходят всегда |

Blood и Innards — представление: на игру не влияют, поэтому целиком клиентские. Если при переносе найдётся влияние
на симуляцию, оно явно выносится в сборку симуляции модуля.

**Что сейчас называется запасным путём, а на деле им не является.** Из четырёх «запасных путей» SWORD чистый — только
один (стопы без постановки: это просто отсутствие модуля, кода у него нет). Три других работают **и при включённом
модуле**:
- `LegacyLocomotion` — локомоция всех врагов (MM — только у игрока);
- `FacingGuard` — блок врагов (`BladeGuard` отдаёт ему всех, кроме игрока);
- `JointDetachment` — хвост цепочки `ChainedDetachment`, когда разрез отказался.

Поэтому они не удаляются, а **переезжают в свои модули** как вторая реализация внутри модуля. Две реализации в одном
модуле законны, если обе работают при полном наборе модулей: MM для игрока и клипы для врагов — это уровни
детализации (hero / near), а не запасной путь.

**Правило:** код, который исполняется только тогда, когда какого-то модуля нет, — запрещён.

**Следствие для проверок:** «каждый модуль выключен» доказывает устойчивость (игра стартует, не падает, остальные
модули работают), но не играбельность: без Locomotion бойцы ходят в позе привязки. Игровые сценарии и эталоны — с полным
набором модулей, доступных на текущем этапе.

Каждый модуль переносит свой md-документ, шейдеры (в своей папке, в выходе — `Shaders/<сборка>/…`) и тесты.

## 11. Пекарня

- `Sword.Bake`, `Sword.Bake.Cli` — переезжают как есть.
- `Sword.Bake.Sword` делится на два плагина:
  - `Sword.Bake.Engine` — текстуры (`Texture/*`, `TextureArrayProcessor`), шрифты (`FontVectorProcessor`, `FontPreview`
    + `UiFontBaker` из `Engine.Ui`), импорт мешей, скелетов и клипов (`GltfMesh`, `RawAnim`, `AnimImport`, `SkinBake`,
    `MeshDecimate`, `SkeletonProcessor`, `AnimPackProcessor`, `ClipSource`, `SpineChain`, `UeRig`, `UeSpace`, `PoseReport`);
  - `Sword.Bake.Game` — оружие (`WeaponBake`, `WeaponStaticProcessor`), кровь оружия (`WeaponBloodBake`), анатомия
    (`AnatomyBake`, `AnatomyMeshProcessor`), `FingerTransfer`, `Inspect` — каждый файл проверяется по зависимостям.
- `Sword.Bake.Studio` — на новом движке (Client, Render, Ui); предпросмотр по-прежнему через `IAssetPreview`.

**Приёмка — сверка пересобранного пака с эталонным паком SWORD (этап 0):**
- тот же список контентных файлов;
- те же размеры и хеши содержимого — они уже есть в оглавлении пака (`PakContentEntry`: путь, размер, хеш);
- `.bake/build.json` — семантически: те же ассеты, обработчики, их версии и хеши параметров. Время (`BuiltUtc`,
  `BakedUtc`) и отпечатки кода (`Builder.Fingerprint` включает имя сборки и MVID — после деления `Bake.Sword` на две
  сборки они другие по определению) не сравниваются.

Побайтное совпадение пака целиком невозможно по устройству и не требуется. Сверка оформляется командой пекарни
(`bake diff`), чтобы ею же проверять будущие изменения обработчиков.

## 12. Приёмка фич и тесты

### Как принимается фича

С этапа 7 (решение 14) — без сверки со SWORD и без переноса тестов SWORD: в п. 1 — откуда идея и какие решения свои, в п. 3 —
свои тесты свойств и метрики с порогами по своим замерам; упоминания SWORD ниже относятся к этапам 0–6.

1. **Перенос.** В md-документе фичи или модуля — откуда логика (файлы SWORD), что изменилось при переписывании
   и какие места стали реактивными.
2. **Агентский вид и манифест.** Состояние фичи видно через `IStateContributor.Describe`; её приёмка описана
   `FeatureManifest` (`feature.json`: сценарии, инварианты, метрики с допусками, виды, бюджеты,
   чек-лист для пользователя); чек-лист раздела 8 пройден, его итог записан в md фичи. Без этого автоматический
   контроль невозможен, и фича не принимается.
3. **Автоматически (Claude, через агентский доступ):** сборка; архитектурные тесты; перенесённые тесты SWORD **без
   изменения ожиданий** — кроме намеренно изменённой семантики (записывается в md фичи и в коммите; пример — тест
   цепочки `JointDetachment`, переписанный под события); новые тесты; **`feature.verify(id)`** — сценарии в `Headless`,
   инварианты, сверка метрик с SWORD там, где они сравнимы, пакеты наблюдения нужных ракурсов, бюджеты
   производительности. Перед каждой сверкой проверяется SHA-256 эталонного пака (этап 0). Вердикт опирается на
   инварианты и эталоны, а не на мнение агента; ослабить ожидания манифеста можно только явной правкой с сообщением
   пользователю.
4. **В игре (пользователь):** список «что проверить» из `HumanChecklist` манифеста — 3–7 пунктов: клавиши, что должно
   происходить, на что смотреть.
5. **Подтверждение** → фиксируется эталон SWORD2 (реплей с хешами состояния и снимок) — для регрессий следующих фич.
   Следующая фича — только после подтверждения.

Ход точки (с этапа 6): исполнитель проверяет свою работу точечно (сборка, тесты своих проектов, `verify.ps1 -Only`) и
полный `verify.ps1` (Debug) запускает один раз в конце; замеры Release и бюджеты — в точке приёмки этапа; проверяющий —
полный Debug один раз, точечные сценарии, мелкие дефекты правит сам. С этапа 7 — волнами параллельно: оркестратор (основная сессия)
запускает точки в своих рабочих деревьях (`.claude/worktrees/`, жёсткая ссылка на пак в корне дерева), у каждой — владение файлами;
контракт вперёд, если точки пишут один проект; одновременно не больше 3–4 агентов, без искусственной нагрузки CPU; эталоны SWORD2
перезаписывает одна ветка за раз с доказательством; слияние — оркестратор (squash, коммит с именем точки, строка в истории этапа).
Малые точки (только тексты или S без изменения поведения) — без отдельного проверяющего; замер времени — один прогон, сомнительное —
вопрос пользователю (корневой `AGENTS.md`). Подробно — [docs/history/stage-7.md](docs/history/stage-7.md), «Решено при разбивке этапа 7».

## 14. Риски

| риск | мера |
|---|---|
| ошибка в новой логике проходит незаметно (с этапа 7 внешнего образца нет) | свои тесты свойств, инварианты (в том числе внутри шага физики), сценарии с порогами по своим замерам, проверка в игре; в md фичи — откуда идея и почему так |
| эталон SWORD незаметно меняется (пак перепекли) | `reference.json`, неизменяемая копия пака, SHA-256 перед каждой сверкой |
| смешанный код живого рэгдолла влияет на трупы | из `Fighter.*` берётся только то, что относится к трупу (разбор — рабочий план этапа 7); инварианты энергии и суставов трупа |
| потребитель срабатывания оказался в стадии производителя (реакция на тик позже) | объявления производителей и проверка при сборке мира; граничные тесты журналов |
| реплей расходится из-за изменений мимо команд | всё, что меняет симуляцию на ходу, — команда с `TickId`; `Headless` воспроизводит запись `Game.App` с теми же хешами |
| прототип затянется | контрольные точки 1а–1д, каждая запускается; что не входит — записано |
| ECS превратится в самоцель | v0 — только то, что нужно прототипу; остальное — по потребителю |
| реактивные системы пропустят или повторят срабатывание | журналы с курсорами: каждый потребитель видит запись ровно один раз; тесты на границы тиков и деактивацию |
| недетерминизм (порядок, потоки, ГСЧ) | барьеры со стабильным слиянием, явные `After/Before`, счётчиковый ГСЧ, хеш состояния в реплеях |
| симуляция незаметно начнёт зависеть от клиента | разделение по сборкам, свойство стороны в MSBuild, архитектурный тест замыкания `Headless` |
| косвенность хэндлов съест производительность | микробенчмарки подсистем, бенч кадра |
| D3D12 протечёт в модули | `Vortice.*` только у Rhi и Render + список исключений, который только сокращается |
| переходные пулы управляемых объектов останутся навсегда | у каждого — план растворения в md фичи |
| хобби-темп: интерес пропадёт на длинном этапе | каждый этап — видимый результат в игре |
| агентский доступ изменит симуляцию мимо команд или попадёт в сборку игры | мутации — только командами с `TickId` и в реплей; ядро и модули об агенте не знают; сборка `-p:WithoutAgent=true` проверяется |
| ответы агенту переполнят контекст модели | сводки, пагинация, лимиты, крупные данные — файлами в `artifacts/agent/` |
| агент гоняется с симуляцией или рендером | обработчик MCP мир не читает; запросы — через очередь в точке обслуживания, снимки — на границе кадра |
| диагностика держит память симуляции | у журналов нет внешних курсоров: клиент и агент получают копии в шаге экспорта; история — в ограниченном кольце |
| агентский слой разрастётся: много узких команд, дорогая диагностика | композиционные инструменты с условиями и проекциями; причинность и тяжёлые инварианты выключены по умолчанию и не меняют хеш; `Sword.Agent.Evals` меряет, какие инструменты полезны |
| приёмка сведётся к мнению агента | вердикт `feature.verify` — по инвариантам и эталонам; ослабить манифест молча нельзя; последнее слово — подтверждение пользователя в игре |
| с параллельностью поменяется семантика создания сущностей | черновики `EntityDraft` с первого дня; тест одинаковых индексов при любом числе потоков |
