## 2. Принципы

1. **Зависимости только вниз.** Движок не знает игру и пекарню. Игра не знает пекарню. Модули видят только контракты
   игры (`Game.Contracts`), но не её устройство и не друг друга.
2. **Подсистема владеет своими данными — и только ими.** Физика владеет телом, но не «обломком»; ECS хранит хэндлы.
   Синхронизация — явными шагами Push/Pull в известных стадиях.
3. **Явные стадии, барьеры и журналы.** Порядок систем задают объявленные зависимости (`After/Before`), а не порядок
   строк; события и срабатывания видны по чётким правилам (раздел 5).
4. **Модуль либо есть, либо нет.** Ядро публикует факты и заявки (события, компоненты), модули действуют по ним;
   ядро никогда не спрашивает модуль и не ждёт ответа. То, без чего игра не имеет смысла (ввод, рендер, проходы
   клинка, урон, смерть и рэгдолл), — ядро в одной реализации, не модуль и не выключается.
5. **Реагировать на то, что случилось, а не опрашивать.** Редкие события — реактивные системы; каждый тик работают
   только непрерывные процессы.
6. **Симуляция авторитетна и детерминирована.** Представление (рендер, GPU-симуляции, UI) только читает её; обратная
   связь с GPU не влияет на игровую логику; случайность не зависит от порядка обхода и потоков.
7. **Устойчивый кадр без аллокаций.** Компоненты — `unmanaged struct`; пулы; цель — 0 выделенных байтов на тик
   после прогрева.
8. **Одна правда для CPU и GPU.** Общие структуры и константы — из одного источника (генерация или проверка при старте).
9. **Не фиксировать до первого потребителя.** Размеры, форматы и механизмы — гипотезы, пока нет потребителя и замера.
10. **Каждый шаг — работающая программа и проверка.** Никакого «большого взрыва».
11. **Наблюдаемо для машины.** Всё, что движок сообщает, — структурированные данные со стабильными именами
    (компоненты, системы, стадии, события, модули, ручки, команды); отчёты, метрики и логи — в JSON рядом
    с человекочитаемым текстом; ошибки — со стабильными кодами. Что нельзя наблюдать, нельзя проверить.
12. **Соглашения репозитория** (переносятся в `AGENTS.md` SWORD2): CRLF во всех текстовых файлах; каждая механика —
    модуль с md-документом (назначение, настройки, зависимости, ограничения, известные ошибки).

## 5. Sword.Engine.Ecs

Свой минимальный архетипный ECS, API по образцу Arch. Размеры и механизмы ниже — стартовые гипотезы:
фиксируются замером, а не заранее.

### Модель

| понятие | устройство |
|---|---|
| сущность | `readonly record struct Entity(int Index, int Generation)`; удаление увеличивает поколение — висячий хэндл распознаётся |
| компонент | `unmanaged struct`; ссылки запрещены ограничением `where T : unmanaged` |
| тег | тип без полей; колонку не занимает (пустой `struct` в C# весит 1 байт — тег распознаётся при регистрации по отсутствию полей) |
| реактивный компонент | помечен `[Reactive]`; меняется только командой `Set<T>` — так каждое изменение попадает в журнал `Changed<T>`. Прямая запись `Write<T>()` в него — исключение в Debug. Частые данные (`Transform`) реактивными не делаются |
| регистрация | явная, при сборке мира, в детерминированном порядке (по полному имени типа). ID не зависят от порядка первого обращения к `ComponentType<T>`; незарегистрированный компонент — ошибка |
| стабильные имена | ID компонентов нигде не сохраняются: сейвы, реплеи и ассеты ссылаются на стабильные имена |
| архетип, чанк | набор компонентов → чанки SoA (колонка на компонент); строки плотные, удаление — перенос последней строки. Размер чанка — настройка (старт 16 КБ), не контракт |
| версии изменений | `Write<T>()` помечает версию всего столбца в чанке, даже если данные не менялись: грубо, но надёжно — хватает для Push «только изменённое» |
| ресурсы | синглтоны мира: `World.Resource<T>()`; замена — `SetResource`, попадает в журнал `ResourceChanged<T>` |
| хуки | `OnAdd<T>/OnRemove<T>` — только время жизни ресурсов подсистем (выделить и освободить хэндл тела, позы); вызываются на барьере, структуру мира не меняют, повторный вход запрещён |

### Системы: непрерывные и реактивные

| вид | когда исполняется | что получает | для чего |
|---|---|---|---|
| непрерывная | каждый тик в своей стадии | запрос по компонентам | то, что идёт всегда: движение, анимация, физика, проходы клинков, ИИ |
| реактивная | в своей стадии, только если с её прошлого запуска были срабатывания | только затронутые сущности или события | то, что случается: появление бойца, смерть, смена оружия, попадание, отруб, смена настроек |

| срабатывание | когда появляется |
|---|---|
| `Added<T>` | компонент добавлен (командой, на барьере) |
| `Removed<T>` | компонент снят или сущность удалена; запись хранит последнее значение `T` |
| `Changed<T>` | существующий реактивный компонент заменён командой `Set<T>`; при отключённых проверках ошибочный `Add<T>` уже существующего компонента также даёт `Changed<T>` |
| `Event<E>` | записано событие `E` |
| `ResourceChanged<T>` | ресурс заменён (ручки, настройки, уровень) |

```csharp
// Регистрируется в стадии Settle: смерти из Resolve и Aftermath к ней уже прошли барьер.
sealed class DeathToRagdollSystem : IReactiveSystem<Added<Dead>>
{
    public void Setup(SystemSetup s)
    {
        s.Label(GameLabels.DeathToRagdoll);
        s.Query().With<Kinematic>();                 // идемпотентна: уже переведённых не трогает
        s.Removes<Kinematic>();
        s.Writes<BodyMode>();
    }

    public void React(in SystemContext ctx, ReadOnlySpan<Added<Dead>> died)   // только умершие с прошлого запуска
    {
        foreach (var e in died) { /* перевести тело в рэгдолл по позе прошлого тика */ }
    }
}
```

- Реактивная система — обычная система: стадия, метка, `After/Before`, объявленный доступ. В v0 у неё одно
  срабатывание; нужно два — две системы.
- Непрерывная система тоже может читать журнал (`ctx.Journal<Event<Hit>>()`) своим курсором. Дополнительный журнал
  реактивной системы (`HitApplySystem`: `StrikeBlocked` при срабатывании по `StrikeContact`) — контекст срабатывания:
  в тике срабатывания видны его записи с её прошлого места в тике, записи тиков без срабатывания пропускаются.
- Реактивная система без срабатываний стоит одну проверку длины журнала.
- Журнал заводится только для срабатываний, на которые кто-то подписан.
- Одну систему можно зарегистрировать в двух стадиях (у каждой регистрации свой курсор) — тогда она обязана быть
  идемпотентной. Так `DeathToRagdoll` повторяет два вызова `SettleDeaths` за тик в SWORD (раздел 9).
- **Идентичность регистрации** — `(Stage, SystemLabel, RegistrationId)`. Метка уникальна внутри стадии; повторная
  регистрация того же типа получает свой `RegistrationId` (`DeathToRagdoll@Gameplay`, `DeathToRagdoll@Settle`).
  По ней ведутся курсоры журналов, граф `After/Before`, профайлер, токены модулей и ответы инструментов.

### Порядок стадий производителя и потребителя

`After`/`Before` задают порядок систем внутри стадии, но **барьера между ними не вставляют**. Поэтому правило:

```
стадия(производитель) <  стадия(потребитель)  → реакция в том же тике
стадия(производитель) >= стадия(потребитель)  → реакция в следующем тике — ошибка сборки мира,
                                                 если потребитель не объявил NextTickOk<T>()
```

Производители объявляют, что порождают (`Emits<E>`, `Adds<T>`, `Removes<T>`, `Sets<T>`, `SetsResource<T>`;
в Debug необъявленное — исключение), потребители — срабатывания; **при сборке мира планировщик проверяет каждую пару
по правилу выше**. Пример: ранняя регистрация `DeathToRagdoll@Gameplay` стоит раньше производителей `Dead` из
Resolve и Aftermath и объявляет `NextTickOk<Added<Dead>>()` — задержки там нет по смыслу, эти смерти в том же тике
уже обработала `DeathToRagdoll@Settle`, которой разрешение не нужно.

Сущность создаётся командой **сразу с окончательным набором компонентов**: реактивная настройка по `Added<Fighter>`
не добавляет компоненты, на которые в той же стадии кто-то реагирует. Общая логика двух реакций (первое оружие при
появлении бойца и смена оружия потом) — одна функция, которую зовут обе системы, а не цепочка срабатываний.

### Создание сущностей: черновики

API создания **одинаков при последовательном и параллельном исполнении** — системам v0 не придётся меняться:

```csharp
EntityDraft piece = ctx.Commands.Create();                  // черновик: живой сущности ещё нет
ctx.Commands.Add(piece, new PartOf { Owner = victim });
ctx.Commands.Add(piece, transform);
ctx.Commands.Emit(new LimbDetached { Part = piece.Ref, … });  // поле Part имеет тип Entity; piece.Ref — отложенное значение
```

- **Тип поля не меняется — меняется значение.** В компонентах и событиях ссылки на сущности — всегда поля типа
  `Entity`. `EntityDraft.Ref` даёт отложенное значение `Entity`: особая кодировка (отрицательный индекс — номер черновика,
  поколение — номер буфера), которую нельзя спутать с живой сущностью.
- **Разрешитель** генерируется при регистрации типа компонента или события: он знает все поля `Entity`, включая вложенные
  структуры (иная форма хранения ссылок — ошибка регистрации). На барьере он заменяет отложенные значения настоящими
  `Entity` **до** того, как компонент или событие станут видны. Применяется к `Add<T>`, `Set<T>` и `Emit<T>`.
- Черновик живёт до ближайшего барьера. Команды и события **своего** буфера могут на него ссылаться; живую сущность
  до барьера получить нельзя.
- В Debug — исключение: черновик чужого `CommandBuffer`; обращение к `World` с неразрешённым отложенным значением;
  отложенное значение, записанное в компонент мимо команд.
- Индексы сущностей назначаются при проигрывании в детерминированном порядке буферов — от числа потоков не зависят.
- Вне исполнения систем (начальная сборка мира, тесты) — `World.CreateImmediate()`.

### Стадии, барьеры, журналы

```
стадия   системы по порядку; каждая пишет события и команды в свои локальные буферы
барьер   1) проигрывание CommandBuffer: порядок системы в стадии → порядок задачи → порядок записи;
            черновики → Entity, разрешитель заменяет отложенные значения в Add/Set; записи Added/Removed/Changed
            в журналы; хуки
         2) слияние событий в том же порядке; разрешитель заменяет отложенные значения в событиях из Emit
         3) следующая стадия видит структурные изменения и новые записи журналов
```

- События и срабатывания — журналы. У каждого потребителя (системы, клиента) свой курсор: **каждую запись каждый
  потребитель видит ровно один раз** — записи стадий раньше него в этом тике и позже него в прошлом тике. Системам
  той же стадии запись видна со следующего тика.
- Запись живёт один полный оборот тика: к следующему барьеру той же стадии её прочли все потребители. Что нужно
  дольше — копируется в своё состояние.
- Деактивированный потребитель журнал не держит; при повторной активации его курсор ставится на конец журнала —
  прошлое не проигрывается.
- Порядок записей стабилен и не зависит от числа потоков.
- `CommandBuffer` проигрывается **на каждом барьере**, а не в конце тика.
- В конце каждого тика журналы читает **шаг экспорта Runtime** — служебная стадия `runtime.export` после барьера
  последней стадии игры (End), поэтому в экспорт тика попадают записи всех его стадий, включая End. Он копирует
  записи тика в очередь кадра клиента с номером тика (`TickId` — кадр из трёх тиков получает события всех трёх, кадр
  без тиков — ничего). Внешних курсоров у журналов нет: клиент получает копии и на освобождение памяти симуляции не
  влияет. Команды тика становятся событиями в служебной
  стадии `runtime.commands` до первой стадии игры — их видят все стадии игры, включая Begin, в том же тике.
- Сущность, созданная командой, становится живой на барьере (раздел «Создание сущностей: черновики»).

**Нормализация на барьере.** События (`Event<E>`) не склеиваются: сколько записали, столько и прочтут. Срабатывания
компонентов сводятся по паре (сущность, `T`) — сравнивается состояние до барьера и после него:

| до барьера → после | запись в журнале |
|---|---|
| нет `T` → есть `T` | один `Added<T>` — сколько бы `Set<T>` ни было после добавления |
| есть `T` → нет `T` | один `Removed<T>` со значением на момент снятия |
| есть → есть, значение заменено (один или несколько `Set<T>`; при отключённых проверках — и ошибочный `Add<T>` существующего) | один `Changed<T>` с итоговым значением |
| есть → есть, снят и добавлен заново | `Removed<T>` (старое значение), затем `Added<T>` |
| нет → нет (добавлен и снят на одном барьере) | ничего: для потребителей компонента не было; хуки при этом отработали оба |
| сущность удалена | `Removed<T>` по каждому компоненту, на который есть подписка, со значениями на момент удаления |
| сущность создана и удалена на одном барьере | ничего |

**Граничные тесты журналов** (обязательны для v0):
- производитель в той же или более поздней стадии — запись видна в следующем тике; без `NextTickOk` — ошибка
  сборки мира;
- производитель в предыдущей стадии — запись видна в текущем тике;
- черновик: отложенные значения в `Add`, `Set` и `Emit` разрешаются на барьере, включая вложенные структуры;
  черновик чужого буфера и обращение к миру с неразрешённым значением — исключение в Debug; одинаковые индексы при
  любом числе потоков;
- `Added<T>` и `Removed<T>` на одном барьере; снят и добавлен заново;
- два `Set<T>` до одного барьера — один `Changed<T>` с итоговым значением;
- удаление сущности — последнее значение `T` в `Removed<T>`;
- `deactivate` → `activate`: старые записи не воспроизводятся;
- одна система в двух стадиях: каждая регистрация видит запись один раз, действие выполняется один раз;
- экспорт тика в очередь кадра клиента при кадрах с 0 и 3 тиками.

### Порядок и планировщик

- Порядок внутри стадии — **явные `After`/`Before`** по меткам систем. Порядок регистрации — только правило развязки
  для независимых систем, не контракт. Цикл зависимостей — ошибка при сборке мира.
- Метки систем ядра игры (`GameLabels.StrikeDetection` и т. п.) лежат в `Game.Contracts`: модуль встаёт до или после
  системы ядра, не видя её типа.
- Объявления чтения/записи — не про порядок, а про параллельность и проверку доступа (в Debug обращение
  к необъявленному — исключение).
- Параллельность внутри системы — `ForEachChunkParallel` поверх `Core.Jobs`; между системами — группы без конфликтов.
  Включается флагом после замера, без правки систем.

### Объём

| версия | что входит |
|---|---|
| v0 (прототип) | сущности, регистрация, архетипы и чанки, запросы `Read/Write/With/Without`, `CommandBuffer`, ресурсы, стадии и барьеры, `After/Before`, **журналы и реактивные системы** (`Added`, `Removed`, `Changed` через `Set` — при отключённых проверках и через ошибочный `Add` существующего, поэтому планировщик считает `Add` возможным производителем `Changed`, `Event`, `ResourceChanged`) с нормализацией на барьере, черновики сущностей, объявления производителей и проверка порядка стадий, идентичность регистрации, граничные тесты журналов; исполнение последовательное |
| v1 (по мере надобности) | хуки времени жизни ресурсов (к физике — сделаны на 5а), проверка доступа в Debug, версии изменений для Push, параллельные чанки и группы систем |
| нет | отношения, префабы, сериализация мира, управляемые компоненты, несколько миров, отслеживание изменений у всех компонентов подряд — пока нет потребителя |

### Цели производительности (BenchmarkDotNet)

- проход `Read` + `Write` по чанкам медленнее сырого цикла по `Span<T>` той же раскладки не более чем на 20–30 %
  на той же машине;
- создание, удаление и перенос между архетипами через `CommandBuffer`, запись и чтение журналов — без аллокаций
  в устойчивом режиме.

### Переходный паттерн

Где логику SWORD сразу разложить по компонентам рискованно, допустим **управляемый объект в пуле + хэндл
в компоненте** (`AnimatorRef { int Slot }` → аниматор бойца). Это инструмент, а не норма: у каждого такого пула
в md-документе фичи записан план растворения.

## 6. Подсистемы

Общий договор подсистемы:
- владеет своими данными — и только ими — в своей раскладке; наружу — хэндлы (индекс + поколение);
- тикается целиком, пачкой, с явными входами и выходами;
- тестируется и замеряется без мира ECS и без игры;
- получает настройки готовыми объектами при композиции — конфиг не читает;
- связь с ECS — только системами Push (ECS → подсистема) и Pull (подсистема → ECS + события) в своей стадии;
- отдаёт своё состояние как участник `IStateContributor` и приносит свои инварианты;
- API подсистемы, которую будут оптимизировать (Physics, Animation), допускает две реализации в одном процессе —
  для дифференциального прогона эталона и кандидата.

```
Entity ──┬─ Transform, PrevTransform          (ECS)
         ├─ Health, CombatState, FighterCommand
         ├─ BodyRef      → Physics.ArticulationHandle   (данные в физике; хуки держат время жизни)
         └─ PoseRef      → Animation.PoseSlot           (данные в пуле поз)
RenderWorld (клиент): инстансы отрисовки по Entity — заводятся и освобождаются по журналам Added/Removed
```

Системы Push/Pull в v1 живут в игре: она определяет компоненты. Появится второй потребитель — вынесем
в интеграционные сборки движка.

### Physics (`Sword.Engine.Physics`)

- **Владеет:** телами (капсулы), сочленениями (рэгдолл: суставы, пределы), контактами. Земля — `HeightField` из Geometry.
- **API:** `CreateBody`, `CreateArticulation` (набор тел и суставов), `SetKinematicTarget` (поза из анимации),
  `SetMode(Kinematic | Simulated)`, `ApplyImpulse`, `Step(dt, substeps)`, запросы (`Raycast`, `SweepCapsule`,
  `Overlap`), поток событий контактов.
- **Откуда логика:** `Sword.Physics` + физическое из игры: `DuelArena` (`SolveContacts`, `Collide`, `GroundEnd`,
  `PushOut`, `PrevOverlap`, `SolveContactVelocities`, трение, подшаги), `DuelArena.ContactVelocity`,
  `KinematicContacts`, `Fighter.Joints` и суставная часть `Fighter.Muscles` для трупа (`SolveConstraints`,
  `RelaxJointVelocities`, `PostVelocity`), `Body`, `RagTrace` (как диагностика физики).
- **Не физика:** клинок (это капсула, которую игра проводит `SweepCapsule`); что такое обломок, сколько ему жить
  и сколько их может быть (`Debris`, `DebrisLife`, `MaxDebris`) — политика игры: сущность с `BodyRef` и `Lifetime`;
  что считать ударом, пороги отруба, реакция на попадание — тоже игра.
- **Раскладка:** сначала логика SWORD за API хэндлов (сверка сценами рэгдолла); SoA и острова — отдельным шагом
  с микробенчмарком и дифференциальным прогоном против первой реализации, которая остаётся эталоном в тестах.
- **Инварианты:** конечность координат, живые хэндлы, энергия рэгдолла не растёт скачком за подшаг — последнее
  проверяется внутри шага в диагностическом режиме.

### Animation (`Sword.Engine.Animation`)

- **Владеет:** скелетами, библиотекой клипов, **пулом поз** (батчи по скелету), состояниями смешивания и MM.
- **API:** `AllocPose(skeleton)`, запросы проигрывания и смешивания, `Tick(jobs)` — сэмплинг всех активных поз пачкой
  (параллельно по батчам, SIMD); выход — позы в модельном пространстве, корневое движение, контакты стоп.
- **Откуда логика:** `Sword.Anim` (`AnimLibrary`, `SkeletalClips`, `AnimMath`, `LegIk`, `FootLock`, `FootPlacement`,
  `FootContacts`, `ContactDetector`, `Loco/*` — движковый Motion Matching). `IGround` → `HeightField`. `SwordBody` →
  игра. `LocoAudit` → `Game.DevTools`.
- **Остаётся в игре:** `FighterAnimator` (машина состояний боя), выбор ударов, окна ударов — это правила игры.
- **Motion Matching (этап 8):** механизм — в подсистеме, без знания игры и контента (`Pose2`, кинематика клипов, контакты стоп,
  схема признаков — вход, база с графом переходов, поиск, запрос, модель предсказания траектории, история корня, проигрыватели за
  хэндлами; переход — инерциализация заданием пула); политика контента (имена клипов GASP, отбор, правило продолжения, веса) — в
  модуле Locomotion. База строится из клипов при загрузке, один раз на процесс, неизменяема; пак и пекарня её не хранят.
- **Наблюдателям — только вид:** данные подсистем вне ECS (пул поз) видны только видом для чтения (`IReadView` в ECS,
  `WorldReader.View`; `IAnimationView` в `Game.Contracts` — не стратегия, ядро его не спрашивает); у каждой симуляции
  свой пул поз, задания он исполняет пачкой в Animation; общие ассеты анимации (`Skeleton`, `ClipLibrary`, `ActionTable`)
  неизменяемы — наружу только `ReadOnlySpan`; ассеты бойца грузит exe (`CharacterAssets`) и отдаёт в
  `Sword.Game.Bootstrap` готовыми — Bootstrap контент не видит (редакции Р10–Р11).

### Geometry (`Sword.Engine.Geometry`)

- Примитивы и пересечения (отрезок–отрезок из `Xpbd.SegSeg` и подобное).
- `HeightField` — **одна правда о рельефе**: игра строит поле высот из описания уровня; физика и IK читают его на CPU,
  шейдеры — те же узлы структурированным буфером. Дублирование `Terrain.cs` / `sim_common.hlsli` исчезает. Поле линейно
  между узлами: вертикальные уступы (подступенки пирамиды) физика получает явными примитивами рядом с полем, а не
  из него. **Уточнено на этапе 7:** симуляция (постановка живых с этапа 1, физика трупов с этапа 7) читает аналитическую
  функцию рельефа игры, физика — через свой интерфейс земли `IGround` (реализует игра: гладкий рельеф и ярусы пирамиды
  точными ящиками); `HeightField` — рендеру.
- Пространственные структуры (хэш-сетка, позже BVH) — общий тип, но **у каждого владельца свой экземпляр** со своим
  размером ячейки: широкая фаза физики, ИИ, проходы клинков.

### Render (`Sword.Engine.Render`)

- **Рендер-граф v0:** проходы объявляют читаемые и записываемые ресурсы (импортированные или временные); граф ставит
  барьеры сам и выделяет временные цели из пула. **Одна graphics-очередь**: `PassKind.Compute` — dispatch на ней же.
  Ресурсы — текстуры и структурированные буферы; буферы, чьё содержимое переживает кадр (состояние GPU-симуляций), —
  хранилища `GpuStorage`, импортируемые в кадр. Цели создаются с оптимальным значением очистки и чистятся только им.
  Проверка — GPU-тесты графа на настоящем устройстве с GPU-валидацией (точка 1б).
  Порядок — по фазам, внутри фазы — порядок регистрации (без отсечения). Отдельной compute-очереди, межочередных fence, async
  compute и алиасинга памяти нет: GPU-симуляция огня идёт на той же очереди.
- **Фазы кадра:** `Simulation` (compute) → `Opaque` → `Composite` → `Transparent` → `Post` → `Ui` → `Debug` (`FramePhase`; без фазы —
  Opaque). Заменяют `ISceneOpaque`/`ISceneComposite` и слоты 10–12: у каждого прохода свои константы.
- **HDR и post** (этап Р): сцена пишет линейный цвет в `SceneColor` (RGBA16F); до `Post` задний буфер не пишет никто. В `Post` рендер
  добавляет bloom UE («сумма гауссиан», интенсивность 10, порог 1) и последним — тонмап: (сцена + bloom) × экспозиция 0.99 → Filmic UE
  (Slope 0.88, Toe 0.55, Shoulder 0.26) → sRGB. Экспозиция фиксированная.
- **Точечный свет:** список источников и light functions на кадр (`Renderer.Lights`; источники клиентских модулей — до проходов игры),
  до 64 видимых в буфер кадра; затухание и диффуз UE (`PointLightsDiffuse`), без specular и теней. Light function — сумма двух текстур
  шума со сдвигами по времени в осях LF (`LightFunction.Rotation`), CPU-эталон — `PointLightMath.LightFunctionSum` по `TextureTexels`;
  `PointLight.VolumetricScattering` — множитель света для объёмов (дым), в буфер кадра не пишется.
- **Прозрачное:** фаза `Transparent` по HDR-сцене с премультиплицированной альфой и чтением глубины (мягкий край); общий слой ½ разрешения
  с апсемплом по глубине (`RenderFrame.HalfRes`, `HalfResTransparency`) — в нём дым огня.
- **Текстуры пака:** `Renderer.LoadTexture` — `.swtex` как есть (R8, RG8, RGBA8, BC1/4/5/7, sRGB) в `Texture2DArray` bindless.
  Подробно — `engine/Sword.Engine.Render/README.md`.
- **GPU-сцена:** буфер инстансов, палитры скиннинга, пул мешей; `SkinnedRenderer` — движковый проход скиннинга.
  Проверка «граф не читает ресурс до записи» — инвариант клиента.
- **Extract:** рендер читает не ECS, а снимок `RenderWorld`, заполненный клиентом (интерполяция по alpha). Сейчас это
  `ArenaExport` + `SkinnedCharacters.Submit`. Позже снимок позволит рендеру уйти в свой поток.
- **GPU-симуляции** — первоклассная часть клиента:

```csharp
public interface IGpuSimulation
{
    string Name { get; }
    void Create(GpuSimContext ctx);                               // постоянные ресурсы, двойная буферизация состояния
    void AddPasses(RenderFrame frame, in SimFrame sim);           // фаза Simulation: шаги на тиках кадра (шаг решает сама)
    void OnReadback(ReadOnlySpan<byte> data);                     // только представление и диагностика
}
```

  `SimFrame` — тики кадра (`TickId` от первого до последнего; 0 тиков — пауза) и заявки. **Каждая заявка CPU несёт
  `TickId`**: наблюдатель тиков модуля (`ClientBuilder.AfterTick`, после каждого тика) кладёт её в `SimRequests`, симуляция в кадре
  берёт заявки кадра по порядку тиков и заявку тика t — к своему шагу тика t; шаг решает она сама (огонь — 60 Гц, каждый второй тик; пара тиков может лежать в разных
  кадрах). Асинхронный readback (`GpuReadback.Latency` — 3 кадра) — только представление и диагностика, на авторитетную симуляцию не
  влияет никогда. Реализация — огонь (`fire.N`: сим `Sword.Engine.Fluid2D` на экземпляр горящего оружия, кисть — головка оружия тика
  `IWeaponTips`); общего GPU-ресурса тел бойцов нет. Кровь (решение 15) и песок — на том же API.
- **Debug draw:** линии, капсулы, текст в мире — для диагностики фич.
- **UI-проход:** `UiRenderer`, `UiVectorFontGpu`, `ui.hlsl` — из `Sword.Engine.Ui` (`UiPass`, `Renderer.Ui`).

### Fluid2D (`Sword.Engine.Fluid2D`)

- Ядро 2D-сима FluidNinja LIVE-2 для огня, позже крови и песка — эффекты отличаются только параметрами (`Fluid2DParams`). Гриды — хранилища
  half с ручной выборкой; шаг — проходы фазы `Simulation` (`fluid.composite` → `fluid.advection` → `fluid.divergence` → `fluid.pressure.x/y`
  → статистика), выход — текстура RGBA16F кадра (`Export`); CPU-эталон `Fluid2DReference` — те же формулы, GPU = эталон до округления half.
  Детерминизм: время — номер шага, редукции без атомиков. Подробно — `engine/Sword.Engine.Fluid2D/README.md`.

### Fluid3D (`Sword.Engine.Fluid3D`)

- Ядро 3D-газа (дым факела в мире; эталон — Epic Niagara Fluids `Grid3D_MovingGridFire`): коллокированная сетка half по осям мира, окно
  едет за целью целыми ячейками с переносом содержимого (дробный остаток — в показ); шаг — проходы фазы `Simulation` (`gas.sources` →
  `gas.curl` → `gas.forces` → `gas.advect.velocity` → `gas.divergence` → `gas.pressure.red/black` → `gas.project` → `gas.advect.*` → статистика);
  CPU-эталон `Fluid3DReference` — те же формулы, GPU = эталон до округления half; статистика и срезы XY/XZ для проверки. Детерминизм: без
  атомиков, SOR red-black на месте. Подробно — `engine/Sword.Engine.Fluid3D/README.md`.

### Ui, Content, Formats, Platform

- **Ui** — без GPU: `UiContext` и виджеты, `UiDrawList`, `UiTextShaper`, данные векторного шрифта. Отрисовка — в Render.
  Виджеты `UiContext` (перенесены на 6е с тестами SWORD) — у панели ручек F3 (`Engine.DevTools/TuningPanel`) и панели
  инвентаря игры (`InventoryPanel`) в слое панелей клиента движка; HUD рисует списком квадов.
  Запекание шрифтов (`UiFontBaker`) — в `Bake.Engine`. Тесты UI идут без видеокарты.
- **Content** — хранилище: пак, источники (`PakSource`, `MemorySource`), поиск пака, загрузка с кэшем и хэндлами,
  крючок горячей перезагрузки. Стабильная ссылка на ассет (`AssetPath`/`AssetId`) — маленький тип в Core: ею
  пользуются Formats и `Game.Data`, не завися от Content.
- **Formats** — двоичные раскладки движка: меш, скелет, клипы, текстуры, шрифты, PNG; чтение **и запись** в одном
  файле с версией формата — их используют и рантайм, и пекарня. Игровые форматы — в `Game.Data`.
- **Platform** — абстракции окна, ввода и диалогов; Win32 — отдельно и без зависимости от UI
  (`UiInputWin32` → адаптер в Client).

## 7. Runtime и Client

### Разделение

| | Runtime (симуляция) | Client (представление) |
|---|---|---|
| что | мир ECS, стадии тика, барьеры, журналы, планировщик, фиксированный тик, модули (часть симуляции), конфиг, ГСЧ, реплеи, хеш состояния | окно, ввод → команды, цикл кадра, Extract, рендер-граф, GPU-симуляции, UI, снимки, бенч кадра, оверлей разработчика |
| зависит от | Core, Diagnostics, Ecs, Content | Runtime, Ecs, Platform, Rhi, Render, Ui |
| нужен GPU | нет | да |
| exe | `Game.Headless` — только `Sword.Game.Bootstrap`: реплеи, сценарии, бенчи симуляции, тесты | `Game.App` — `Sword.Game.Bootstrap` и клиент |

Симуляцию (`Simulation`) создаёт exe через `Sword.Game.Bootstrap` и отдаёт клиенту движка; тики исполняет только он.
Клиентская часть игры видит симуляцию через узкий `SimulationLink` (Engine.Client): мир только для чтения
(`WorldReader` — чтение компонентов и ресурсов-значений, запросы и обход без записи; ни немедленных операций, ни тика,
ни записи колонок), какие команды принимаются (`Accepts<T>`), команды на ближайший тик, время тика, — поэтому
`Sword.Game.Client` не ссылается на Runtime (точка 1в). Проверка — `PublicSurfaceTests.SimulationLink_ReachesOnlyReadOnlyWorld`:
из публичных сигнатур `SimulationLink` транзитивно не достижим ни один изменяющий тип ECS и Runtime.

### Тик (Runtime)

```
Тик — после каждой стадии барьер (раздел 5)
├─ Begin       время тика, Prev* для интерполяции
├─ Intent      команды игрока (из клиента или реплея), ИИ, сценарии → FighterCommand; команды арены → спаун, Set<WeaponSlot>
├─ Gameplay    смерти до физики → рэгдолл; настройка новых бойцов; смена оружия; решения боя, аниматор; Guard: выносливость (отложен — решение 16)
├─ Animation   Push → Animation.Tick → Pull: позы, корневое движение
├─ Movement    корни-контроллеры, постановка стоп (FootPlacement)
├─ PrePhysics  кинематические капсулы по позе
├─ Physics     Push → XPBD, подшаги → Pull
├─ Combat      проходы клинков → StrikeContact
├─ Defense     блок и столкновения клинков (Guard) → StrikeBlocked, Clash — пуста: Guard отложен (решение 16)
├─ Resolve     урон по неотбитым контактам → Hit, Dead, SeverRequested
├─ Dismember   расчленение отвечает на заявки (Cutting) → LimbDetached, обломки (решение 21); сила удара (Impact) → HitResponse (решение 22)
├─ React       отдача и реакции на удары; последствия отруба (маска Severed, кровотечение)
├─ Aftermath   кровопотеря (→ Dead), возрождение, пересборка разбитых, политика обломков
├─ Settle      смерти тика → рэгдолл; «усадка» свежих отрубов (Cutting); статистика
└─ End         хеш состояния; запись реплея
служебные      runtime.commands до Begin: команды тика (игрока, арены, ручек, модулей) → события, их читают системы
               любой стадии игры в том же тике; runtime.export после барьера End: очередь кадра клиента и
               (наблюдатели — после тика). Добавляет Runtime, модулям недоступны
между тиками   точка обслуживания инструментов (DevTools): мир согласован, запросы из очереди исполняются здесь
```

Раскладка повторяет порядок `DuelArena.Tick`:

| SWORD | SWORD2 |
|---|---|
| `Think` (мозги бойцов) | Intent |
| `SettleDeaths()` в начале тика — «умершие до физики» | Gameplay: первая регистрация `DeathToRagdoll` |
| `KinematicBegin`, `ResolveRoots`, `PlaceBodies` | Gameplay → Animation → Movement → PrePhysics |
| подшаги XPBD | Physics |
| `KinematicStrikes`, `ApplyHits` (с отрубом внутри `ApplyHit`) | Combat → Defense → Resolve → Dismember |
| `ApplyReactions`, `KinematicReactions` | React |
| `AfterTick` (кровопотеря), возрождение, пересборка | Aftermath |
| `SettleDeaths()` в конце тика — в том числе умершие от кровопотери и свежие отрубы | Settle: вторая регистрация `DeathToRagdoll`, усадка отрубов модулем Cutting |
| `TickEnded` (модули) | End; затем служебная `runtime.export` → очередь кадра клиента |

Одно намеренное отличие: в SWORD отруб выполняется внутри `ApplyHit`, поэтому второй удар того же тика по той же
части приходится уже по отделённой части. Здесь все удары тика применяются в Resolve, а отрубы — в Dismember; повторная
заявка на уже отделённую часть отклоняется. Случай редкий, записывается как намеренное изменение семантики
(раздел 12). Стадий может стать больше — барьер дешёвый.

### Кадр (Client)

```
Кадр
├─ Platform     сообщения окна, снимок ввода
├─ FrameBegin   GPU, профайлеры, горячая перезагрузка шейдеров
├─ Input        ввод + камера → команда игрока в мировых координатах (раздел «Ввод»)
├─ Simulate     накопитель → N тиков Runtime (≤ MaxTicksPerFrame); после каждого — наблюдатели тиков клиентских модулей (заявки
│               GPU-симуляций с TickId); прибивка к границе тика для снимков
├─ Extract      журналы Added/Removed → инстансы; интерполяция → RenderWorld; Extract и точечные источники модулей
├─ Render       рендер-граф: проходы игры, затем модулей (шаги GPU-симуляций на тиках кадра, свои фазы); фазы Simulation → Opaque →
│               Composite → Transparent (слой ½) → Post (bloom, тонмап) → Ui → Debug
└─ Present      Present, снимок, бенч кадра; на границе кадра — снимки и GPU-диагностика (FrameId + TickId)
```

### Ввод

Клиент снимает ввод раз в кадр, а Runtime делает за кадр 0, 1 или несколько тиков. Правила:
- удерживаемые действия (движение, блок, цель под курсором) повторяются в каждом тике кадра;
- нажатие и отпускание потребляются **ровно одним тиком** — первым после кадра, в котором случились;
- кадр без тиков: фронт сохраняется до ближайшего тика; кадр из трёх тиков: `AttackPressed` не повторяется трижды;
- направление движения относительно камеры вычисляется в клиенте **до** записи команды: симуляция камеры не знает;
- реплей хранит готовые команды по тикам (`PlayerCommand` — уже в мировых координатах), а не клавиши; `FighterCommand` —
  намерение бойца, его пишет Intent из команды игрока, ИИ или сценария.

Клавиши арены (число врагов PageUp/PageDown, сброс R, смена оружия T, инвентарь 1–9) в SWORD меняют арену прямо
из `Program.cs`; здесь они — `ArenaCommand` из `Game.Contracts` по тем же правилам: фронт — ровно одним тиком,
в реплей — готовой командой. Привязки клавиш к действиям (`Attack`, `Block`, `Dodge`, `Move`, `ToggleHud`…) —
в конфиге.

### Модули

Четыре вида модульности — это разные уровни сложности, в v1 они разведены:

| вид | в v1 | как |
|---|---|---|
| отдельная сборка | да | модуль — сборка симуляции и/или клиентская сборка; подключается к exe статически |
| активация при запуске | да | `modules.<id>.enabled` в конфиге; неактивный модуль не регистрирует ничего |
| сборка без модуля | проверка | конфигурация `-p:Without<Модуль>=true` (как `DisableCutting` в SWORD): exe собирается без ссылок на модуль |
| деактивация на ходу | ограниченно | `deactivate`: системы модуля перестают исполняться, его проходы пропускаются, курсоры отпускают журналы; компоненты и ресурсы остаются. Полная горячая деактивация (удалить компоненты, дождаться fence GPU, освободить проходы и ресурсы) — поздний этап |
| выгрузка сборки | нет | `AssemblyLoadContext` не используется; слово «unload» не используется |

Хост ведёт **регистрационный токен модуля**: какие системы, курсоры журналов, проходы, ручки и строки бенча
принадлежат `ModuleId`. `deactivate` и `activate` работают по токену и, как любое изменение симуляции на ходу,
приходят командой с `TickId` (раздел «Детерминизм»). Проверки `SWORD_*_DISPOSE_AT` из SWORD (освобождение модуля
посреди игры) в v1 заменяет `modules.<id>.deactivateAt`.

Регистрация модулей симуляции — только в `Sword.Game.Bootstrap` (раздел 3); `Game.App` добавляет к ней клиентские.
Ядро (принцип 4) регистрируется тем же построителем, но не как модуль: `Simulation.Build(config, stages, core, modules)` —
без токена модуля и без ключа `modules.<id>`, выключить его нельзя.

```csharp
public interface IModule                          // Engine.Runtime; реализует сборка симуляции модуля
{
    string Id { get; }                            // латиницей: ключ конфига, логи, реестр
    void Configure(SimulationBuilder b);          // настройки, компоненты, системы по стадиям (After/Before), ручки, строки бенча
}

public interface IClientModule                    // Engine.Client; реализует клиентская сборка модуля
{
    string Id { get; }                            // тот же Id, что у симуляции модуля (или свой — у чисто клиентского)
    void ConfigureClient(ClientBuilder b);        // наблюдатель тиков, Extract, свет, проходы, GPU-симуляции, шейдеры, ручки, оверлеи
}
```

У модуля один `Id` на обе стороны: `modules.cutting.enabled` включает и `Sword.Game.Cutting`, и
`Sword.Game.Cutting.Client`; клиентская часть активна, только когда активен модуль. Id чисто клиентского модуля (огонь —
`fire`) объявляется симуляции (`Simulation.Build(…, clientModules)`, у игры — `SwordSimulation.ClientModuleIds`): группа `modules` его
знает (`modules.fire.enabled`), в `ActiveModules` (состав реплея) и хеш он не входит, Headless его секцию пропускает; Id, которого
симуляция не знает, — ошибка композиции. Выключенный клиентский модуль не настраивается вовсе. Композиция — exe
(`ClientModules.Compose`, у игры — `Sword.Game.App/ClientModuleList.cs`), сборка без модуля — `-p:Without<Модуль>=true` (шаг
`without-modules` verify.ps1). Построители узкие: `SimulationBuilder` знает ECS, стадии, конфиг и ручки; `ClientBuilder` — секцию
конфига, сервисы клиента игры (`IWeaponTips`, `ISceneFog`, `ISceneSky`), наблюдатель тиков (`AfterTick`, с `TickId`), `Extract`,
точечные источники (`Lights`), проходы по фазам, GPU-симуляции, числа шейдеров, вкладку F3, оверлей, `TickDt` и раздел итога
`--json`; игра (`IClientGame`) модулей не знает. Подробно — `engine/Sword.Engine.Client/README.md`.

- **Точки расширения** — стадии и метки систем, события и компоненты из `Game.Contracts` (протокол — раздел 9).
- **Стратегий-вопросов нет.** Сейчас ядро спрашивает модуль и ждёт ответа: `DuelArena.DetachStrategy`
  (`ILimbDetachmentStrategy`, `ChainedDetachment`), `DuelArena.Guard` (`IStrikeGuard`), `DuelArena.BodyPlacer`
  (`IBodyPlacer`), `FighterAnimator.SetLocomotion` (`ILocomotionSource`). Такой вопрос требует ответа и без модуля —
  отсюда и росли запасные пути. В `Game.Contracts` таких интерфейсов нет.

### Конфигурация

Живёт в Runtime. Слои, каждый перекрывает предыдущий: значения в коде → `sword.json` (в репозитории) →
`sword.user.json` (вне git) → переменные `SWORD_<СЕКЦИЯ>_<КЛЮЧ>` → ключи `--set секция.ключ=значение`.
Секции — типизированные записи. Подсистемы конфиг не читают: получают готовые объекты настроек при композиции;
ручки (`TuningGroup` из Diagnostics) привязываются к этим объектам там же. **Изменение ручки на ходу — команда
симуляции:** панель F3 ставит её на ближайший тик, в служебной стадии `runtime.commands` она становится событием с
`TickId` и применяется системой ручек в том же тике (для реактивных систем —
`ResourceChanged`) и записывается в реплей. Соответствие ~70 нынешних `SWORD_*` новым ключам составляется по мере
переноса фич; ручки живого рэгдолла не переносятся.

### Диагностика

`Log` с категориями вместо `Console.WriteLine("[sword] …")`, без аллокаций; профайлер CPU по стадиям и системам;
GPU — по проходам графа; счётчики (выделенные байты на тик, сборки GC, ожидание GPU); каналы трасс (обобщение
`RagTrace`, `MM_TRACE`, `HITTRACE`, `FEET_TRACE`).

Действующие правила производительности (приняты на этапах П и 6; полный текст —
[docs/history/stage-p.md](docs/history/stage-p.md), [docs/history/stage-6.md](docs/history/stage-6.md)):
- **Долгие циклы (OSR):** метод, который вызывается раз в тик или кадр и содержит долгий цикл, — тело цикла в отдельный
  метод (иначе многоуровневый JIT заменяет его на ходу — рывок на главном потоке); `AggressiveOptimization` — только
  тонкому методу из вызовов или примитивному циклу без пользы от PGO (корневой `AGENTS.md`; AGENTS.md Runtime, Client,
  Render).
- **Профайлер** (`--profile`, F2) — простой профайлер зон и `profile.json`, симуляцию не трогает: в хеш и реплей не входит, выключенный стоит ~0,
  включается ключом запуска или панелью, а не командой симуляции; GPU-таймстемпы проходов включены всегда. Не делаем:
  стеки вызовов в процессе (`dotnet-trace`/PerfView), события среды и ядра ETW, захват аномалий, вердикт «код или машина»,
  статистику конвейера GPU, снимки кучи.
- **Служебные кадры App** не входят в средние профайлера, худший кадр и байты итога прогона: все кадры до первого сыгранного
  тика включительно, смена размера, снимок.
- **Машина пользователя:** провал времени из-за фоновой нагрузки сообщается пользователю, пределы не ослабляются.

### Детерминизм, реплеи, эталоны

- **Авторитетна только симуляция.** Представление читает её и на неё не влияет; readback с GPU идёт только
  в представление и диагностику.
- **Счётчиковый ГСЧ.** Случайное число — чистая функция `f(главное зерно, поток, TickId, Entity, номер выборки)`
  (хеш-функция уровня Philox/xxHash). Решение конкретного бойца не зависит от порядка обхода, потока исполнения
  и от того, сколько случайных чисел взяли другие системы. У представления свои потоки, в реплей они не входят.
- **Всё, что меняет симуляцию на ходу, — команда с `TickId`:** команды игрока и арены, изменения ручек, деактивация
  и активация модулей. Клиент ставит их на ближайший тик, симуляция в служебной стадии `runtime.commands` делает
  из них события этого тика (их применяют системы стадий игры), реплей записывает.
  Отдельных «тихих» путей изменить симуляцию мимо команд нет.
- **Реплей** хранит: версию сборки (коммит), хеш `Content.swpak`, fixed dt и число подшагов, полный конфиг запуска
  (после всех слоёв), список активных модулей, главное зерно, команды по тикам (игрока, арены, ручек, модулей) и
  **хеш состояния мира каждые K тиков**. При воспроизведении первое расхождение хеша называет тик.
- **Хеш состояния:** сущности — в стабильном порядке (по `Entity`), компоненты — по стабильному имени; хешируются
  **поля**, а не сырые байты структур (padding не участвует); `-0` приводится к `+0`, NaN — к одному значению.
  Функция хеширования полей генерируется при регистрации компонента.
- **Вклад подсистем.** В ECS лежат только `BodyRef` и `PoseRef`, а Runtime не знает ни Physics, ни Animation —
  поэтому зависимость обращена:

```csharp
public interface IStateContributor                        // Engine.Runtime
{
    string Id { get; }                                    // стабильный: "physics", "animation", …
    void AppendHash(ref StateHasher hasher);              // полное авторитетное состояние, в стабильном порядке хэндлов
}
```

  Интеграционные системы игры регистрируют участников: `physics` — тела и сочленения, `animation` — авторитетные
  состояния аниматоров и поз, при необходимости другие. Runtime обходит их по `Id`. В реплей пишется хеш
  **по каждому участнику** — расхождение сразу называет не только тик, но и подсистему. Нужно к этапу 3.
- **Эталоны SWORD2** (`tests/reference/replays/*.swreplay`) фиксируются после подтверждения фичи пользователем
  (раздел 12). Изменение, которое меняет хеши, перезаписывает их теми же командами с доказательством: участники, которых
  изменение не касается, и траектории бойцов совпали тик в тик (перезаписи этапов 4–6 — `docs/history/stage-*.md`).
- Бенч, сценарии (`IScenario`: сцены рэгдолла, маршруты автопилота), снимок, прибитый к тику, — как в SWORD.

  `Severed`, `WeaponSlot`…), события (`StrikeContact`, `StrikeBlocked`, `Clash`, `Hit`, `SeverRequested`,
  `LimbDetached`), команды (`PlayerCommand`, `ArenaCommand`), намерение бойца (`FighterCommand`), идентификаторы (сегменты тела — сейчас константы `Fighter.Pelvis`,
  `Fighter.FArmL`…), метки систем ядра; раскладки GPU-данных тел (`GpuUnit`, `GpuSeg`) и ключи ресурсов графа —
  чистыми данными, без ссылок на Render. Без логики и без интерфейсов-стратегий.
- **`Sword.Game`** — симуляция: системы и правила. Модули его не видят, поэтому устройство арены им недоступно.
- **`Sword.Game.Client`** — ввод → команды, камера, Extract бойцов и тел, проходы сцены, HUD.
- **`Game.Data`** — игровые форматы (риг, оружие, кровь оружия, анатомия, `actions.json`).

### Системы (в порядке стадий)

Каждая реакция, которая должна произойти в том же тике, стоит в стадии позже своего производителя; задержки на тик
явно помечены `NextTickOk` (раздел 5). И то и другое проверяется при сборке мира.

| стадия | система | вид | откуда логика |
|---|---|---|---|
| Intent | `PlayerCommandSystem`, `EnemyAiSystem`, `BenchAutopilotSystem`, сценарии | непрерывные | `PlayerController`, `EnemyAi`, `BenchAutopilot`, `RagdollScene` (интерфейс `IFighterBrain` уходит) |
| Begin (с 6б; 4а–6а — Intent) | `ArenaCommandSystem` | реактивная: `Event<ArenaCommand>` — спаун и удаление врагов, сброс, меч игрока (`PlayerInventory`, `Set<WeaponSlot>`); Intent видит арену после неё | `SetEnemyCount`, `Reset`, `NextPlayerWeapon`, `EquipPlayerWeapon` (сейчас из `Program.cs`) |
| Gameplay | `DeathToRagdollSystem@Gameplay` | реактивная: `Added<Dead>` — смерти до физики (сценарии, команды); `NextTickOk<Added<Dead>>` для смертей из Resolve и Aftermath | `SettleDeaths()` в начале тика |
| Gameplay | `FighterSetupSystem` | реактивная: `Added<Fighter>` — поза, аниматор, первое оружие (сочленение — хуком `BodyRef`, 5а); боец создан сразу с полным набором компонентов | `Spawn`, `Build`, `PlaceBuilt`, `AttachRig` |

`DeathToRagdollSystem` зарегистрирована дважды (`@Gameplay` и `@Settle`), как `SettleDeaths` вызывается дважды за тик
в SWORD; она идемпотентна (берёт только бойцов с `Kinematic`), поэтому смерть, уже переведённая в конце прошлого тика,
в начале следующего пропускается.

В клиенте (`Sword.Game.Client`): камера (`RtsCamera`), Extract бойцов и тел (`SkinnedCharacters`, `ArenaExport`,
`GpuArena`; инстансы — по журналам `Added/Removed`), проходы сцены, HUD (`Hud`, `InventoryUi`). Уровень
(`ArenaLayout`, `ArenaWorld`, `Terrain`) — описание, из которого строятся `HeightField` и колонны.

**Цель боя** (пользователь, при разбивке этапа 6): максимально отзывчивый бой — игрок влияет на действия и движение
всегда (антипример — Dark Souls, где анимация отнимает управление). Ошибки SWORD исправляются, каждое отличие
записывается в md фичи; рывок (Пробел) — временное быстрое ускорение без последствий для дальнейшей скорости, во время
рывка — уклонение от ударов.

### Протокол боя без стратегий

Модуль влияет на исход не ответом ядру, а фактом в журнале. У каждого факта — идентификатор, по которому его
сопоставляют: `ContactId` и `RequestId` = (`TickId`, порядковый номер в детерминированном порядке).

```
Combat     StrikeDetection → StrikeContact { ContactId, Attacker, Victim, Part, Point, Dir, Blade, Speed, Kind }
Defense    Guard читает StrikeContact → StrikeBlocked { ContactId, Kind, StaminaCost }, Clash { ContactId, Point }
Resolve    HitApply применяет каждый StrikeContact, для которого нет StrikeBlocked → Hit, Dead, SeverRequested { RequestId, … }
Dismember  Cutting читает SeverRequested → при успехе LimbDetached { RequestId, Victim, Segment, Part }
React      реакции на Hit и Clash; ядро реагирует на LimbDetached: маска Severed, кровотечение
Aftermath  кровопотеря → Dead
Settle     Dead → рэгдолл; Cutting «усаживает» свежие отрубы; статистика
```

Без Guard не появляется `StrikeBlocked` — удар проходит. Без Cutting заявка на отруб остаётся без ответа — конечность
на месте. Это не запасной алгоритм, а естественная обработка фактов: ядро не ждёт ни ответа, ни модуля. Guard
отложен (решение 16): стадия Defense пуста — удары проходят всегда. Cutting в работе (решение 21): пока модуль не
отвечает, стадия Dismember пуста и заявки на отруб остаются без ответа.

### Контракт расчленения

Пространство `Sword.Game.Cutting` в SWORD (`CutMesh`, `CutSurface`, `DerivedSkinMesh*`, `LimbDetachment`,
`LimbDetachCaptured`, `SkinCut*`) используют ядро арены, кровь и внутренности — это **контракт**, а не часть модуля.
В `Game.Contracts` уходят **только данные и события**: заявка на отруб, событие отделения, компоненты отрубленной
части, описание поверхности среза. Логика — в модуле: отделение и капсулы (`FighterCutter`, `MeshCutter`,
`JointDetachment`) — в `Sword.Game.Cutting`, разрез мешей (`SkinMeshCutter`, `SkinCutMeshes`) — в
`Sword.Game.Cutting.Client`. Точное деление и модель (энергия против сечения, профиль ткани, перелом, отрыв, клочья) — план этапа 11
`artifacts/plans/dismemberment/PLAN.md` (решение 21).

### Что не переносится (живой рэгдолл)

- `Fighter.Locomotion` (шаги живого: `UpdateFeet`, `UpdateCapture`, `BuildSupport`, выпуклая оболочка опоры);
- мышечный привод живого в `Fighter.Muscles` (`DrivePelvis`, `DampMuscles`, коэффициенты `K*`);
- цели руки и клинка (`HandGoal`, `BladeGoal`, `BladeAngles`) и живая часть `Fighter.BeginTick`;
- ручки живого рэгдолла (`SWORD_MUSCLE`, `SWORD_KARM`, `SWORD_KLEG`, `SWORD_GAIN`, `SWORD_CP_*`…); разовые исследования
  `tools/ue/probe_*.py`, `retarget_variants.py` (конвейер Unreal `tools/ue` переносится — раздел 11).

**Осторожно со смешанным кодом.** `Fighter.BeginTick` сейчас идёт для всех не-кинематических, то есть и для трупов,
и зовёт `UpdateCapture`/`UpdateFeet`. При переносе рэгдолла из смешанного кода берётся только то, что влияет на трупы, —
это часть рэгдолла трупа, а не живого. Приёмка — сцены рэгдолла против чисел SWORD (этап 7).

на симуляцию, оно явно выносится в сборку симуляции модуля.

**Что сейчас называется запасным путём, а на деле им не является.** Из четырёх «запасных путей» SWORD чистый — только
один (стопы без постановки: это просто отсутствие модуля, кода у него нет). Три других работают **и при включённом
модуле**:
- `LegacyLocomotion` — локомоция всех врагов (MM — только у игрока);
- `FacingGuard` — блок врагов (`BladeGuard` отдаёт ему всех, кроме игрока);
- `JointDetachment` — хвост цепочки `ChainedDetachment`, когда разрез отказался.

Поэтому они не удаляются, а **переезжают в свои модули** как вторая реализация внутри модуля. Две реализации в одном
модуле законны, если обе работают при полном наборе модулей: MM для игрока и клипы для врагов — это уровни
детализации (hero / near), а не запасной путь.

**Правило:** код, который исполняется только тогда, когда какого-то модуля нет, — запрещён.

**Следствие для проверок:** «каждый модуль выключен» доказывает устойчивость (игра стартует, не падает, остальные
модули работают), но не играбельность: без Locomotion бойцы ходят в позе привязки. Игровые сценарии и эталоны — с полным
набором модулей, доступных на текущем этапе.

Каждый модуль переносит свой md-документ, шейдеры (в своей папке, в выходе — `Shaders/<сборка>/…`) и тесты.

## 12. Приёмка фич и тесты

### Как принимается фича

С этапа 7 (решение 14) — без сверки со SWORD и без переноса тестов SWORD: в п. 1 — откуда идея и какие решения свои, в п. 3 —

1. **Перенос.** В md-документе фичи или модуля — откуда логика (файлы SWORD), что изменилось при переписывании
   и какие места стали реактивными.
2. **Состояние видно.** Состояние фичи хеширует её участник (`IStateContributor`); её свойства проверяют тесты и инварианты
   симуляции.
3. **Автоматически (Claude):** сборка; архитектурные тесты; тесты свойств фичи; инварианты; эталонные реплеи;
   `verify.ps1`. Перед сверкой эталонов проверяется SHA-256 эталонного пака (этап 0). Ослабить ожидания тестов можно
   только явной правкой с сообщением пользователю.
4. **В игре (пользователь):** список «Что проверить в игре» md фичи — 3–7 пунктов: клавиши, что должно происходить, на
   что смотреть.
5. **Подтверждение** → фиксируется эталон SWORD2 (реплей с хешами состояния и снимок) — для регрессий следующих фич.
   Следующая фича — только после подтверждения.

Ход работы — по корневому [AGENTS.md](AGENTS.md) («Ход работы», «Сборка и проверка»): быстрая разработка без классов точек,
отдельных проверяющих и записей истории по шагам (пользователь, 2026-10-16). Прежний ход точки (этапы 6–15) —

| смешанный код живого рэгдолла влияет на трупы | из `Fighter.*` берётся только то, что относится к трупу (разбор — рабочий план этапа 7); инварианты энергии и суставов трупа |
| потребитель срабатывания оказался в стадии производителя (реакция на тик позже) | объявления производителей и проверка при сборке мира; граничные тесты журналов |
| реплей расходится из-за изменений мимо команд | всё, что меняет симуляцию на ходу, — команда с `TickId`; `Headless` воспроизводит запись `Game.App` с теми же хешами |
| прототип затянется | контрольные точки 1а–1д, каждая запускается; что не входит — записано |
| ECS превратится в самоцель | v0 — только то, что нужно прототипу; остальное — по потребителю |
| реактивные системы пропустят или повторят срабатывание | журналы с курсорами: каждый потребитель видит запись ровно один раз; тесты на границы тиков и деактивацию |
| недетерминизм (порядок, потоки, ГСЧ) | барьеры со стабильным слиянием, явные `After/Before`, счётчиковый ГСЧ, хеш состояния в реплеях |
| симуляция незаметно начнёт зависеть от клиента | разделение по сборкам, свойство стороны в MSBuild, архитектурный тест замыкания `Headless` |
| косвенность хэндлов съест производительность | микробенчмарки подсистем, бенч кадра |
| D3D12 протечёт в модули | `Vortice.*` только у Rhi и Render + список исключений, который только сокращается |
| переходные пулы управляемых объектов останутся навсегда | у каждого — план растворения в md фичи |
| хобби-темп: интерес пропадёт на длинном этапе | каждый этап — видимый результат в игре |
| диагностика держит память симуляции | у журналов нет внешних курсоров: клиент получает копии в шаге экспорта; инварианты только читают и хеш не меняют |
| с параллельностью поменяется семантика создания сущностей | черновики `EntityDraft` с первого дня; тест одинаковых индексов при любом числе потоков |
