### 8. Агентский доступ

Движок рассчитан на то, что его запускает, наблюдает и отлаживает ИИ-агент — Claude Code, Codex (GPT) или любой
другой MCP-клиент. Агент — такой же пользователь движка, как человек: у человека панели DevTools, у агента —
инструменты MCP, и оба стоят на одном слое интроспекции. Отсюда же автоматический контроль фич (решение 4).

**Агентский API отвечает на проверяемые вопросы, а не выгружает внутренности движка (решение 13):** почему это
случилось, выполняется ли условие, чем отличаются два прогона, что будет, если изменить параметр. Цель — агент как
экспериментатор над движком, а не удалённый оператор панелей.

#### Слои

```
агент (Claude, GPT…) ──MCP──► Engine.Agent — хост: реестр инструментов, сеансы, квитанции, артефакты и снимки,
                              │               инструкции сервера
                              ├─ вопросы: условия, инварианты, причинность, история, снимки и сравнения
                              ├─ эксперименты: реплеи, ветвления, перебор параметров, минимизация, дифференциальные прогоны
                              ├─ приёмка: FeatureManifest → feature.verify
                              ├─ Engine.Agent.Client — пакет визуального наблюдения, GPU-время (только в Game.App)
                              └─ Game.Agent — игровые виды и пробы: бойцы, арена, сценарии
человек ──────────── UI ────► Engine.DevTools / Game.DevTools
                                │
                  Engine.Introspection — общая основа: очередь запросов и точка обслуживания; компоненты по
                  стабильным именам и полям; IStateContributor.Describe; ObservationHistory; журнал причинности;
                  язык условий; управление инвариантами (контракт IInvariant и проверка после барьеров — в Runtime);
                  карта архитектуры; управление временем; постановка команд
```

Ядро игры и модули об агенте не знают: своё состояние они отдают через `IStateContributor` (раздел 7), события —
через шаг экспорта в конце тика, проверки — через инварианты и манифесты фич. Runtime не знает ни MCP, ни моделей:
протокол живёт только в `Engine.Agent`.

#### Потоковая модель

Главная гарантия агентского слоя: **агент не гоняется с симуляцией и рендером.**

- Обработчик MCP живёт на своём потоке и **никогда напрямую не читает** `World`, Physics, Animation или Render.
- Запрос к симуляции ставится в очередь и исполняется **на потоке симуляции в точке обслуживания** — между тиками,
  после экспорта тика (служебная стадия `runtime.export`), когда мир согласован. `Game.App` обслуживает очередь раз в кадр после шага Simulate (и на паузе),
  `Game.Headless` — после каждого тика (и на паузе). По запросу `time.break` точка обслуживания ставится после
  барьера нужной стадии — останов посреди тика.
- В точке обслуживания данные только **копируются** в ответ; разбор, JSON и отправка — на потоке агента. У точки есть
  бюджет времени на тик; тяжёлые запросы в живом App исполняются только на паузе.
- **Каждый ответ содержит квитанцию** (ниже) — с `TickId`, а при останове посреди тика и со стадией.
- Снимок кадра и GPU-диагностика исполняются **на границе кадра** клиентом и возвращают `FrameId` вместе с `TickId`
  показанного состояния.
- Мутация только **ставит команду на конкретный будущий тик** (по умолчанию — ближайший); в текущий и прошедшие тики
  писать нельзя.
- Панели DevTools читают мир по тем же правилам — через точку обслуживания и Extract, а не напрямую: когда рендер уйдёт
  в свой поток, менять их не придётся.

#### Квитанции, артефакты, снимки

- **Квитанция в каждом ответе:** `BuildId`, `ContentHash`, `SessionId`, `TickId`, `Stage`, `FrameId`, `Complete`,
  `Truncated`, `ContinuationToken`, `ArtifactId`. По ней видно, к какому состоянию относится ответ и полон ли он.
- **Большое остаётся на стороне сервера** под `ArtifactId` в `artifacts/agent/<сеанс>/`; в ответе — сводка и путь.
- **`world.snapshot`** сохраняет наблюдательную копию состояния (компоненты по стабильным именам + `Describe`
  подсистем) под `SnapshotId`; **`world.diff(a, b)`** сравнивает два снимка на сервере — модели не нужно передавать
  оба состояния. Это не сериализация для восстановления мира — её в v1 нет (раздел 5).
- **Ответы под бюджет контекста:** сводка, пагинация, лимиты. У MCP-клиентов есть предел размера ответа инструмента —
  ответы проектируются заведомо меньше.
- **Инструкции сервера MCP** — короткие: рекомендуемый порядок расследования, ограничения, стоимость тяжёлых
  инструментов. У инструментов — аннотации: только чтение или мутация, класс стоимости.

#### Язык условий: ObservationPredicate

Условия нужны многим инструментам сразу, поэтому язык у них **один** — типизированное JSON-дерево:

```
all:
  - component: Transform
  - field: Transform.Position.Y
    lessThan: -10
```

- Узлы: `all`/`any`/`not`; наличие компонента; сравнения полей (`lessThan`, `between`, `isFinite`…); «событие
  случилось» (тип, отбор по полям, окно тиков); агрегаты по запросу (`count`, `min`, `max`, `sum`, `mean`); наборы
  сущностей; окна тиков; стадия.
- На нём строятся: `time.runUntil(условие)`, `time.break(стадия, условие)`, `watch.add(условие, проекция)`,
  `invariant.define(условие)`, `profile.captureWhen(условие)`, проверки в сценариях и манифестах фич.
- **Произвольного C# нет** — только операции из белого списка. Условие компилируется при установке в быстрый
  исполнитель, его стоимость видна агенту; исполняется на потоке симуляции (в точке обслуживания или после нужного
  барьера), детерминировано и состояние не меняет.

#### Инварианты

```csharp
public interface IInvariant                      // Engine.Runtime, как IStateContributor: реализуют игра и модули
{
    string Id { get; }                           // стабильный: "physics.finite", "fighter.deadNotKinematic", …
    InvariantCost Cost { get; }                  // каждый тик, раз в N тиков, по запросу
    InvariantScope Scope { get; }                // сущность, система, подсистема (в т. ч. внутри шага), мир, клиент
    string After { get; }                        // после барьера какой стадии (имя; runtime.export — конец тика)
    void Evaluate(in InvariantContext ctx, ref ViolationSink violations);
}
```

- Инварианты в коде регистрируют подсистемы, игра и модули; агент добавляет свои условиями — `invariant.define`.
- Нарушение — структурированный факт `InvariantViolation { Id, TickId, Stage, Entity?, Details }`: попадает
  в `ObservationHistory`; `time.breakOnInvariant` останавливает симуляцию в точке обслуживания после нарушившего барьера.
- Примеры: все координаты конечны; каждый `BodyRef` указывает на живое тело; одна физическая ручка принадлежит ровно
  одной сущности; мёртвый боец не остаётся кинематическим; энергия рэгдолла не выросла в 100 раз за подшаг; модуль
  после выключения не оставил своих компонентов; рендер-граф не читает ресурс до записи.
- Проверки внутри шага подсистемы (подшаги физики) живут в самой подсистеме и включаются в диагностическом режиме.
- Режимы: в тестах и `verify` — все дешёвые включены; в бенче — выключены (их стоимость меряется отдельно); в игре —
  по конфигу. Исправления после Пд: в живой игре (Sword.exe) тяжёлые — раз в 4 тика (`InvariantCost.Heavy`,
  `SimulationInvariants.LivePeriods`), везде остальном — каждый тик. Инвариант ничего не меняет, его стоимость измеряется.
- Инструменты: `invariant.list`, `invariant.run`, `invariant.enable`, `invariant.define`, `time.breakOnInvariant`.
- Решено на точке 3г: стадия — имя (стадии мира — строки, отдельного `StageId` нет); `InvariantCost` — период в тиках
  (1 — каждый тик, N, 0 — по запросу: сам не включается, включённый явно — каждый тик); Id — части из латиницы, цифр и
  `_` через точку, первой — строчная буква; режим — `sim.invariants` (по умолчанию включены; бенч кадра — выключены);
  `TickId` нарушения — номер тика, в котором нарушено (как у событий); в живой игре `time.breakOnInvariant` встаёт после
  тика нарушения (посреди тика — только Headless, как `time.break`). Базовые: движка — `ecs.finite` (каждый тик),
  `ecs.entityRefs` (по запросу); анимации — `animation.finite`, `animation.settled`, `animation.pool`,
  `animation.owners`; модуля Locomotion — `locomotion.poses`. Поз без владельца ядро не ищет: позы модуля лежат в его
  компонентах — их держит инвариант модуля.

#### Причинность: state.why

Агент спрашивает не только «что», но и «почему»:

```
state.why(player, "Health.Value")
→ Health: 100 → 64 · тик 1842 · система HitApply@Resolve
  причина: PlayerCommand.Attack → StrikeContact → Hit → Set<Health>
  источник: HitApplySystem.cs:117
```

- **Диагностический режим** (выключен по умолчанию; включение не меняет хеш состояния): команды, события и записи
  `Set<T>` получают `CauseId`, `ParentCauseId`, `TickId`, стадию, регистрацию системы и источник
  (`[CallerFilePath]`/`[CallerLineNumber]` у методов команд). Записи идут в ограниченный кольцевой `CausalityLog`.
- **Родительская причина** передаётся сама: реактивная система обрабатывает срабатывания, у каждого есть `CauseId`,
  и всё, что она порождает при обработке, получает его родителем (окружение `ctx.Cause` при обходе или явный параметр).
  Корни цепочек — команды игрока, арены и агента.
- **Точность — честно:** для дискретных фактов (команды, события, `Set` реактивных компонентов) цепочка точная;
  для непрерывных чисел (`Transform` из физики) — грубая: какая регистрация системы писала столбец в каком тике.
  На вопрос «почему число такое» отвечают история, `time.break` и дифференциальный прогон.
- **Слот `CauseId` в записях команд и событий есть с ECS v0** (вне диагностического режима пуст) — дооснащать ECS
  не придётся.
- Глубже кольца — `replay.observe` с включённой причинностью.

#### Контракт фичи: FeatureManifest и feature.verify

Приёмка фичи (раздел 12) описывается машинным манифестом рядом с её md-документом (`feature.json`):

| поле | что в нём |
|---|---|
| `FeatureId`, `SourceRoots` | имя фичи и где её код |
| `RequiredModules` | с какими модулями она проверяется |
| `Scenarios` | сценарии и их проверки (условия) |
| `Invariants` | инварианты, которые должны держаться |
| `ExpectedMetrics` | метрики с допусками — свои числа (с 7а, решение 14) |
| `VisualViews` | какие пакеты наблюдения снять (ракурс, оверлеи) |
| `PerformanceBudgets` | время стадий и систем, байты на тик — со статистикой повторов; кадр App (с точки 4д) |
| `HumanChecklist` | список «что проверить в игре» для пользователя |

- **`feature.verify(id)`** одним воспроизводимым вызовом: запускает сценарии в `Headless`, проверяет инварианты,
  сравнивает метрики, снимает виды в App, проверяет бюджеты — и выдаёт краткий итог с путями к артефактам.
- **Вердикт независим от агента:** он опирается на инварианты, эталоны и подтверждение пользователя в игре, а не на
  мнение того же агента. Ослабить ожидания манифеста (допуски, инварианты) молча нельзя — только явной правкой,
  в коммите и с сообщением пользователю.
- Решено на точке 3д: манифест — JSON с комментариями (`format: sword-feature`, `version: 1`), строгий разбор (неизвестный
  ключ, тип, ссылка на несуществующий сценарий — ошибка с путём); поля плана — `id`, `sourceRoots`, `requiredModules`,
  `scenarios`, `invariants`, `metrics`, `views`, `budgets`, `checklist`. Сценарий — реплей из репозитория (хеши
  сверяются) или команды по тикам (`{command, fields, from, to}`) на конфиге из кода; каждый сценарий записывается, его
  проверки — условия `ObservationPredicate` после тика (`always`, `never`, `eventually`, `atEnd`, окно `tickId`).
  Инварианты манифеста включаются явно; нарушение любого включённого инварианта — провал. Метрика — поле сущности
  (несколько листьев — длина вектора) после тика или `min/max/mean` окна против `expected ± tolerance`. Бюджет —
  отдельные прогоны как бенч (без инвариантов, записи и сверки хешей), медиана повторов: мс на тик, мс стадий (время от
  барьера до барьера; время систем — отдельный прогон с профайлером, с Па), байты на тик; время проверяется только
  в Release, байты — всегда. Вид — кадр `Sword.exe --replay`
  по записи сценария (App сверяет хеши с Headless); эталонных снимков нет — кадры смотрят глазами. Чек-лист = пункты
  «Что проверить в игре» md фичи (тест). Логика — Introspection (`FeatureVerifier`), инструменты — `feature.list`,
  `feature.verify`, без агента — `Sword.Headless --feature ID|all` (код 4 — провал), `verify.ps1` шаг `features`.
  Манифесты задним числом — `movement`, `control`, `tools` (прототип), `animation`, `determinism`.

#### Эксперименты

- **`experiment.fork(реплей, тик, варианты)`** — пересчитать реплей до тика в `Headless` и продолжить ветками
  с вариантами (команды, конфиг, модули, ручки); ветки идут параллельными процессами.
  **`experiment.compare(ветки)`** — метрики, хеши, первое расхождение, разница описаний.
- **`experiment.sweep(параметры)`** — перебор комбинаций в `Headless`; на выходе: время стадий и систем, число
  обработанных сущностей, аллокации и память, хеш результата, статистическая устойчивость (повторы, медиана, разброс)
  и место первого резкого ухудшения масштабирования. Пример:

```
fighters = [100, 1000, 10000]
workers  = [1, 2, 4, 8, 16]
lod      = [hero, hybrid, crowd]
```

  Такие переборы масштабирования осмысленны после параллельного планировщика и LOD-уровней; сам механизм — раньше.
- Основа всего — детерминизм, реплеи и `Headless` как пакетный исполнитель.
- Решено на точке 3д: ветки `experiment.fork` — потоки одного процесса, а не процессы (симуляции независимы, общие только
  неизменяемые ассеты; процессы — когда понадобится изоляция падений); вариант ветки — `set` (конфиг действует с тика 0:
  конфиг собирает симуляцию), `commands` с тика развилки и позже (перебивают команды реплея своего типа), `cut` (команды
  реплея после развилки не идут — `Replay.Head`); «ручка с тика T» — команда ручки (`TuningCommand`, с 6е). Ветка
  записывается с хешем каждого тика и сравнивается с записью базы: команда тика T
  меняет состояние после T+1 тиков. `experiment.compare` — `ReplayDiff` и листья описаний разошедшихся участников на
  первом разошедшемся хеше. `experiment.sweep` — комбинации (до 64) по очереди, повторы, медиана и разброс, мс стадий,
  байты, детерминизм итогового хеша, «резкое ухудшение» — время растёт больше чем в 1,5 раза быстрее числового ключа.

#### Минимизатор: replay.minimize

`replay.minimize(условие ошибки)` — дельта-отладка над реплеем: убирает лишние команды, бойцов, модули, ключи
конфига, хвост тиков, части сценария, пока ошибка (условие или инвариант) ещё воспроизводится. Итог — короткий реплей
и его описание `scenario.json`: вместо десятиминутной битвы — «два бойца, 47 тиков, одна команда удара». Отрезать
начало (стартовать посреди боя) можно будет, когда появится сериализация мира.

#### Дифференциальное исполнение подсистем

`differential.run(reference, candidate)` — две реализации одного API подсистемы (например, `Physics.Sequential`
и `Physics.ParallelSoA`) получают одинаковые входы; после каждого шага сравниваются положения и скорости, контакты,
решения суставов, события — с допусками, — и производительность. Два режима: пошаговый с пересинхронизацией
(ошибка одного шага) и свободный прогон (накопленное расхождение).

- **Эталонная реализация — не запасной путь** (решение 9): в игре работает одна реализация, эталон живёт в тестах
  и диагностике как оракул для оптимизаций (SoA, SIMD, параллельность).
- **Требование уже сейчас:** API подсистем (Physics, Animation) допускает две реализации в одном процессе.

#### Пакет визуального наблюдения: capture.bundle

Вместо голого снимка — пакет: цвет; глубина; ID сущности на пиксель; нормали; векторы движения; отдельные
отладочные оверлеи (капсулы, контакты, проходы клинка, скорости); список видимых сущностей с экранными
прямоугольниками и именами («левое предплечье бойца 17»); камера; `TickId`, `FrameId`. Мультимодальная модель
понимает сцену по данным, а не угадывает по пикселям. Требование к рендеру: инстансы GPU-сцены несут `Entity`
и сегмент тела; ID-проход — в диагностическом режиме.

#### Карта архитектуры из живого мира

`architecture.projects`, `ecs.plan`, `ecs.explainSystem`, `ecs.componentUsage`, `render.graph`, `module.graph` —
строятся из фактически собранного мира, а не из документации. Например, `ecs.explainSystem("HitApply")` возвращает:
стадию и порядок, чтение и запись компонентов, порождаемые события, потребляемые журналы, зависимости и `NextTickOk`,
исходный файл (caller info при регистрации), активна ли система в текущей конфигурации. Метаданные у планировщика,
реестра и рендер-графа есть и так — карта почти бесплатна.

#### Оценка агентского интерфейса: Sword.Agent.Evals

Удобство для агента — измеряемое свойство, а не ощущение:
- набор типовых неисправностей — **модули-неисправности** `Sword.Game.Faults` (модуль симуляции, включается
  конфигом; каждая неисправность — известная ошибка; в сборку игры не входит);
- ожидаемый диагноз, допустимое число вызовов инструментов, время до локализации, объём возвращённых данных, доля
  ложных выводов, получен ли минимальный реплей;
- прогон — скрипты, запускающие агента (Claude Code, Codex) в неинтерактивном режиме против `Headless`, и подсчёт оценок.

Так выясняется, полезен ли `state.why`, какие ответы слишком многословны, каких агрегатов не хватает, какие
инструменты агент вызывает в неправильном порядке.

#### Инструменты

Несколько композиционных инструментов вместо десятков узких: условия, проекции и агрегаты — параметры, а не новые
команды.

| группа | инструменты |
|---|---|
| сеанс | `session.start` (Headless или живой App; конфиг, модули, зерно), `session.status`, `session.stop` |
| время | `time.pause`, `time.resume`, `time.step(n)`, `time.runUntil(тик или условие)`, `time.break(стадия, условие)`, `time.breakOnInvariant`, `time.seek(тик)` |

| проверки | `invariant.list`, `invariant.run`, `invariant.enable`, `invariant.define` |
| команды | `command.send` — игрока, арены, ручек, модулей; всегда на будущий тик |

#### Правила

- **Один протокол — MCP**: его понимают Claude Code, Codex и другие клиенты. Транспорт: stdio для
  `Game.Headless --agent`; для живого `Game.App --agent` — Streamable HTTP на 127.0.0.1 (решено на точке 1е: HTTP
  Claude Code подключает без моста; свой HTTP/1.1 на `TcpListener`, потому что http.sys без прав администратора
  резервирует не всякий адрес). Реализация — свой минимальный JSON-RPC по спецификации MCP (решено на точке 1е:
  официальный SDK тянет хостинг и внедрение зависимостей в exe игры, а нужны четыре метода).
- **По умолчанию — только чтение.** Всё, что меняет симуляцию, — команды с `TickId` (ручки, команды игрока и арены,
  модули); они пишутся в реплей. Сеанс агента воспроизводим и проверяем человеком: вот реплей, вот что агент сделал.
- **Стабильные имена и коды ошибок** — те же, что в ECS, конфиге и журналах; ответ — JSON по схеме инструмента.
- **Отладка держится на детерминизме:** `time.seek`, `replay.diff`, эксперименты и минимизатор работают, потому что
  симуляция детерминирована (раздел 7).
- **Только локально и только при разработке:** выключено по умолчанию, включается ключом `--agent`; сборка
  `-p:WithoutAgent=true` не содержит сборок агента и модулей-неисправностей; сам агент в хеш состояния не входит и мимо
  команд ничего не меняет.
- **Жизнь сервера агента** (6а, 6ж): `Sword.Headless --agent` выходит по концу stdin, по концу родителя и после 15 мин
  без вызовов (`--idle-exit`; клиент переподключает сам); дети инструментов и фоновые запуски `verify.ps1` — в задании
  Windows `KILL_ON_JOB_CLOSE`; сервер собирается с `-nodeReuse:false` (узлы MSBuild не висят).
- **Фича без агентского вида не принимается:** её состояние видно через `IStateContributor.Describe`, её приёмка
  описана манифестом (раздел 12).

#### Чего не делаем

- произвольное выполнение C# через MCP;
- прямой доступ агента к памяти ECS;
- правки `AGENTS.md` агентом без просмотра человеком: агент предлагает, человек принимает;
- десятки узкоспециализированных команд вместо нескольких композиционных;
- приёмку фичи только по заключению того же агента — без независимых инвариантов, эталонов и подтверждения в игре;
- модель-специфичные типы внутри Runtime.

#### Правило: каждое изменение кода — проверка агентских инструментов

При написании любого кода — фичи, модуля, системы, исправления — отвечаем на вопрос: **сможет ли агент увидеть,
проверить и отладить это изменение уже имеющимися инструментами?** Если нет — вид, инвариант или инструмент
добавляется в том же изменении, а не «потом».

| что появилось в коде | что проверить и, если нужно, добавить |
|---|---|
| новое состояние (компонент, поле подсистемы) | видно ли через `world.query`/`entity.get` по стабильному имени или через `IStateContributor.Describe`; нет — расширить `Describe` |
| новое свойство, которое должно всегда держаться | инвариант (`IInvariant`) с классом стоимости |
| новое событие или факт | стабильное имя; передаётся ли причина (`CauseId`); попадает ли в `ObservationHistory` |
| новая механика с приёмкой | `FeatureManifest`: сценарии, инварианты, метрики, виды, бюджеты, чек-лист |
| новое видимое (эффект, тело, траектория) | оверлей и ID в `capture.bundle` |
| новый способ воздействия (клавиша, ручка, режим) | команда для `command.send` с записью в реплей |
| новая трасса или отладочный вывод | канал для `trace.read`, а не `Console.WriteLine` |
| новая подсистема | участник `IStateContributor`, её инварианты; если её будут оптимизировать — API, допускающий дифференциальный прогон |
| для отладки пришлось писать временный скрипт, лог или выписывать числа руками | сигнал, что инструмента не хватает: превратить это в инструмент, вид или инвариант |

- **Сначала расширять существующее** — `Describe`, инвариант, сценарий, оверлей, условие. Новый инструмент MCP —
  только если существующие не покрывают задачу; у него схема ответа, лимиты, тест и строка в `docs/agent-playbook.md`.
- **Итог анализа записывается всегда**, даже если ничего не понадобилось: в md фичи или модуля — раздел «Агентский
  доступ» (что агент видит и чем, что добавлено); в отчёте о приёмке — «инструменты агента: добавлены …» или
  «не требуются: …, потому что …».
- **Устаревшие инструменты удаляются** вместе с кодом, который они обслуживали.

## README engine/Sword.Engine.Agent

## Агентский доступ

ИИ-агент (Claude Code, Codex, любой MCP-клиент) подключается к SWORD как к серверу MCP: двигает время, читает мир,
отправляет команды, снимает кадр, разбирает устройство тика, принимает фичи. Две точки входа:

- `Sword.Headless --agent` — симуляция без окна, MCP на stdio: клиент сам запускает процесс
  (`tools/scripts/agent-headless.cmd` собирает Headless в новый каталог `artifacts/agent-bin/headless/<запуск>` —
  работающий агент не держит ни обычный `bin/` (`dotnet build` не падает), ни каталог следующего сеанса; сборка не
  удалась — отказ, старая сборка не запускается (агент не проверяет не тот код); каталоги закончившихся сеансов
  убираются; `.mcp.json` → `sword-headless`). Стартует на паузе, время двигает агент.
- `Sword.exe --agent [--agent-port N]` — живая игра, MCP по HTTP на `http://127.0.0.1:47813/mcp`
  (`.mcp.json` → `sword-app`). Игра идёт как обычно; агент ставит паузу, шаги, команды и снимает кадр.

Код: `engine/Sword.Engine.Introspection/` (точка обслуживания, время, разбор полей, каталог имён, запросы, карта
архитектуры), `engine/Sword.Engine.Agent/` (хост: сеанс, инструменты, квитанции, MCP, транспорты, цикл Headless),
`engine/Sword.Engine.Agent.Client/` (агент в кадре клиента, `capture.bundle`, `render.graph`),
`game/Sword.Game.Agent/` (имена сущностей игры, инструменты игры; `physics.bodies {trace, events}`: трасса физики —
диагностический режим `physics.trace` через `ServiceContext`), композиция — `AgentMode.cs` в `Game.Headless` и `Game.App` (в
сборке `-p:WithoutAgent=true` их нет). Рецепты для агентов — [docs/agent-playbook.md](../../docs/agent-playbook.md). История
(подробные протокол и транспорты, полный список проверок) — [docs/history/engine-agent.md](../../docs/history/engine-agent.md).

### Устройство (раздел 8 плана)

- **Потоковая модель.** Протокол — на своём потоке; к миру он не прикасается. Запрос к миру ставится в очередь
  (`ServiceQueue`) и исполняется на потоке симуляции в **точке обслуживания**: Headless — после каждого тика и на паузе
  (`SimulationLoop`), App — раз в кадр после тиков кадра, и на паузе, и при свёрнутом окне, и пока тянут рамку
  (`ClientAgent.Serve` через `IClientTool`). В точке данные только копируются (`WorldReader.Copy`); разбор в JSON — на
  потоке агента (пакет наблюдения пишет поток кадра на границе кадра). Бюджет точки: 50 мс на тик (Headless), 4 мс на кадр
  (App). Запрос, которого не дождались (таймаут, отмена), не исполняется вовсе.
- **Время.** `TimeControl`: пауза, запас шагов (`time.step`), цель (`time.runUntil`), ожидание тика; решение «пауза ли и
  сколько тиков» — атомарно (`Gate`). Клиент спрашивает ворота тиков (`ITickGate`): на паузе часы стоят, кадр показывает
  ровно последний тик (доля тика 1), шаги — не больше `sim.maxTicksPerFrame` за кадр; после каждого тика кадра —
  `ITickGate.StopAfterTick` (пауза и условие встают на своём тике). Снятие паузы сбрасывает запас шагов. Свёрнутое окно
  обслуживается, но тиков не играет — `time.step` ждёт, пока окно развернут.
- **Команды.** Только на будущий тик и не дальше 1 000 000 тиков вперёд — весь диапазон `repeat`
  (`Simulation.EnqueueRaw`, байты по полям — `FieldCodec`: дробное в целое поле, неизвестное поле, необъявленное значение
  перечисления или бит `[Flags]` — ошибка с путём поля). Команды инструмента выдаются после команд клиента того же типа:
  в живой игре агент перебивает ввод клавиатуры того же тика. `repeat` — одной постановкой (`TickCommands`).
- **Квитанция в каждом ответе:** `buildId` (exe, версия с коммитом, MVID), `contentHash` (оглавление пака), `sessionId`,
  `tickId` (сыграно тиков; посреди тика — номер идущего), `stage` (стадия останова `time.break`, иначе null), `frameId` (кадр
  клиента; у ответа о мире — из точки обслуживания, `ServiceContext.Point`), `complete`, `truncated`, `continuationToken`
  (`skip=N`, `after=N`), `artifactId`. `world.query` с `take` 0 — только число, без продолжения; пути `fields` проверяются по
  схеме полей до запроса. `ecs.explainSystem` связывает `Changed<T>` с `Set<T>` и, как возможного производителя, с `Add<T>`;
  когда связь видна (`when`, `why`) — по стадии и виду записи (прямая запись колонки — системе позже по порядку; команды — на
  барьере после стадии производителя). `render.graph` — граф, размер, `frameId` и `tickId` одного показанного кадра, GPU-время
  проходов (`passes[].gpuMs`, `gpu`: кадр данных — показанный минус `lagFrames`, обычно 3); у `capture.bundle` — `gpu` кадра снимка.
- **Артефакты** — `artifacts/agent/<сеанс>/` в корне репозитория: `capture-<кадр>-<метка>.color.png`, `.depth.png`,
  `.bundle.json`; записи сеанса, отчёты, файлы больших ответов.
- **Протокол** — свой минимальный JSON-RPC по спецификации MCP (официальный SDK тянет хостинг и внедрение зависимостей в exe
  игры): `initialize` (версии 2025-11-25, 2025-06-18, 2025-03-26, 2024-11-05; незнакомая — последняя своя), `ping`,
  `tools/list`, `tools/call`, уведомления `initialized` и `cancelled` (отменённый вызов — без ответа, в пределах своего сеанса;
  отмена, обогнавшая свой запрос, помнится 10 с), пакеты. Ответ — на каждый запрос (внутренняя ошибка — -32603); `id` —
  строка или число (null — -32600); повтор ключа — не JSON (-32700); `jsonrpc` — ровно `"2.0"` (иначе -32600 с `id: null`);
  `params`/`arguments` — объект или ничего (иначе -32602). Аргументы проверяются до действия: неизвестный, явный `null`,
  пропущенный обязательный — ошибка. Ошибка инструмента — результат с `isError` и квитанцией; ответ — `structuredContent` и
  тот же JSON текстом.
- **Транспорты.** stdio — сообщение на строку; конец входа — вызовы, не закончившиеся за 2 с, отменяются, не ответившие на
  отмену ещё за 2 с — бросаются (`StdioTransport.CancelGrace`). HTTP (Streamable HTTP без потока событий, свой HTTP/1.1 на
  `TcpListener`, только 127.0.0.1): `POST /mcp` с `Content-Type: application/json` (иначе 415); уведомление и ответ клиента →
  202, `GET`/`HEAD` → 405, чужой `Origin` → 403, неизвестная `MCP-Protocol-Version` → 400, `Expect: 100-continue` → 100;
  сеанс — `Mcp-Session-Id` на успешный `initialize`, DELETE завершает его и отменяет его вызовы, завершённый или незнакомый
  номер → 404, запрос без номера — разовый, сеансов не больше 64; испорченный запрос → 400; простой соединения 2 мин, чтение
  запроса ≤ 30 с, исполнение вызова ≤ 35 с (`timeoutSeconds` у `time.*` и `capture.bundle` в живой игре — не больше 30 с,
  `HttpTransport.MaxWait`; Headless — 600 с). Закрытие окна отменяет ожидающие запросы и ожидания тиков.
- **Время жизни сервера stdio.** Клиент держит сервер, пока открыт его сеанс (Claude Code — до выхода из
  приложения), а сервер загружает ~850 МБ. Поэтому `Sword.Headless --agent` выходит сам: конец stdin; конец родителя
  (`ProcessLifetime.WhenParentExited`); простой без вызовов инструментов (`McpServer.IdleFor`, `--idle-exit МИН`, по умолчанию
  15, 0 — не выходить); `session.stop`. Выход — с реплеем сеанса в артефакты; не вышел за 20 с — сторож. Следующий вызов
  клиент исполняет на новом сервере (сеанс с тика 0, другой `sessionId`; реплей прежнего — `artifacts/agent/<прежний
  сеанс>/session-*.swreplay`). Дочерние процессы инструментов — в задании Windows `KillOnCloseJob.Shared`. За чем следит сервер
  — строка старта, причина выхода — строка `выход: …` в stderr.

### Ограничения

- Минимизатора (`replay.minimize`) и дифференциального прогона нет (раздел 8, «По этапам»). Причинность — только в
  кольце журнала (65 536 записей): старше — вытеснено (`complete: false` со словами); `replay.observe` с причинностью не
  сделан. Ветки `experiment.fork` — потоки одного процесса (симуляции независимы, общие только неизменяемые ассеты); время
  веток мерится параллельно — для замеров `experiment.sweep` (по очереди).
- Живая игра реплей только пишет: `session.start`, `time.seek` (в обе стороны) и `replay.check` — только Headless.
- Останов посреди тика (`time.break`) — только Headless: в живой игре тик идёт внутри кадра рендера, а кадр не ждёт
  агента. Условие `time.runUntil` в живой игре встаёт на своём тике (кадр прерывает тики), но между тиками.
- `capture.bundle`: цвет, глубина (8 бит, ближе — светлее, растянуто на диапазон кадра), бойцы с рамками и именами,
  камера, `paused` и `alpha` (доля тика кадра); по заказу — ID-буфер (`ids`: сущность и сегмент тела на пиксель, легенда
  словами) и оверлеи игры слоем поверх цвета (`overlays`: у арены — `capsules`, `blades`, `joints`, `contacts`, `mm`; пустой слой —
  заметка игры в `notes`). Нет нормалей и векторов движения. Кадр на ходу — интерполяция между тиками (`alpha` < 1):
  точное состояние — на паузе (`alpha` 1).
- Виды `feature.verify` снимает Sword.exe той же конфигурации сборки, что Headless (`game/Sword.Game.App/bin/<Debug|Release>`);
  сборка Headless в свой каталог (`agent-headless.cmd`) App рядом не видит — виды проваливаются с причиной (`views: false`).
- Бюджет точки обслуживания в App соблюдается между запросами, не внутри: один тяжёлый запрос может удлинить кадр;
  `capture.bundle` (ожидание GPU и PNG) исполняется на границе кадра и удлиняет свой кадр — он служебный. Кадр с запросами
  агента — служебный и для профайлера («кадр инструментов», фича [«Профайлер»](../../game/Sword.Game/Features/Profiler/README.md)).
- `--bench` и `--agent` вместе не задаются: пауза и снимки агента исказили бы замер.

### Решения и почему

- Свой минимальный JSON-RPC вместо официального SDK MCP: SDK тянет хостинг и внедрение зависимостей в exe игры.
- Свой HTTP/1.1 на `TcpListener`: http.sys без прав администратора резервирует не всякий адрес.
- Мир — только в точке обслуживания, изменения — только командами на будущий тик: агент не ломает детерминизм и реплей.
- Headless под агентом выходит сам: клиенты держат stdio-сервер часами, а он загружает ~850 МБ.
- Новый инструмент — только если существующие не покрывают задачу (раздел 8): отдельных `profile.anomalies` и `gpu.passes`
  нет — расширены `profile.stages`, `render.graph`, `capture.bundle`.

## Sword.Engine.Introspection — правила

Общая основа агента и (позже) DevTools, без протокола: точка обслуживания (`ServiceQueue`, `ServiceContext`),
управление временем (`TimeControl`), разбор данных по полям (`FieldCodec`), имена данных мира (`Catalog`), запросы к
миру (`WorldQuery`), карта архитектуры (`ArchitectureMap`), имена сущностей игры (`IEntityNames`). Раздел 8 плана.

- К миру — только в точке обслуживания, на потоке симуляции, между тиками: запрос копирует данные
  (`WorldReader.Copy`) и может поставить команду на будущий тик (`ServiceContext.Enqueue`). Разбор и JSON — на потоке
  агента. Сохранять `ServiceContext` нельзя.
- Имена данных — стабильные (полное имя типа); короткое имя — удобство, неоднозначное — ошибка с перечнем.
- `FieldCodec` разбирает значение через упакованную копию (раскладку считает среда): поля в порядке объявления,
  автосвойство — именем свойства, `Entity` — `12v3`, нечисла — строками, перечисление — точным именем (не «A,B»)
  или объявленным числом; `[Flags]` — списком «A, C» или числом только из объявленных битов. Необъявленное значение
  из мира разбор показывает числом (записать его обратно нельзя — намеренно: запись только объявленных значений).
  float вне диапазона float — ошибка, а не бесконечность (бесконечность — только явной строкой `Infinity`). Ключ ручки
  (`Runtime.TuningKey`, 6е) — именем ручки «секция.ключ» (без учёта регистра; незаведённое имя — ошибка с перечнем ручек процесса;
  число — как есть), схема — перечень ручек. Ручки симуляции — `Catalog.Tuning` (`new Catalog(simulation)`): `world.types` показывает их у
  ресурса и у `TuningCommand`.
  `[InlineArray]` и `fixed`-буфер — массив всех элементов. Путь поля проекции — `FieldCodec.CheckPath` до запроса.
- `TimeControl.Stop` — конец симуляции: ожидания отменяются, новое ожидание недостигнутого тика сразу отменено.
  Headless зовёт его в конце `SimulationLoop.Run`, живая игра — при закрытии окна (вместе с `ServiceQueue.CancelAll`).
- Связи карты архитектуры — те же, что производители срабатываний в ECS (`Registration.Produces`): `Changed` даёт
  `Set`; `Add` — возможный производитель (при отключённых проверках ошибочный `Add` существующего тоже даёт `Changed`;
  штатно он запрещён).
- Произвольного кода нет: только копии и разбор.
- Язык условий (этап 3в) — `ObservationPredicate`: JSON-дерево из белого списка узлов (`Syntax`), компилируется в точке
  обслуживания (имена сущностей разрешаются один раз) в узлы, читающие листья полей по `FieldLayout`; три области —
  мир, сущность, запись журнала. Условие на сущность наверху — «есть такая сущность»; `for` — только в условии мира,
  его серия обновляется в `Evaluate` до корня (у всех окон, изнутри наружу): `all`/`any` не пропускают окно.
  Собранный в памяти JSON проходит через текст (int читается как число). Ошибка — `ArgumentException` с путём в условии.
- `ObservationHistory` — кольцо тиков с записями журналов, снятыми после тика по возрасту записей (1…число стадий) без
  своего курсора: мир и хеш от неё не зависят; событие без потребителя журнала не имеет и не видно. `ObservationHub`
  (наблюдатель `ISimulationObserver`) — история, наблюдения `Watch`, одно условие остановки: после тика или после
  барьера стадии (`BreakHandler` хозяина цикла — только Headless); попадание — `TimeControl.Halt` на этом тике.
  `Attach` к новой симуляции очищает историю, перепривязывает наблюдения, снимает условие. Поле наблюдения может быть
  вычисляемым полем игры (`ObservationHub.Fields` — `IEntityFields`, 5г): лист `F64` с компонентом −1, NaN — нет значения.
  7з: и поле условия — `ObservationPredicate.Compile(…, fields)`: путь, который не начинается с имени компонента мира и который
  понимают поля игры, — вычисляемое поле (узел `ComputedFieldNode`, сравнения чисел; NaN — нет значения: `isNaN`, `notEquals` выполнены, прочие — нет). Поля
  передают проверки манифеста (`FeatureEnvironment.Fields`), `time.runUntil` (`AgentHost.Fields`) и `replay.observe`.
- `WorldSnapshot` — копии байтов в точке обслуживания, плоский вид (`12v3/Transform/Position.X`) — на потоке агента;
  `SnapshotDiff` — по ключам, числа с разницей и допуском. `ReplayObservation` — прогон реплея с наблюдением (события,
  наблюдение, условие; нарушения инвариантов — сводка и строки `InvariantViolation`) в отдельной симуляции.
- Инварианты (этап 3г): нарушения тика узел получает `OnViolation` (до `AfterStage` барьера) и кладёт в историю
  (`AddViolation` → слот тика в `Capture`; посреди тика — `Pending`). Остановка на нарушении — `ArmInvariant` (то же
  одно условие остановки): с `BreakHandler` — посреди тика после нарушившего барьера, без него — после тика.
  `AgentInvariant` — инвариант агента условием (`condition` мира или `must` на каждую сущность под `where`), владелец
  `agent`; узел хранит определения и включения (`SetInvariantEnabled`) и переносит их в новую симуляцию в `Attach`.
  `ServiceContext.Invariants` — реестр симуляции в точке обслуживания. 7и: `ServiceContext.Diagnostics` и методы `HasDiagnostic`,
  `DiagnosticEnabled`, `SetDiagnostic`, `ResetDiagnosticWindow` — диагностические режимы симуляции (трасса физики игры) из точки
  обслуживания: мир, хеш и реплей от них не зависят; методы — инструментам игры без типов Runtime.
- Приёмка фич (этап 3д): `FeatureManifest` — `feature.json` рядом с md фичи, разбор строгий (неизвестный ключ, тип,
  ссылка на несуществующий сценарий — `InvalidDataException` с путём); `FeatureVerifier.Verify` — сценарии (реплей из
  репозитория или команды по тикам на конфиге из кода, всегда с записью) в отдельных симуляциях построителя
  `FeatureEnvironment.Build`: проверки — условия `ObservationPredicate` после каждого тика (`always`, `never`,
  `eventually`, `atEnd`; 7з — и по вычисляемым полям игры), хеши реплея, нарушения любых включённых инвариантов — провал; инварианты
  манифеста включаются явно; 7з — ключ сценария `diagnostics`: диагностические режимы симуляции (`physics.trace`) включаются до тика 0
  в каждой симуляции сценария (Id — по правилу инварианта; режима нет — провал словами), их читают инварианты манифеста; метрики — `FieldProbe` (поле сущности, несколько листьев — длина вектора; путь, который понимают вычисляемые поля
  игры `IEntityFields` — `FeatureEnvironment.Fields`, `AgentHost.Fields`, 5б: тела бойца вне ECS, — читают они) после тика
  или статистика окна — всегда своё число SWORD2 (7а, решение 14: источник `sword` и ряды против трассы SWORD — ключи `source`,
  `trace`, `series` — сняты, такой ключ — ошибка разбора); 6ж — поле ресурса мира (`resource` вместо `entity`/`field`:
  `FieldProbe.OfResource`, путь — как у условия `{resource:…}`); бюджеты — отдельные прогоны без инвариантов, записи и сверки хешей (`Replay.Head(…,
  hashes: false)`), медиана повторов `SimulationMeasure` (мс на тик, мс стадий `StageTimer`, байты на тик), время — только
  при `Optimized`; кадр App (`budgets[].frame`, точка 4д) — делегат exe `MeasureFrame` над записью сценария (бенч,
  хеши App сверяются; 5г: `frame.overlays` — оверлеи игры на весь замер, разбор — как у видов), пределы — только при
  `Optimized`, без видов не меряется; виды — делегат exe `CaptureView` над
  записью сценария (5в: `views[].overlays` — отладочные оверлеи игры поверх кадра, строгий разбор имён, App — `--overlay`). Вердикт — список провалов словами, отчёт — `report.json`.
- Эксперименты (этап 3д) — `Experiments`: `Fork` (база и ветки параллельно, каждая — своя симуляция; сравнение записей
  `ReplayDiff`), `Compare` (и листья описаний разошедшихся участников на первом разошедшемся хеше), `Sweep` (круг прогрева —
  каждая комбинация по разу без замера, затем повторы по кругу комбинаций: JIT свежего процесса, 4д; детерминизм
  итогового хеша, первое резкое ухудшение масштабирования; реплей — без сверки хешей, как бюджеты). 6ж: перед повторами перебора и
  бюджета — прогрев до затишья JIT (`Diagnostics.JitWarmup`: сценарий без замера, ≤ 1 с; бюджет — `jitWarmup` в отчёте). Доводка 6ж:
  только в Release (`FeatureEnvironment.Optimized`; перебор — `Sweep(…, warmJit: true)`, `experiment.sweep` — по сборке сеанса), тёплая
  симуляция одна (у перебора — одна на комбинацию) и идёт дальше конца сценария без постройки заново; в Debug `jitWarmup` бюджета — строка
  «не греется».

- Время систем (этап П, точка Па): `SimulationMeasure.Run(…, profile: true)` — прогон с профайлером CPU, `Systems` — мс
  зон `метка@стадия` на тик после прогрева. Бюджет фичи — после повторов ещё один такой прогон (`budgets[].systems`,
  `budgets[].profiled`; байты — тот же предел), перебор — круг после повторов (`SweepRow.Systems`, `systems: false` —
  без него): медианы и пределы — по-прежнему без профайлера (`StageTimer`).
- Машина (точка Пб): `SimulationMeasure.Machine` — снимки на границах замера (первый тик после прогрева и конец, вне времени
  и байтов тиков), счётный поток (доля CPU — критерий вердикта); бюджет — сумма повторов (`budgets[].machine`, `runs`), перебор —
  `SweepRow.Machine`; прогон с профайлером — `budgets[].profiled.runtime`. Вердикт не меняет пределы: провал времени бюджета
  дописывает его словами (« — машина: …», « — среда: JIT во время замера …»); кадр App — `FrameResult.Machine` из итога
  Sword.exe, так же.

- Причинность (6д) — `CausalityQuery`: в точке обслуживания по журналу причинности мира (`WorldReader.Causality`) — последние
  изменения поля сущности (записи `Add/Set/Remove` компонента; `Set`, не менявший листья поля, пропускается — по значениям до и
  после), цепочка каждого по родителям до корня (`Complete`) или до обрыва со словами (`Stop`: родитель вытеснен, глубже предела),
  регистрации, писавшие столбец на месте (`Writers` — грубо), объявленные производители из плана мира (`Producers` — и без режима).
  Только копии записей и значений; разбор в JSON — на потоке агента (`state.why`, `events.history`). `CausalityQuery.Source` —
  путь от папки репозитория и строка. 8з: `WhyCause` — цепочка записи по её номеру (`cause.id`/`cause.parent` строки `events.history`) до
  корня — `state.why {"cause":N}`: почему случилось событие (переход Motion Matching, попадание).
- Метрики фич, 8з: статистика окна — ещё `p95` (ближайший ранг, как `p99`); ключ `skipUndefined` — тики без значения (NaN вычисляемого
  поля: скольжение опорной стопы без стопы на земле) не входят в окно (в отчёте — `defined`), окно без значений — провал; без ключа NaN в
  окне — провал «значения нет», как раньше. Проверка — `FeatureTests.Verify_Metric_P95_SkipUndefined`.
- 8и: пик зоны профайлера в бюджете — ключ `budgets[].zones` (`{"locomotion.search": 0.25}`, `FeatureBudget.Zones`): наибольшее время зоны за
  тик после прогрева в прогоне бюджета с профайлером (`SimulationMeasure.Zones` — все зоны профайлера замера; кольца нет — среднее, максимум,
  вызовы, доля тиков), в отчёте `budgets[].zones` (пик, среднее, вызовы, доля, родитель, предел); как время — судится только в Release,
  зоны нет в прогоне — провал в любой сборке. Нужен для редкой дорогой работы, которую медиана тика прячет (поиск MM раз в 12 тиков).
  Проверка — `FeatureTests.Verify_Budget_ZonePeak_LimitOnlyInRelease_MissingZoneFails`. `Experiments.Fork(…, fields)` — замер ветки читает и
  вычисляемые поля игры (как метрики; `experiment.fork` передаёт `AgentHost.Fields`): поза ветки — `Body.foot.l.Position`, `MotionMatch.*`;
  проверка — `FeatureTests.Fork_BranchDivergesOnTickAfterChange_ConfigFromStart`.
- Огонь: вид — `views[].tune` (клиентские ручки App `--tune`, «группа.ключ=значение», `light.night=1` — ночь; в реплей не идут), итог App
  `--json` — рядом с PNG (`view-<id>.json`, в отчёте вида — `json`); бюджет кадра — `frame.camera` (`--camera`), `frame.tune`, `frame.gpu`
  (`{"fire": 0.5}`: сумма GPU-времени проходов бенча `report.bench.passes` с именем ключа или «ключ.…»; как время — только в Release, ни
  одного прохода — провал в любой сборке). Проверка — `FeatureTests.Verify_FrameBudget_GpuPassesCameraTune`. Ожидания вида — `views[].expect`
  (`ViewExpectation`): путь в итоге App (`fire.checks.*` — каждый элемент, `fire.metrics[0].flame.heightCm`), `equals` или `min`/`max`; не
  то значение, нет пути, пустое `*`, нет итога App — провал вида словами с путём. Проверка — `FeatureTests.Verify_ViewExpect_ReadsAppJson_FailuresNamePath`.

## docs/agent-playbook.md

## Рецепты для агентов

Как ИИ-агенту (Claude Code, Codex, любой MCP-клиент) запускать, наблюдать и отлаживать SWORD. Устройство агентского
доступа — [engine/Sword.Engine.Agent/README.md](../engine/Sword.Engine.Agent/README.md), правила — раздел 8
[плана](../ARCHITECTURE_PLAN.md). Рецепты — в текущем виде; прежняя редакция с пометками точек и замерами —
[docs/history/playbook.md](history/playbook.md).

### Подключение

- **Claude Code** читает `.mcp.json` в корне: `sword-headless` (stdio: `tools/scripts/agent-headless.cmd` собирает Headless в
  `artifacts/agent-bin/headless/<запуск>` и стартует `Sword.Headless.exe --agent`; сборка не удалась — исправить и переподключить в `/mcp`)
  и `sword-app` (HTTP, `http://127.0.0.1:47813/mcp` — сначала `Sword.exe --agent`, иначе переподключить в `/mcp`). `sword-headless` выходит
  сам после 15 мин без вызовов (`--idle-exit`): следующий вызов идёт на новый сервер (сеанс с тика 0). Виды `feature.verify` сервер снимает
  `Sword.exe` из `game/Sword.Game.App/bin/Debug` (собирает `dotnet build SWORD.slnx`; не собран — «Sword.exe не собран»).
- **Окна `Sword.exe` агентов — без фокуса**: пользователь работает на той же машине. В `.claude/settings.local.json` (вне git)
  задано `"env": {"SWORD_NO_ACTIVATE": "1"}` — запуски `Sword.exe` из Claude Code идут как с `--no-activate` (окно внизу порядка
  перекрытия; журнал — `окно без фокуса: SWORD_NO_ACTIVATE=1`, итог `--json` — `window.activate: false`). Вне Claude Code — запускать
  с `--windowed WxH --no-activate` (замеры — `--windowed 640x480`); `--activate` возвращает фокус.
- **Codex** (`~/.codex/config.toml`):

  ```toml
  [mcp_servers.sword]
  command = "cmd"
  args = ["/c", "D:\\Work\\Visual Studio\\SWORD2\\tools\\scripts\\agent-headless.cmd"]
  ```

- **Любой клиент**: stdio — строка JSON-RPC на сообщение; HTTP — `POST /mcp` с сообщением, ответ `application/json`.

### Порядок

`session.status` → устройство (`ecs.plan`, `architecture.projects`, `module.graph`) → состояние (`world.query`,
`entity.get`, `state.hash`, `state.describe`) → время (`time.step`, `time.runUntil`, `time.seek`) → воздействие (`command.send`) →
проверка состояния → `log.tail`; реплеи — `replay.*`, `session.start`. Каждый ответ несёт квитанцию: `tickId` — сыграно тиков к
моменту ответа, `frameId` — кадр живой игры.

### Рецепты

**Проверить движение игрока (Headless).**
1. `world.types {"name":"PlayerCommand"}` — поля; `command.send {"command":"PlayerCommand","fields":{"Move":{"X":1,"Y":0}},"repeat":120}`
   (команда игрока действует один тик, поэтому `repeat`).
2. `time.step {"ticks":120}`; `entity.get {"entity":"player","components":["Transform","RootVelocity"]}` — x ≈ 3,94, скорость 4,2 м/с.

**Проверить анимацию бойца.**
1. Клипами (враги; игрок — при `locomotion.player=clips`: тесты, сценарии фич, эталоны) —
   `entity.get {"entity":"enemy 1","components":["LegacyLocomotionState","AnimatorMotion"]}`: какой клип играет (номер), время клипа, доля
   кроссфейда; сглаженная скорость и «идёт». Игрок в игре (`sword.json`: `locomotion.player=mm`) — на Motion Matching:
   `entity.get {"entity":"player","components":["MotionMatchState","SteerModel"]}` — клип (номер), кадр в клипе, доля, темп, поисков и смен,
   итог последнего поиска (цена, цена продолжения, 12 групп), модель контроллера тика; база и проигрыватель —
   `state.describe {"part":"locomotion","filter":"base"}` (сводка, отпечаток) и `{"filter":"0v1:foot"}`; ручки —
   `command.send {"command":"TuningCommand","fields":{"Knob":"locomotion.switchGain","Value":1}}`; MM против клипов —
   `experiment.fork` с веткой `{"set":["locomotion.player=clips"]}`; подробно — раздел «Motion Matching игрока».
2. `anim.clips {"index":N}` — имя клипа по номеру (или `{"filter":"Run"}`): длительность, цикл, скорость корневого движения; страницы по 50
   (`skip` из `continuationToken`).
3. `anim.pose {"entity":"player"}` — суставы (таз, голова, кисти, стопы) в пространстве персонажа и в мире; `pool` — живые позы и задания
   последнего тика (`staleLastTick` должен быть 0); у врага — ещё `action` (слой действий).
4. Регрессия — эталоны SWORD2 (`--filter ReferenceReplays`: хеш `animation` каждого тика) и сценарий `locomotion` манифеста `animation`.

**Враги и команды арены.**
1. Headless со `sword.json` стартует с 10 врагами (`arena.enemies`; `--units N` или `--set arena.enemies=N`, 0…32; тесты и сценарии фич
   без `sword.json` — 0). Сколько задано — `ArenaState.Enemies` (`state.describe {"part":"ecs","filter":"resource:"}`); враги —
   `world.query {"with":["EnemyTag"],"fields":["FighterSlot","Transform"]}`; враг по месту — `entity.get {"entity":"enemy 3"}`.
2. PageUp/PageDown/R: `command.send {"command":"ArenaCommand","fields":{"Action":"ChangeEnemies","Enemies":1}}` (`-1` — PageDown),
   `{"Action":"SetEnemies","Enemies":32}`, `{"Action":"Reset"}`; изменения видны после `time.step {"ticks":1}`; команда — в реплее.
3. Места без дыр и число бойцов — инвариант `arena.slots` (`time.breakOnInvariant {"ids":["arena.slots"]}`).
4. Сброс строит бойцов заново на тех же сущностях (`player`, `enemy N` в условиях и `watch.add` его переживают); после PageDown и PageUp
   враг — новая сущность, поэтому место — полем: `{"exists":{"all":[{"component":"EnemyTag"},{"field":"FighterSlot.Index","equals":5},{"field":"Transform.Position.X","greaterThan":0}]}}`.
5. Без агента: `Sword.Headless --ticks N --units 32 --json` — `arena` в итоге (враги по местам, расстояние до игрока, скорость,
   составляющие ИИ); приёмка — `feature.verify {"id":"enemies"}` / `Sword.Headless --feature enemies`.

**ИИ врагов: почему враг идёт туда, куда идёт.**
1. `entity.get {"entity":"enemy 3","components":["EnemyAiTerms","FighterCommand","GazeTarget"]}` — составляющие намерения тика:
   `Distance`, `ApproachSpeed` (> 0 — подходит; ноль на 1,8 м, предел −2…3,2), `SwaySpeed` (±0,7), `Separation` и `Neighbours` (соседи
   ближе 1,4 м); `FighterCommand` — итог, `GazeTarget` — корень игрока.
2. Как менялось: `watch.add {"entities":["enemy 3"],"fields":["EnemyAiTerms","FighterCommand","Transform"]}` → `time.step` →
   `entity.history {"entity":"enemy 3","changes":true}`.
3. Когда подошли все: `time.runUntil {"condition":{"none":{"all":[{"component":"EnemyTag"},{"field":"EnemyAiTerms.Distance","greaterThan":2.5}]}},"maxTicks":1200}`;
   сводка — `world.query {"with":["EnemyTag"],"aggregate":["EnemyAiTerms.Distance","EnemyAiTerms.Neighbours"],"take":0}`.
4. Намерение считается по корням до движения тика: посреди тика — `time.break {"stage":"Intent"}` и `entity.get`. Время арены —
   `{"resource":"SimTime.Time"}`. Свойства ИИ — `dotnet test tests/Sword.Game.Tests --filter EnemyAi`.

**Столкновения бойцов: кто кого толкнул и где перекрытие.**
1. `entity.get {"entity":"enemy 3","components":["RootContacts","Transform","RootVelocity"]}`: `Contacts`, `Push` (сдвиг корня парами),
   `FromPlayer`, `Deepest` и `DeepestWith` (место; 0 — игрок, −1 — касаний нет), `Obstacle` (сдвиг колоннами и краем арены). Толчок игрока
   парами — `−Σ FromPlayer`: `world.query {"with":["EnemyTag"],"aggregate":["RootContacts.FromPlayer.X","RootContacts.FromPlayer.Z"],"take":0}`.
2. «Когда игрок толкнул врага»: `time.runUntil {"condition":{"exists":{"all":[{"component":"EnemyTag"},{"field":"RootContacts.DeepestWith","equals":0}]}},"maxTicks":600}`;
   кого — `world.query {"with":["EnemyTag"],"where":{"field":"RootContacts.DeepestWith","equals":0},"fields":["RootContacts","FighterSlot"]}`.

Метрика по ресурсу мира: `{"id": …, "resource": "ArenaStats.LastDamage", "expected": 60.8, "tolerance": 0.001}` вместо `entity`/`field`.
Статистика окна метрики (`stat` с `from`/`to`) — `min`, `max`, `mean`, `p95`, `p99` (95-й и 99-й перцентили ближайшим рангом — распределение
без одиночных выбросов `max`); потолок «не больше L» — `expected` = `tolerance` = L/2. Величина, определённая не в каждом тике (NaN:
скольжение опорной стопы без стопы на земле), — `"skipUndefined": true`: такие тики не входят в окно (в отчёте — `defined`), окно без
значений — провал; без ключа NaN в окне — провал «значения нет».
Редкая дорогая работа (поиск MM раз в 12 тиков), которую медиана тика прячет, — пик зоны профайлера в бюджете: `"zones": {"locomotion.search":
0.25}` — наибольшее время зоны за тик в прогоне бюджета с профайлером, мс; в отчёте `budgets[].zones` (пик, среднее, вызовы, доля тиков);
судится в Release.

(`поворот,наклон,дистанция[,x,z]`, как у вида). GPU-бюджет клиентского модуля — `frame.gpu`: `{"fire": 0.5}` — сумма GPU-времени проходов
бенча `fire` и `fire.…`, мс на кадр (судится в Release; ни одного прохода — провал в любой сборке). Итог App `--json` вида — рядом с PNG,
`view-<id>.json` (числа модулей на кадре вида, например `fire.metrics`).

**Эксперимент «что если».**
1. `experiment.fork {"replay":"my.swreplay","at":300,"variants":[{"name":"back","commands":[{"command":"PlayerCommand","fields":{"Move":{"X":-1,"Y":0}},"from":300,"to":301}]},{"name":"nolo","set":["modules.locomotion.enabled=false"]}],"measure":[{"entity":"player","field":"Transform.Position"}]}`
   — база и ветки параллельно; `vsBase.firstHashTick` (команда тика T — это T+1; ключ конфига — с тика 0), `measure`, `file` — запись
   ветки; `cut: true` — команды реплея после развилки не идут. `measure` читает и вычисляемые поля игры (`Body.foot.l.Position.X`,
   `MotionMatch.JointJump`); по тикам — `replay.observe` по `file` веток.
2. `experiment.compare {"a":<file базы>,"b":<file ветки>}` — заголовки и конфиг, первый тик с разными командами, первый хеш с разными
   участниками, листья описаний (`путь`, `a`, `b`).
3. `experiment.sweep {"params":{"arena.enemies":[0,8,16,32]},"replay":"<артефакты enemies>/scenario-crowd.swreplay","repeats":7}` — по
   комбинации мс на тик (медиана, разброс), стадии, байты, `deterministic`, `scaling`; время — в Release; сначала каждая комбинация по разу
   без замера (прогрев JIT), смотреть медиану; сеанс агента меряет с инвариантами (`sim.invariants=false` в `params` — как бюджет);
   `rows[].systems` — мс систем (профайлер), `rows[].machine` — вердикт машины («Код или машина»).

**Где время кадра или тика (профайлер CPU).** Выключен по умолчанию; включённый не меняет симуляцию и не выделяет памяти.
1. `profile.stages {"enable":true,"reset":true}` — включить и забыть прошлое (App — со следующего кадра).
2. Дать поработать (Headless — `time.step {"ticks":600}`; App — секунды игры); первые сотни тиков свежего процесса — неоптимизированный
   JIT: после них ещё раз `reset` или смотреть медиану.
3. `profile.stages {"top":30}` — зоны за кадр (App) или тик (Headless; `per`): `meanMs`/`medianMs`/`p99Ms`/`maxMs`, `selfMs`, `bytes`,
   `calls`, `presence`, `parent`. Имена: `frame.*` (`frame.simulate`, `frame.render`, `frame.fenceWait`, `frame.build`, `frame.record`,
   `frame.present`), `tick`, `stage.<стадия>`, `<метка>@<стадия>` — система, `barrier.<стадия>`, `invariant.<id>`, `sim.record`,
   `sim.observers`, `render.<проход>`, `arena.*`, `physics.*` (внутри шага физики); узко — `prefix`; по кадрам — `history`.
4. В файл — `profile.stages {"write":true}` → `profile.json`; выключить — `enable:false`. Без агента: `Sword.exe --profile` /
   `Sword.Headless --ticks 600 --units 32 --profile` → `artifacts/profile/<прогон>/profile.json`. Бюджеты — `budgets[].systems`, `profiled`.
5. Байты: `bytes` зоны — выделения потока владельца (спускаться от `frame` по зонам с `bytes` > 0); чужие потоки и время между кадрами зоны
   не видят. Среда: `runtime` — `cpuMs`/`wallMs`, `gc`, `jit` (`mainThread` — пауза кадра), `processBytes`; по периодам — `history`.
6. Что именно — `profile.stages {"events":true}` (дороже, для расследования) → `events`: `alloc.types`, `jit` (`tier0`/`tier1`/`osr`…),
   `gc`, `recent`; выключить — `{"events":false}`; без агента — `--profile runtime`. Стеки — `dotnet-trace collect -p <pid>` / PerfView.

**Код или машина.** Бюджет или бенч упал — сначала вердикт, потом код (пользователь иногда нагружает машину).
1. Где: `feature.verify` → `budgets[].machine`, `budgets[].frame.machine`; `experiment.sweep` → `rows[].machine`; `Sword.Headless --json` →
   `machine`; `Sword.exe --json` → `report.machine`; `profile.stages` → `machine`; журнал — `[bench] вердикт: …`.
2. `verdict`: `машина` — другие процессы заняли ≥ 25 % логических процессоров (`othersBusyPct`), или счётный поток был на CPU < 90 %
   (`threadOnCpuPct`), или частота ядра ниже 90 % базовой (`mhz.probe`, Release), или ОС ограничила частоту (`mhz.limit` < `mhz.limitBase`);
   `среда` — JIT на главном потоке или GC во время замера; `код` — время за код. Фоновый JIT — причина, вердикт не меняет.
3. Замер — один прогон: сомнительный результат (`машина`, провал предела, число у предела) не перемерять, а сообщить пользователю числа;
   предел бюджета не трогать. `среда` с JIT на главном потоке — разовая компиляция в замере (какая — аномалия тика); `код` → профайлер.
   `note` в `machine` — окно короче 0,5 с: загрузка по счётчикам ОС грубая (короче 0,1 с — в вердикт не идёт).

**Почему был медленный кадр или тик (захват аномалий).**
1. Включённый профайлер ловит сам: кадр дольше `медиана + max(2 мс, 0.75·медиана)`, тик — `медиана + max(1 мс, 0.75·медиана)` (медиана —
   128 последних); свой порог — `profile.stages {"threshold": 5}` (`0` — снова по медиане) или `--profile-threshold 5`; у Sword.exe — F2.
2. Где: `log.tail {"category":"profile"}`; `profile.stages {"anomalies": 20}` → `anomalies.list` (`ms`, `class`, `causes`, `zone`, `file`,
   `noticeable`), `byClass`. **Видел ли человек** — `noticeable` (кадр не короче интервала показа монитора): жалоба «дёрнулось» — сначала
   заметные. Кадр инструментов (`history[].tools` — агент выполнял запросы) не судится: мерить игру — между вызовами.
3. Класс: `jit` — компиляция на главном потоке (OSR долгого цикла → тело цикла в свой метод, `AGENTS.md` Runtime; все компиляции —
   `DOTNET_JitDisasmSummary=1 DOTNET_JitStdOutFile=<файл>`); `gc` — пауза сборки; `gpu` — `frame.fenceWait`/`frame.present` (секция `gpu`
   файла называет проходы); `machine` — поток сняли с процессора (сообщить пользователю, код не трогать); `code` — смотреть `mainZone`.
   «Главной зоны нет» (`zone: null`) — абсолютный порог ниже обычного периода.
4. Файл `anomaly-<frame|tick>-N.json`: `mainZone.path`, `zones`, `tree`, `header`, `recent` (32 периода до), `tick`, `events`
   (диагностический режим), `machine`. Картинкой — `trace` файла или `profile.stages {"trace":true}` / `--profile-trace` → https://ui.perfetto.dev.
5. Проверить исправление: тот же прогон — аномалии класса и зоны пропали, p99 ниже.

**Упор в CPU или GPU (GPU-время проходов).** GPU-время — всегда, без профайлера.
1. Бенч — `Sword.exe --units 32 --bench 10 --json` → `report.bench`: `averageMs`, `cpuMs`, `waitMs`, `gpuMs`/`gpuP99Ms`, `passes`; живая
   игра — `render.graph` (`passes[].gpuMs`, `gpu.frameMs`) или `profile.stages` → `gpu`.
2. **GPU** — `gpuMs` ≈ кадр, `waitMs` большие: смотреть проходы; **CPU** — `cpuMs` ≈ кадр, `waitMs` ≈ 0: зоны CPU; p99 ≈ `gpuP99Ms` —
   рывки GPU. GPU-время в кадре N — кадра N − 3 (`lagFrames`; у `capture.bundle` и `--json` — 0); сравнивать прогоны одной машины подряд.

**Понять, почему поле такое.** Режим причинности: `session.start {"causality":true}` (или сервер с `--causality`; хеш и реплей не меняет),
воспроизвести → `state.why {"entity":"player","field":"Health.Hp"}`: последнее изменение (тик, `Set`/`Add`/`Remove`, система, `source`,
`before`/`after`) и `chain` до корня (попадание ← касание ← начало удара ← решение ИИ или команда); `summary` — строкой; смерть —
`{"field":"Dead"}`; `changes: N`; `events.history` в режиме даёт `cause`. Непрерывное поле (`Transform`) — `writers`, дальше
`ecs.componentUsage`, `ecs.explainSystem`, `watch.add`, `time.break`. `complete: false` — родитель вытеснен из кольца: смотреть ближе.
Почему случилось событие (переход Motion Matching, попадание) — `state.why {"cause":N}`: `N` — `cause.id` (или `cause.parent`) строки
`events.history` в режиме; цепочка записи до корня, `summary`.

**Посмотреть на кадр живой игры.** `time.pause` (кадр показывает ровно последний тик) → `capture.bundle {"name":"look"}` → `color` и
`depth`; `entities[].rect` — где кто. `render.graph` — проходы кадра и их GPU-время.

**ID-буфер и оверлей капсул.** Чья часть на пикселе, стоят ли капсулы на персонаже: `time.pause` → `capture.bundle
{"name":"ids","ids":true,"overlays":["capsules"]}`.
- `ids.png` — ID-буфер для глаз; `ids.raw` — коды (uint32 на пиксель, строки сверху вниз); `ids.legend` — `entity`, `name`, `segment`,
  `title` («левое предплечье врага 3», «голова трупа врага 1»), `pixels`, `rect`. Код = (номер сущности + 1) << 8 | сегмент; 0 — ничего.
- `overlays.capsules` — снимок с капсулами тел и подписями бойцов; `color` — без них. Пусто в легенде у видимого бойца — ошибка рендера;
  `notes` — что заказано, но не снято. Капсулы оверлея — «как показан боец»: сверять числа с `physics.bodies` — на паузе (`alpha` 1). В
  видах фичи — `views[].overlays: ["capsules"]` (`Sword.exe --overlay capsules`).

**Длинный прогон и страницы.** `time.runUntil {"tick":N,"timeoutSeconds":120}` (в живой игре — не больше 30; таймаут не отменяет прогон,
`time.pause` останавливает). `world.query` — не больше 100 сущностей: `receipt.truncated` и `continuationToken` (`skip=N`); `log.tail`
без `after` — последние записи по фильтру (`level`, `category`), дальше — `after` = `last`.

### Рэгдолл

Фича [«Рэгдолл»](../game/Sword.Game/Features/Ragdoll/README.md), физика — [README](../engine/Sword.Engine.Physics/README.md) подсистемы.

**Команды сцен и привязка скина.** `SceneCommand` (Intent того же тика; в реплее):
1. Поставить бойца места в точку курсом (постройка заново, мёртвый оживает): `command.send {"command":"SceneCommand",
   "fields":{"Action":"Place","Slot":1,"Position":{"X":-13,"Y":0},"Facing":1.5708}}` (`Position.Y` — это z).
2. Убить без удара: `{"Action":"Kill","Slot":1}` → `entity.get {"entity":"enemy 1","components":["Dead"]}` — `Cause: Command`, `Time`.
3. Сдвинуть тела трупа без скорости (тиком позже смерти) — `{"Action":"ShiftBodies","Slot":2,"Offset":{"X":0.2,"Y":0,"Z":0}}`; меч места —
   `{"Action":"Weapon","Slot":3,"Weapon":0}`; намерение игрока — `{"Action":"PlayerIntent","Velocity":{"X":0,"Y":4.2},"Facing":0}`, `"repeat":360`.
4. Привязка скина мёртвого — `physics.bodies {"entity":"enemy 1"}` → `skin`: `captured`, `time`, `joints`, `drift` (насколько скин ушёл от
   позы смерти); матрицы — `state.describe {"part":"skin"}`; нет привязки — нарушение `ragdoll.skin`.

**Труп на экране и трасса физики.**
1. Скин и тела: `physics.bodies {"entity":"enemy 1"}` — `skin.drift`; картинкой — `capture.bundle {"ids":true,"overlays":["capsules"]}`:
   меш трупа на капсулах, «голова трупа врага 1», рамка трупа — по телам; кресты тел на физике (зелёный — на земле, синий — спит).
2. Суставы: `physics.bodies {"entity":"enemy 1"}` → `joints` (`list`: родитель, ребёнок, `enabled` — у запястья false, `pointError`,
   `excess`; `excessMax`); картинкой — `capture.bundle {"overlays":["joints"]}`. У живых суставов нет (`joints: null`).
3. Трасса — диагностический режим (мир, хеш, реплей не меняет): `physics.bodies {"trace":"on"}` → тики → `physics.bodies
   {"trace":"show","events":16}` — `trace.last`, `trace.window` (с `reset`), `trace.run`: `speed.max` и чьё тело, `speed.p99`,
   `angularSpeed`, `capped`, `nonFinite`, `sources` (`ground`, `wall`, `pair`, `joints`, `push.*`: сдвиг / h, `hidden` — должен быть 0,
   псевдоимпульс, глубины), `energy`, `sleep`, `top` и `recent` (события быстрее 12 м/с). Окно: `{"trace":"reset"}` → тики → `show`;
   выключить — `{"trace":"off"}`. В Headless включённая трасса переживает `session.start` и перемотку.
4. Контакты последнего подшага: трасса включена (п. 3 или K) → `capture.bundle {"overlays":["contacts"]}` (зелёный — земля, синий — стена
   и колонны, пурпурный — пара трупов, жёлтый — части одного трупа, оранжевый/красный — толчок телом/клинком); выключена — слой пуст, в `notes` — почему. Числа —
   `trace.contacts`. `Sword.exe --overlay contacts` включает трассу с первого кадра (и при `--replay`).
5. F3 «Рэгдолл» человеку — агенту те же ручки командой и те же числа: мёртвые — `world.query {"with":["Dead"],"take":0}`, быстрейшее —
   `trace` (`speed.max`, `capped`), покой — `Body.ComVelocity`; вкладки — итог `Sword.exe --json` (`panels.tuning`).

**Труп на физике.**
1. Переход: `command.send {"command":"SceneCommand","fields":{"Action":"Kill","Slot":1}}` → `time.step 1` → `physics.bodies
   {"entity":"enemy 1"}` — у 14 тел `mode: simulated`, `profile: 1`, `joints` — 13, у запястья `enabled: false`; смерть от удара — так же
   (переход — в Settle). Системы — `ecs.explainSystem {"name":"core.death-to-ragdoll"}`.
2. «Играть, пока труп не ляжет»: `time.runUntil {"condition":{"all":[{"entity":"enemy 1"},{"component":"Dead"},{"field":"Body.KineticEnergy","lessThan":0.05}]},"maxTicks":1200}`.
   По тикам — `watch.add {"entities":["enemy 1"],"fields":["Body.ComVelocity","Body.KineticEnergy","Body.Energy","Body.Com.Y"]}` →
   `entity.history` (труп лёг: `Body.ComVelocity` ≤ 0,05 м/с, `Body.KineticEnergy` — сотые доли джоуля и убывает); те же поля — в
   `replay.observe` и манифестах.
3. Инварианты трупа — `invariant.list`: `physics.modes`, `physics.simulatedSpeed`, `physics.joints`, `physics.ground`, `physics.inArena`
   (после Physics). Диагностические `physics.energy`, `physics.pushes` читают трассу: `physics.bodies {"trace":"on"}` и `invariant.enable
   {"ids":["physics.energy","physics.pushes"],"enabled":true}`; встать — `time.breakOnInvariant {"ids":["physics.energy"]}`, затем
   `trace` → `energy`. Нечисловой труп строится заново живым в точке корня (`core.body-rebuild`; `physics.finite` — нарушение на тике).
4. Хеш: `state.describe {"part":"physics","filter":"1v1"}` — `jointCount`, `jointN` (вид, пределы, `enabled`, `measure`), `reaction`,
   `asleep`, `restTime`; `{"part":"physics","filter":"passes"}` — проходы пар.
5. Ручки: `command.send {"command":"TuningCommand","fields":{"Knob":"ragdoll.popSpeed","Value":3}}` — шаг этого тика уже по новым;
   перебор — `experiment.sweep` по `ragdoll.*` на реплее со смертями.
6. Сцены: s8 — `Place` врага на ступени пирамиды (`{"X":-16,"Y":0}`), тиком позже `Kill`; s4 — два `Place` в (±0,36; 1,5), `Kill` обоим,
   тиком позже `ShiftBodies` второго на `{"X":-0.52,"Y":0,"Z":0}`; приёмка — `feature.verify {"id":"ragdoll"}`.

**Толчки живых и удары по трупам.**
1. Проход сквозь труп (s3): `Place` врага в `{"X":0,"Y":4}`, тиком позже `Kill`, через 2 с — `PlayerIntent`
   `{"Velocity":{"X":0,"Y":4.2},"Facing":0}` с `"repeat":360`; `watch.add {"entities":["player"],"fields":["RootVelocity.Value.Z","Recoil.Velocity.Z","Recoil.Tick"]}`
   и `{"entities":["enemy 1"],"fields":["Body.ComVelocity"]}` → `entity.history`: скорость корня у трупа падает на сотые доли.
2. Толчки по трассе: `trace` → `sources` `push.body`/`push.pass` (импульс), доли бюджетов пары и прохода, выталкивание сверх толкающей
   точки (≤ `PopSpeed`), отдача; картинкой — `contacts`.
3. Метки и проходы: `state.describe {"part":"physics","filter":"<сочленение из BodyRef>"}` — у тела `source` (`Pass` — клинок в ударе),
   `reaction`; `{"filter":"passes"}` — проходы (удар, номер, открыт, бюджет, остаток).
4. Удар по трупу (s1): `Kill` врага рядом, `PlayerCommand {"Attack":true,"Gesture":{"X":1,"Y":-1}}` — `events.history {"types":["Hit"]}`
   (`Corpse: true`), `entity.get {"entity":"enemy 1","components":["HitImpulse","Health"]}`, `ArenaStats.CorpseHits`. Почему дёрнулся —
   `state.why {"entity":"enemy 1","field":"HitImpulse"}` (с `causality`); отдача — `state.why {"entity":"player","field":"Recoil"}`.
5. Инварианты `physics.sources`, `ragdoll.hitSource`, `ragdoll.hitImpulse`, диагностический `physics.pushes`. Ручки отдачи —
   `ragdoll.playerRecoil`, `ragdoll.enemyRecoil`, `ragdoll.recoilMaxSpeed`. Без сеанса: `Sword.Headless --replay
   artifacts/features/ragdoll/scenario-s3.swreplay --set ragdoll.playerRecoil=4 --sample 1 --json` — `trajectory[].speed` игрока.

**Скорость и покой физики трупа.**
1. Где время шага: `profile.stages {"enable":true,"reset":true}` → тики с трупами → `profile.stages {"top":40}` — зоны `physics.*` под
   `core.physics-step@Physics` (фазы подшага и сон; README физики, «Порядок шага»); прогрев шага — `log.tail` → `[physics] прогрев …`.
2. Откуда энергия: `trace` → `energy` (`last`, `window`, `run`): `growth` — труп без толчков и без контакта с трупом (накачка — около 0),
   `paired`/`pairedBody` — у трупа в контакте с трупом, `pairedTotal` — сумма касавшихся (допуски `physics.energy` — 12,5 и 25 Дж),
   `phases` — `integrate`, `joints`, `world`, `pairs`, `pressed`, `velocity`, `contactVelocity`, `relax`; нарушение пишет те же фазы.
3. Глубина в земле: `time.breakOnInvariant {"ids":["physics.ground"]}` → `physics.bodies {"entity":"<чьё тело>"}` (`grounded`, концы) и
   `trace.contacts` (`ground`/`pair`/`push.*`: глубина и решённая) — кто держит тело в земле.

**Сон трупа.**
1. Кто спит: `physics.bodies {"entity":"enemy 3"}` → `asleep`, `restTime`; ждать — `time.runUntil {"condition":{"all":[{"entity":"enemy 3"},{"field":"Body.Asleep","equals":1}]}}`;
   по тикам — `watch.add` на `Body.Asleep`, `Body.RestTime` (не в `world.query`); сколько спит — `state.describe {"part":"physics"}`.
2. Кто будил: `trace` → `sleep`: `sleeps`, `asleepMax`, `contacts` (касаний спящего — опора), `wakesBy` — `push` (живой глубже 1 см или
   быстрее 0,5 м/с), `hit`, `touch` (труп быстрее 0,5 м/с или падающий), `chain` (лежащие на разбуженном и на уведённом теле), `command`,
   `settings`. Висит ли кто-то: `Body.Com.Y` лежащего на земле ~0,15…0,2 м (сценарий `sleep-support`).
3. Инварианты `physics.sleep`, `physics.sleepContacts`; цена — зона `physics.sleep`. Ручки: `command.send {"command":"TuningCommand",
   "fields":{"Knob":"ragdoll.sleepSpeed","Value":0}}` — сна нет (`ragdoll.sleepBodySpeed`, `ragdoll.sleepTime`; F3 — «СОН ТРУПА», F7 —
   синий крест). Приёмка — сценарии `sleep-*`, `s3-asleep`, `s1-asleep` манифеста `ragdoll`.

### Рендер: HDR, bloom, свет, прозрачное

Рендер — [README](../engine/Sword.Engine.Render/README.md). Сцена игры — в HDR: линейный цвет → (+ bloom) × экспозиция 0.99 → Filmic → sRGB.

1. Яркость кадра: `Sword.exe --windowed 1280x720 --no-activate --frames 40 --no-hud --shot artifacts/look.png --json` → `report.hdr`
   (экспозиция, bloom) и `report.hdr.shot` — яркость входа тонмапа (максимум, среднее, `overOne`, `nonFinite`), рядом `look.hdr.png` (ложные
   цвета: зелёный — средний серый 0.18, жёлтый — 1, красный — 4, голубой — NaN) и сырой half `look.hdr.bin`. Живая игра — `capture.bundle` →
   `hdr`. Пятна `nonFinite` — NaN в шейдере сцены или модуля.
2. Bloom: `report.hdr.shot.bloom` / `capture.bundle` → `hdr.bloom` — добавка × экспозиция, карта `.bloom.png` той же шкалы; проходы
   `post.bloom.*` и их GPU-время — `render.graph`. Нет свечения — сравнить яркость с порогом (`threshold`, по умолчанию 1).
3. Точечный свет: `Sword.exe --test-light [N]` — факел LIVE-2 у игрока (N − 1 ещё по кругу 3 м); `report.lights` / `render.graph` → `lights` —

4. Ручки «Свет» (F3; клиент, не реплей): `Sword.exe --tune light.night=1 --tune light.testLight=1 --tune light.exposure=2` (ещё `bloom`,
   `bloomIntensity`, `bloomThreshold`) — с первого кадра; итог `--json` → `light`. В `sword.user.json` не пишутся.
5. Прозрачное: слой ½ — `report.hdr.shot.transparent` / `capture.bundle` → `hdr.transparent` (размер ½, яркость, `coverage` — средняя
   альфа), карта `.transparent.png`; проходы `transparent.halfres.depth` и `.composite` — в `render.graph`. Слоя нет в кадре — поле `null`.
6. Текстуры пака: `report.textures` / `render.graph` → `textures` (путь, формат, размер, мипы, слои, sRGB, байт видеопамяти); журнал —
   категория `texture`. Проверить любой пак — `SWORD_CONTENT=<пак> dotnet test tests/Sword.Engine.Render.Tests --filter TextureGpuTests`.
7. Порядок проходов и фазы (Simulation → Opaque → Composite → Transparent → Post → Ui → Debug) — `render.graph` → `passes[].phase`;
   запись заднего буфера до Post — исключение графа с именем прохода (журнал, `log.tail`).
8. Клиентские модули ([контракт](../engine/Sword.Engine.Client/README.md)): `--json` → `report.modules` (включён ли, проходы, оверлеи,
   ручки, GPU-симуляции, тики наблюдателя); выключить — `--set modules.<id>.enabled=false`. Огонь ([модуль](../game/modules/Sword.Game.Fire.Client/README.md)):
   факел в руке — `--set combat.playerWeapon=torch --overlay fire` (головки по тикам, рамка площадки сима, центр шага, точка кисти;
   `capture.bundle {"overlays":["fire"]}`); поле сима — `--overlay fire.field` (ρ тепловой шкалой) или `--tune fire.field=1`, ручки
   `--tune fire.kMin=…` (`simSpeed`, `accumulation`, `brushStrength`, `brushSize`); итог — `fire`: огни, экземпляры `sims[]` (k, WOD, шаги,
   Σρ, центроид в см, `checks` finite/bounded/centered, `fieldHash`); поля в снимок — `<shot>.fire[N].density.png`, `.velocity.png`, `.brush.*`.
   Бег — `--move 1,0`, замах — `--hold attack` (один удар в начале), кадры повторяемы — `--fps 60`. Повтор полей: `--record` → два
   `--replay` с разным `--fps` и тем же числом тиков при неподвижной камере (`--camera Y,P,D,X,Z`; площадка пламени — к глазу кадра) →
   `fire.sims[0].fieldHash` равны. На мече — `--set fire.weapons=["sword_1h"]`.
   Пламя (по умолчанию видно; `--tune fire.flame=0` — выкл.): итог — `fire.flame` (площадок, площадь на экране, фаза, туман, числа формулы),
   вклад — `--overlay fire.flame` / слой `fire.flame` (цвет x/(1 + x), альфа), проход и GPU-время — `fire.flame`; ночь — `--tune light.night=1`.

### Пекарня

Проект — [Bake/](../Bake/README.md), ядро — [tools/Sword.Bake](../tools/Sword.Bake/README.md), плагины — [Engine](../tools/Sword.Bake.Engine/README.md),

Консоль — `tools/Sword.Bake.Cli/bin/Debug/net10.0-windows10.0.22000.0/sword-bake.exe` (плагины той же конфигурации собирает
`dotnet build SWORD.slnx`); запускать в `Bake/` (проект ищется от текущего каталога вверх, иначе `--project КАТАЛОГ`).

**Перепечь, сверить с эталоном, отладить.**
1. `sword-bake status --json` — `assets[]` (`status` `upToDate`/`dirty`/`noSource`/`error`, `reason`), `project.problems` (плагины,

2. `sword-bake build [шаблоны] --json` (`anim/gasp`, `anim`, `processor:anim.pack`) — `assets[].result`, `reason`, `error` и `log`
   упавших, `pakWritten`, `pak.status`; ошибка любого ассета — пак не записан, прежний цел. Полная выпечка — Debug ~31 с, Release
   ~9 с. Ход выпечки (корень, пальцы, FK, «записано / без изменений», слои текстур) — лог `build` текстом. Правка кода выпечки
   клипа — поднять `AnimImport.ToolVersion`, иначе клипы не перепекутся.
3. `sword-bake pak --verify` (код 2 — нарушена целостность), `which ПУТЬ` (кто пишет файл), `list --content`.
4. Сверка: `sword-bake diff ..\Content.reference.swpak ..\Content.swpak --expect reference.expect.json --json` —
   `summary` (`same`, `sameContent`, `unexpected`), `unexpected[]` (`source` `file`: `path`, `kind` `onlyA`/`onlyB`/`size`/`hash`,
   `detail` сравнителя или «отличаются байтами»; `buildInfo`: ассет и поле `.bake/build.json`), `expectations.unused`; код 0 —
   неожиданных нет, 2 — есть. Сейчас: 22 равны байтами, 1048 клипов — по содержимому (без `SourceHash`), 24 ожидаемых (оружие — новый хват), 0 неожиданных.

7. Studio глазами (выходы, форма, предпросмотры) — `tools/Sword.Bake.Studio/bin/Debug/net10.0-windows10.0.22000.0/Sword.Bake.Studio.exe

### Если что-то не так

- «симуляция не дошла до точки обслуживания» — кадр живой игры завис (или Headless остановлен); запрос не исполнен — повторить. В свёрнутом
  окне тики живой игры не идут; проверочный прогон (`--frames`, `--bench`) рисует и свёрнутым, кадров нет 60 с (`--stall N`) — код 5. Без
  захвата окна — `Sword.exe --windowed 640x480 --no-activate --minimized --frames 60 --json`.
- Неизвестный аргумент — ошибка со списком аргументов; незаданный аргумент пропускается, а не передаётся `null`.
- Живая игра перезапущена — прежний сеанс незнаком (404): начать сеанс заново или переподключить `sword-app` в `/mcp`. Вызов по HTTP — не
  дольше 35 с: долгое ожидание — `time.runUntil` с `timeoutSeconds` до 30 и повтором.
- Кадр живой игры на ходу интерполирован (`alpha` < 1): для точного кадра — `time.pause`. «тик уже прошёл» — команды только на будущий тик; без `tick` — на ближайший. Имя компонента неоднозначно — полное имя из `world.types`
  (`stableName`). Ошибки движка — `log.tail {"level":"warning"}`.
- **Процессы агентских серверов.** Каждый сеанс Claude Code (`claude.exe`) и поток Codex держат свой `Sword.Headless --agent` (~850 МБ;
  подагенты — сервер сеанса); сервер выходит сам по концу stdin, концу обёртки `cmd` и после 15 мин без вызовов, Sword.exe видов умирает с
  ним. Посмотреть: `Get-CimInstance Win32_Process -Filter "Name='Sword.Headless.exe'" | Select ProcessId,ParentProcessId,CreationDate,WorkingSetSize`.
  **Чужие не завершать** — только без живого родителя-клиента или свои. Узлы MSBuild и `VBCSCompiler` выходят сами; `dotnet build-server
  shutdown` не звать, пока работают другие сеансы.
