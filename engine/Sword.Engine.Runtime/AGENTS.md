# Sword.Engine.Runtime — правила

Симуляция без окна (раздел 7 ARCHITECTURE_PLAN.md), v0: `Simulation` — мир ECS со стадиями, фиксированный тик,
команды тика, ядро и статические модули, конфиг, экспорт тика.

- Стадии мира — служебная `runtime.commands`, стадии игры, служебная `runtime.export` (`Simulation.CommandStage`,
  `ExportStage`); служебные добавляет Runtime, модулям они недоступны (`SimulationBuilder.System` — только стадии игры).
- Всё, что меняет симуляцию на ходу, — команда тика (`Simulation.Enqueue`): в `runtime.commands` своего тика она
  становится событием `Event<T>` (`TickCommands`) — его видят все стадии игры в том же тике. Тип команды регистрирует
  ядро или модуль: `SimulationBuilder.Command<T>()`. Мир снаружи — только `WorldReader` (`Simulation.World`), и у
  владельца тоже: других путей изменить симуляцию нет (тест `OwnerSeesWorldReadOnly`).
- Ядро (принцип 4 плана) — не модуль: `Simulation.Build(config, stages, core, modules)`, регистрации ядра без токена
  модуля, выключить его нельзя (`modules.core` — неизвестная группа).
- Модули — `IModule` (`Id`, `Configure`). `Id` — строчная латиница, цифры и `_`, первой — буква (`IModule.IsValidId`):
  без точки, которая делит путь конфига, и без регистра; не имя секции движка (`sim`, `modules`, клиентские — `input`);
  иное — ошибка сборки симуляции.
  Выключенный (`modules.<id>.enabled=false`) не регистрирует ничего; системы включённого помечены его токеном
  (`World.SetModuleActive` — задел под деактивацию командой).
- Настройки модуля — секция с его `Id` (`SimulationBuilder.Settings<T>()`); у выключенного модуля она пропускается
  (`ConfigSet.Skip`), а не считается неизвестной. Переключатели модулей — секция групп
  (`ConfigSet.Groups<ModuleSettings>`): те же слои и та же строгость (переменная `SWORD_MODULES_<ID>_ENABLED`;
  неизвестный модуль и неизвестный ключ — ошибки). Сырого чтения конфига нет.
- Без модуля нет его компонентов, команд и экспорта: наблюдатели спрашивают `WorldReader.Knows<T>`,
  `Simulation.Accepts<T>`, `TickExport.Exports<T>` (у клиента — `SimulationLink`); команда без модуля — исключение.
- `SimulationBuilder` действует только до сборки мира: регистрация из `OnWorldBuilt` и позже — исключение.
  `OnWorldReady` — начальное наполнение после всех `OnWorldBuilt` ядра и модулей (ядро ставит по ресурсу, который задаёт
  модуль при сборке мира: тела бойцов по позе постройки — 5в).
- Хуки времени жизни ресурсов подсистем — `SimulationBuilder.OnAdd<T>/OnRemove<T>` (ECS, `WorldHooks.cs`; владелец —
  ядро или настраиваемый модуль, виден агенту в `ecs.componentUsage`). Первый потребитель — тело бойца (`BodyRef`, 5а).
- Конфиг — `ConfigSet`: код → `sword.json` → `sword.user.json` → `SWORD_<СЕКЦИЯ>_<КЛЮЧ>` → `--set`. Вложенные объекты
  сливаются ключ за ключом (`--set секция.объект.ключ`, `SWORD_СЕКЦИЯ_ОБЪЕКТ_КЛЮЧ`); ключ — только записываемое
  свойство; регистр имён не важен ни в одном слое (тот же ключ в другом регистре — тот же, действует последний); ключ
  дважды в одном файле, `null` или число вместо объекта — ошибки с путём к файлу. Неизвестные секции проверяет exe в
  конце композиции — `ConfigSet.Complete()` (секции читают и симуляция, и клиент); после него конфиг заморожен.
  Секции клиента движка — `ConfigSet.ClientSections` (`input`); exe без клиента (Headless) пропускает их
  `SkipClientSections()` — общий `sword.json` один на оба exe, а клиентских сборок Headless не видит. Итог —
  `Effective`, источники без повторов — `Sources`.
- Время тика — ресурс `SimTime`: номер, шаг, время — как `DuelArena.Time` SWORD (`+= dt` во float в начале тика). Шаг —
  `sim.tickRate` (по умолчанию 120, как `FastTick` SWORD).
- Экспорт тика (`TickExport`, стадия `runtime.export` — после барьера последней стадии игры): объявленные срабатывания
  (`SimulationBuilder.Export<T>`) копируются с номером своего тика в очередь кадра. Кадр начинает `BeginFrame()`
  (клиент — `SimulationClock`, Headless — каждый тик), записи кадра — `Frame<T>()`. Кто делает тики без
  `BeginFrame`, у того очередь растёт.
- Исполнять тики может только владелец `Simulation` (exe, клиент движка); клиентской части игры доступен узкий
  `SimulationLink` (Engine.Client).

Ограничения: переменная `SWORD_*` с опечаткой не находится (переменные ищутся по известным ключам, а общий префикс
`SWORD_` занят и переменными SWORD) — опечатки ловят файлы и `--set`. Группы `modules` знают только модули симуляции:
чисто клиентский модуль (раздел 7) потребует своего списка групп.

- Путь инструментов (агент): `Simulation.CommandTypes` и `EnqueueRaw(type, tick, bytes, repeat)` — команда байтами по
  типу, только на будущий тик, `repeat` тиков подряд одной постановкой; ожидающих команд этого пути одного типа — не
  больше `TickCommands.MaxToolCommands` (1 000 000; сверх — `InvalidOperationException`, агент видит ошибку). Очередь команд — по тику с курсором: тик берёт
  свои записи с головы, хвост не просматривается (`CommandQueueTests`). В тике команды этого пути выдаются после команд `Enqueue` (клиента) того же типа: где действует
  последняя команда тика своего типа, побеждает инструмент; между типами — порядок регистрации типов. Место регистрации системы (`SimulationBuilder.System` — файл и строка вызова)
  идёт в `SystemInfo.Source` — карта архитектуры агента.

- Хеш состояния (этап 3, точка 3а; раздел 7 плана): `Simulation.HashState(parts)` — между тиками, без выделения
  памяти; участники по Id (`StateParts`), итог — хеш их хешей. `ecs` заводит Runtime — всё, что мир переносит из
  тика в тик: живые сущности по индексу, у каждой компоненты по стабильному имени; ресурсы-значения по имени; слоты
  (поколения свободных, порядок свободных номеров); журналы по имени (записи последнего оборота тика с возрастом в
  барьерах); регистрации систем в порядке исполнения (включена ли, сколько записей каждого журнала не прочла). Номеров
  записей и барьеров в хеше нет — он не зависит от числа сыгранных тиков. Ресурсы со ссылками (пулы, ассеты) не
  входят — их состояние отдают свои участники (`SimulationBuilder.StateContributor`, `IStateContributor`: Id по правилу
  модуля, не `ecs`, без повторов). Хешируются **листья полей** (`FieldLayout`: смещения считает среда), не сырые
  байты: padding не участвует, `-0` → `+0`, любой NaN → один, bool → 0/1. `Describe` и `DescribeState` — ровно те же
  листья: при расхождении сравниваются описания. Внутреннее состояние систем (поля классов систем) не хешируется —
  системы его не держат; всё авторитетное — в компонентах, ресурсах или у участников.
- ГСЧ — ресурс `SimRandom` (зерно `sim.seed`, по умолчанию 1): чистая функция (зерно, поток, тик, сущность, выборка),
  состояния нет. Поток — `SimRandom.Stream("назначение")`, считать при настройке. `System.Random` и
  `Random.Shared` в симуляции не использовать: они ломают реплеи.
- Реплеи (этап 3б; раздел 7 плана): `Simulation.Record(info, hashEvery)` и `Simulation.Play(replay)` — только с тика 0.
  Запись берёт каждую выданную команду тика в `runtime.commands` (очереди клиента и инструментов и сам реплей, любые
  типы) листьями полей `FieldLayout`; тики с одинаковыми командами — отрезок (удержание не выделяет памяти; хеши — 8 байт на тик и участника, кусками до 64 КБ). Команды
  реплея выдаются в тике первыми, очереди — после (команда инструмента перебивает реплей — ветвление). Хеш по
  участникам — на тике 0 и каждые `hashEvery`; первое расхождение — `ReplayPlayer.Divergence` (тик, последнее
  совпадение, участники). Конфиг воспроизведения — `Replay.CreateConfig()` (`ConfigSet.FromReplay`: только записанный
  итоговый конфиг, ни файлов, ни переменных). Файл `.swreplay` — JSON в CRLF, запись → чтение → запись — тот же текст.

- Наблюдатели (этап 3в): `Simulation.Observe(ISimulationObserver)` — только владелец; `AfterStage` после барьера каждой
  стадии (`Simulation.Stage` — её имя, мир согласован; `World.RunTick(tick, afterBarrier)`), `AfterTick` после тика и
  записи реплея. Наблюдатель только читает; посреди тика команда — не раньше `NextCommandTick` (`Tick + 1`: команды
  идущего тика уже выданы), между тиками — `Tick`. Без наблюдателей хука нет (`RunTick` без делегата). В хеш и реплей
  наблюдатель не входит (`ObservationTests.Observers_DoNotChangeStateHash`).

- Инварианты (этап 3г; раздел 8 плана): контракт `IInvariant` (`Id` — части из латиницы, цифр и `_` через точку,
  первой — строчная буква; `Cost` — `InvariantCost` каждый тик, раз в N, по запросу; `Scope`; `After` — имя стадии,
  `runtime.export` — конец тика; `Evaluate(ctx, ref ViolationSink)`). Регистрирует ядро или модуль —
  `SimulationBuilder.Invariant`/`Invariants` (владелец — `core` или Id модуля), базовые инварианты движка
  (`ecs.finite`, `ecs.entityRefs` — `EcsInvariants`) Runtime заводит сам. Проверка — `Simulation.Invariants`
  (`SimulationInvariants`) после барьера своей стадии, до наблюдателей (`ISimulationObserver.OnViolation`); хук барьера
  — только если есть включённые инварианты или наблюдатели. Инвариант только читает мир, в хеш не входит; без
  нарушений не выделяет памяти (`InvariantTests.SteadyTick_WithInvariants_DoesNotAllocate`, `headless-smoke`);
  исключение в проверке — нарушение. `sim.invariants` (по умолчанию `true`) — кодовые включены; «по запросу» — только
  явно (`SetEnabled`, затем каждый тик) или `Run` (нарушения только в ответе). Учёт — проверки, нарушения, среднее
  время, кольцо последних 256; в журнал — первые 5 нарушений каждого.
- Эксперименты и приёмка (этап 3д): `Replay.Head(at, hashes)` — начало реплея (ветка, которая дальше идёт своими
  командами; без хешей — замеры времени). Воспроизведение не выделяет памяти на тик
  (`ReplayTests.Playback_SteadyTick_DoesNotAllocate`: команды тика выдаются по индексу — перечислитель через интерфейс
  упаковывался, 32 байта на тик; нашли бюджеты фич).

- Профайлер CPU (этап П, точка Па): `Simulation.AttachProfiler(CpuProfiler)` — владелец, между тиками; тик — период
  профайлера (зона `tick`), в нём зоны мира (`World.AttachProfiler`), инвариантов (`invariant.<id>` — у каждой проверки;
  исключение в проверке раскручивает стек до зоны), реплея с хешем (`sim.record`) и наблюдателей (`sim.observers`).
  Профайлер только читает часы: хеш, реплей и выделения тика от него не зависят (`ProfilerTests`, толпа 32 врагов —
  `ArenaTests`); включает его владелец (ключ `--profile`, `profile.stages`), а не команда симуляции.

- **Долгий цикл раз в тик — тело в свой метод** (исправления после Пд): метод, который вызывается раз в тик или кадр и содержит
  долгий цикл (порядка 1000 итераций за вызов и больше: пары бойцов, сущности × компоненты × листья, слоты пула × суставы), —
  тело цикла в отдельный метод, иначе многоуровневый JIT заменяет его на ходу (OSR) — синхронная компиляция 1,5…3,5 мс на
  главном потоке в первые секунды (`RootCollision.Resolve`, `EcsInvariants`, `AnimationState.AppendHash` — исправлены).
  `AggressiveOptimization` — только тонкому методу из вызовов или примитивному циклу, которому PGO не нужен (пиксели, байты): у
  счётного кода он теряет PGO (+3 % тика, [docs/history/profiler.md](../../docs/history/profiler.md), «Разбор Пд»).
  Проверка — `Sword.Headless --ticks 3600 --units 32 --move 1,0 --profile
  runtime`: в `events.recent.jitMain` отчёта нет `osr`; все компиляции процесса — `DOTNET_JitDisasmSummary=1
  DOTNET_JitStdOutFile=<файл>` (строки `Tier1-OSR`).
- **Период инвариантов — только в живой игре** (исправления после Пд, решение пользователя): период кодового инварианта
  (`InvariantCost.Every(N)`; тяжёлые — `InvariantCost.Heavy`, раз в `HeavyPeriod` = 4 тика) действует только при
  `SimulationInvariants.LivePeriods` (ставит Sword.exe без `--replay`; `time.breakOnInvariant` снимает на время ожидания); тесты,
  `feature.verify`, Headless (и агент в нём), сверка реплея — каждый тик. Инвариант агента (`Add`, `invariant.define every`) держит
  свой период всегда. `InvariantInfo.Every` — как часто проверяется сейчас. `Heavy` — кодовому инварианту, чья медиана в тике толпы
  (32 врага) — от ~2 % тика и который не считает тики подряд (счёт с периодом ломается — `movement.rootOverlap` каждый тик);
  нарушение, которое держится, в живой игре видно не позже чем через 3 тика, короче периода — может не попасть в проверку. Тесты —
  `InvariantTests.Periodic_AndThrowing_Invariants`, `LiveGame_HeavyInvariant_CatchesPersistentViolationWithinPeriod`.

- Причинность (6д): поле причины записей журналов (`Cause`) — вне хеша `ecs` и его описания (`FieldLayout.Without`): хеш — только
  данные записи. `Simulation.EnableCausality`/`DisableCausality` — диагностический режим (владелец, между тиками; ключ
  `--causality` Headless и App, `session.start {causality}`): хеш, реплей и выделения тика те же (`CausalityTests`). Команда тика в
  `runtime.commands` — корень (`CommandBuffer.EmitCommand`) с пояснением очереди: `клиент` (`Enqueue`), `агент` (`EnqueueRaw`),
  `реплей` — любая зарегистрированная команда, в том числе ручки 6е, корень автоматически.
- **Ручки** (точка 6е; раздел 7 плана, «Конфигурация») — `Tuning.cs`: ядро или модуль заводит ручки секции над ресурсом мира
  `SimulationBuilder.Tuning<T>(секция).Float(…)/.Bool(…)` — ручка = поле ресурса (`TuningKnob`: имя — ключ конфига «секция.ключ», поле,
  диапазон, значение в коде, подпись, подсказка, владелец; `Simulation.Tuning`, `Simulation.Knob(имя)`). Изменение на ходу — только команда
  `TuningCommand {Knob, Value}` (заводится с первой секцией; ключ `TuningKey` — хеш имени без учёта регистра: от порядка регистрации и
  набора модулей не зависит; имя по ключу — `TuningKey.Name`, общий словарь процесса): событие в `runtime.commands` → система секции
  `tuning.<секция>` в первой стадии игры (с токеном владельца) прижимает значение к диапазону (нечисло и чужая ручка — пропуск) и одной
  командой `SetResource` заменяет ресурс — с барьера стадии его видят все следующие стадии тика, реактивные — `ResourceChanged<T>`
  (причина замены — последняя применённая команда ручки: корень 6д).
  Секция — один раз, ключ — латиница и цифры, диапазон — конечный min < max, поле ресурса должно быть — иначе ошибка сборки. Проверка —
  `TuningTests` (тот же тик, прижатие, одна замена ресурса, реплей с ручками посреди прогона — те же хеши, ошибки регистрации).
- **Файл пользователя** — `UserConfig` (6е, панель F3): `PathFrom(каталог)` — `sword.user.json` рядом с `sword.json`; `WriteSection` —
  бережная запись одной секции (переписывается по лексемам: другие секции и ключи, порядок, комментарии — блоком — остаются; значение null —
  ключ убрать; CRLF, UTF-8 без BOM, замена через временный файл; испорченный файл — `InvalidDataException`, файл не тронут); `ReadSection`,
  `Numbers` — для «загрузить». Проверка — `UserConfigTests`.

- **Диагностические режимы** (7и) — `Diagnostics.cs`: `IDiagnosticMode` (Id по правилу инварианта, название, включён ли, включить и
  выключить, начать окно заново) регистрирует ядро или модуль (`SimulationBuilder.Diagnostic`, владелец — `core` или Id модуля), список —
  `Simulation.Diagnostics` (`SimulationDiagnostics`: `Has`, `IsEnabled`, `Set`, `ResetWindow`, `EnabledIds`; неизвестный Id — ошибка со
  списком). Режим не меняет ни мир, ни хеш, ни реплей (как причинность и события профайлера), поэтому это не команда тика: включает
  владелец (клиент — `SimulationLink`), агент — из точки обслуживания (`ServiceContext`), только между тиками (посреди тика —
  `InvalidOperationException`). Первый — `physics.trace` игры (трасса физики 7д). Проверка — `DiagnosticsTests`.

Не сделано: деактивация модуля командой тика.

Проверка: `tests/Sword.Engine.Runtime.Tests` (`InvariantTests` — модуль-неисправность ловится на своём тике после своей
стадии, «по запросу», режим выключенных, период, исключение, ошибки регистрации, 0 байт; `StateHashTests` — план полей, padding и `-0`/NaN, два прогона, участники,
0 байт на хеш, ГСЧ; `ReplayTests` — запись, файл бит в бит, воспроизведение, расхождение, ветвление, сравнение; конфиг по слоям и его строгость, модули, ядро, команды, края тика:
команда в первой стадии игры и событие последней стадии в экспорте своего тика, кадры с 0 и 3 тиками, время тика),
`tests/Sword.Engine.Client.Tests` (кадры через клиент), `verify.ps1` шаг `headless-smoke` (каждый модуль по очереди
выключен — 10 с игрового времени; опечатка в конфиге и выключение ядра — ошибки).
