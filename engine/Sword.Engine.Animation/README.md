# Sword.Engine.Animation

Подсистема анимации движка (раздел 6 плана, этап 2). Владеет скелетом, библиотекой клипов и **пулом поз**; наружу —
хэндлы поз. Игра и модули ставят пулу задания, пул исполняет их пачкой в стадии Animation.

## Назначение

- `Skeleton` — имена и родители суставов, хеш (по нему клип узнаёт свой скелет), поза привязки из меша
  (`WithMeshBindPose` — новый скелет), прямая кинематика `ToModel`.
- `ClipLibrary` — все клипы одного скелета одной таблицей: локальные позы по кадрам, корневое движение (смещение и
  поворот), сэмплинг `Sample`, смешивание `Blend`, длительность, скорость корня, поиск по ID «источник/имя».
- `PosePool` — позы (локальные повороты и смещения, модельные матрицы) в общих массивах; задания `Sample`, `Blend`,
  `BlendMasked` (6в: смешивание по маске суставов, зарегистрированной в пуле `AddMask` — вес сустава
  `w·(mask[j] + (1 − mask[j])·stand)`, идея — `CharacterRig.LayerMask` + `SkeletalClips.Blend` SWORD), `AddMasked` (6г: добавка
  поворотов по маске — `rot[j] = normalize(rot[j]·slerp(identity, conj(ref[j])·pose[j], mask[j]·w))`, идея — `CharacterRig.AddUpper`
  SWORD; смещения не трогает), `Copy`, `ToModel`, `Motion` (этап 8: шаг проигрывателя Motion Matching — раздел
  [«Motion Matching»](#motion-matching)); `Tick` — исполнить очередь; `LastTick` — счётчики заданий (смешивание и добавка по маске —
  в `Blends`, шаги проигрывателей — в `Motions`).
- `AnimMath` — ориентации капсул, двухзвенный IK, векторы поворота, критически демпфированные пружины.
- `Motion/` — механизм Motion Matching (этап 8, идёт): раздел [«Motion Matching»](#motion-matching).

## Откуда логика

SWORD 2eab13b, `Sword.Anim`:

| SWORD | SWORD2 | что изменилось |
|---|---|---|
| `SkeletonAsset` (формат) | `Formats.SkeletonFile` | чтение потоком с точным числом байт, обрезка — `InvalidDataException` |
| `ClipAsset` (формат) | `Formats.ClipFile` | то же; поза читается одним блоком (28 байт на сустав), испорченный счётчик кадров не выделяет память (только у потока с `Seek`); строки длиннее 4096 байт (`MaxStringBytes`) — испорченный файл, в SWORD предела нет |
| `SkeletonAsset` (данные), `SkeletalClips.ToComponent` | `Skeleton` | прямая кинематика — в заранее посчитанном порядке вместо рекурсии с флагами (итог побитово тот же); поза привязки — из меша (в SWORD не нужна: без локомоции боец не рисовался), bind-матрица, не разложимая на поворот и перенос, — `InvalidDataException` |
| `AnimLibrary.Load` | `ClipLibrary.Load` | контент не читает: файлы — `ClipSource` (путь, поток, имя); правила пропуска те же: чужой скелет — молча, изменившийся скелет, другая частота, испорченный файл — с причиной; папка `anim/` — без учёта регистра, как у SWORD. Отличие: «свой» скелет клипа — по `Skeleton.Id` из файла `.swskeleton`, а SWORD сравнивает с запрошенным ID (именем файла скелета); если ID в файле и имя файла разойдутся, SWORD2 не возьмёт ни одного клипа. На эталонном паке они совпадают (`ue5_manny`) |
| `SkeletalClips` (кроме формата `.swskel`) | `ClipLibrary` | без изменений логики; формат `.swskel` не перенесён — пак его не содержит |
| `AnimMath` | `AnimMath` | без изменений |
| — | `PosePool` | новое: позы в пуле вместо массивов в `FighterAnimator`, задания вместо прямых вызовов |

Не перенесено до своих этапов: `FootContacts`, `FootLock`, `LegIk`, `FootPlacement` (этап 9), `MeshEdges`, `SkinnedMeshData`
(уже в Formats). `IGround` → `HeightField`, `SwordBody` → игра, `LocoAudit` → `Game.DevTools`. `Loco/*` и `ContactDetector`
(поднят с этапа 9 — нужен базе) — не перенос, а идеи для своего Motion Matching: раздел [«Motion Matching»](#motion-matching).

Скелет и библиотека клипов неизменяемы: их делят все симуляции (`CharacterAssets` грузится один раз), поэтому
данные отдаются только `ReadOnlySpan`, конструкторы копируют входные массивы. Пул запоминает модельные матрицы позы
привязки при создании — у неизменяемого скелета они не устаревают.

## Настройки

Нет: подсистема конфиг не читает. Размер пула растёт вдвое по требованию (`PosePool(capacity)` — начальный).

## Зависимости

`Sword.Engine.Core`, `Sword.Engine.Diagnostics`, `Sword.Engine.Formats` (раздел 4). Контент (пак) — у вызывающего.

## Ограничения

- Сэмплинг последовательный, по суставам; SIMD и параллельность по батчам — позже, с дифференциальным прогоном против
  этой реализации (раздел 8 плана).
- Маски слоёв — задание `BlendMasked` (6в); добавка поворотов по маске — `AddMasked` (6г: вздрагивание игрока, `CharacterRig.AddUpper`).
- Смешивание — по кратчайшей дуге (`Quaternion.Slerp`, как SWORD). У сустава с частичным весом, чьи повороты в двух позах
  расходятся через 180°, она перескакивает на другую сторону; `BlendMasked` с памятью (`BlendMemory`: итог и итог по кратчайшей
  дуге прошлого задания — две позы) доворачивает такой сустав к ней не больше 8° за задание (`MaxArcStep`), без перескока —
  побитово как без памяти. `Blend` без маски памяти не имеет.
- Один скелет на пул: второму скелету — второй пул.
- Позы между тиками не интерполируются (как в SWORD): клиент рисует позу последнего тика, плавно идёт корень.

## Агентский доступ

Пул и библиотеку игра отдаёт наблюдателям видом `IAnimationView` (`Game.Contracts`): позы по суставам, имена клипов,
счётчики пула. Инструменты агента — `anim.pose`, `anim.clips` (`Sword.Game.Agent`). Хватает, чтобы увидеть, какой клип
играет и какая поза получилась; регрессию держат эталоны SWORD2 (хеш участника `animation`).

## Решения и почему

- Позы — в пуле с заданиями, а не в массивах аниматора: игра и модули ставят задания, пул исполняет их пачкой в стадии
  Animation (раздел 6 плана); наружу — только хэндлы (индекс и поколение).
- Прямая кинематика — в заранее посчитанном порядке «родитель раньше ребёнка», а не рекурсией с флагами: у экспорта UE
  родитель бывает после ребёнка; итог побитово тот же.
- Скелет и библиотека клипов неизменяемы (`ReadOnlySpan`, копии входных массивов): их делят все симуляции.
- Формат `.swskel` не перенесён — пак его не содержит.
- Сверка с SWORD (тесты трасс SWORD) снята на 7а (решение 14, свой путь).

### Оси и порядок умножения

- Пространство персонажа — как у всего SWORD2: +Z вперёд, +X влево, Y вверх; курс — поворот вокруг Y, «+ — от +Z к +X»
  (`Matrix4x4.CreateRotationY`, `ClipLibrary.RootYaw`, `Transform.Facing` игры); вперёд — (sin курса, 0, cos курса).
- Вектор слева (v·M), как у `ClipLibrary.MotionMatrix` и `Skeleton.ToModel`: `Pose2` — это `MotionMatrix(Position, Yaw)`
  (`ToMatrix`, обратно — `From`).
- `Compose(a, b)` — система b, заданная в системе a: матрица `M_b · M_a`; `Relative(a, b)` — система b в системе a:
  `M_b · M_a⁻¹`, курс в (−π, π]; `Compose(a, Relative(a, b)) = b`. Перенос корня за интервал — `Relative(кадр f, кадр f + 1)`.
  Обратный порядок (`M_a⁻¹ · M_b`) даёт ложный сдвиг, растущий с удалением a от начала (урок SWORD — до 30 м/с на клипах с
  поворотом): тест `Relative_OnTurningRootFarFromOrigin_HasNoFalseShift`.
- `Compose` складывает курсы без заворота (цепочки интервалов остаются непрерывными); `Relative` и `From` заворачивают в
  (−π, π] (`Wrap`: ровно −π — это π). `Lerp(a, t)` — доля от тождества: смещение и курс × t (0 — тождество, 1 — a побитово).

### Контракт

- **Схема** (`MotionSchema`): группы в порядке строки признаков, размер — из вида группы: траектория (положения и направления
  в моменты будущего, положения в моменты прошлого), корень (скорость, угловая скорость), суставы (положения, скорости, курс
  по паре «левый, правый») — номерами скелета; вес по умолчанию и пол разброса `MinStd`; моменты будущего (> 0, по
  возрастанию) и прошлого (< 0, от ближнего); суставы контактов. Вид задаёт источник: траектория — в базе по графу, в запросе
  из модели и истории, в цену шва не входит; корень — в базе из клипа, в запросе из модели; суставы — в базе из кинематики, в
  запросе — признаки текущего кадра. Не больше 16 групп и 8 суставов контактов. Противоречие — `ArgumentException` при
  создании; раскладка 45 признаков, какими искал SWORD, описывается (тест).
- **Политика графа** (`IMotionGraphPolicy`, реализует модуль, зовётся только при постройке): кандидаты продолжения
  нециклического клипа по измеренному выходу (`MotionClipInfo`: скорости начала, выхода и средняя в системе корня, поворот);
  прошлое у начала клипа — `Standing` или `StartVelocity`. Лучший кадр входа среди кадров кандидатов база выбирает сама ценой шва.
- **База** (`MotionDatabase`, неизменяемая, общая): кадры базы подряд с локальными номерами (клипы — по возрастанию номера в
  библиотеке, порядок списка постройки не важен), `ClipOf`, `LibraryFrame`; граф `Next`, `Interval` (`Pose2`), `Entry` (кадр
  выхода «становится» кадром входа; −1 — нет), `Searchable`; признаки — только нормализованные, по кадрам (`FeatureRow`), сырые —
  `RawFeatures` (`·Std + Mean`); `Rows` и блоки по 16 строк с `BoundsMin/Max`; `Contacts` (байт на кадр, бит — сустав контакта);
  `RootVelocity` кадра; `MovingJoints`; `Fingerprint` (64 бита от схемы, клипов, графа, признаков и разметки; время не входит);
  `Summary`. Постройка — `Build(библиотека, клипы, схема, политика, параметры)` (8б); конструктор из готовых массивов — для
  тестов 8в и 8г, общая с `Build` часть (проверка, строки, блоки, отпечаток, сводка) — готова.
- **Поиск** (`MotionMatcher.Search(запрос, веса групп, текущий кадр, скидка продолжению, окно пропуска в кадрах)` →
  `MotionMatch`: кадр, цена, цена продолжения, осмотрено блоков и кадров, цены по группам; `SearchBruteForce` — образец):
  нижняя оценка по блокам, строгое «меньше» (ничья — ранний кадр), окно своего клипа — по кругу через шов цикла, 0 Б.
- **Запрос** (`MotionQuery.Fill`): будущее — `TrajectoryModel.Predict`, прошлое — `RootHistory.At`, суставы — нормализованные
  признаки текущего кадра; масштаб данных `velocityScale` (kv) и `goalScale` (kg), зажим ω — параметры; `DataYawRate` — 99-й
  перцентиль базы.
- **Модель предсказания** (`TrajectoryModel(Rate, TurnRate, GoalVelocity, GoalYaw)` + `TrajectoryState(Root, Velocity)`):
  шаг — курс к цели не быстрее ω·dt, скорость `v += (цель − v)·min(1, k·dt)`, корень на новую скорость; `Predict(t, dt)` —
  n = round(t/dt) таких шагов без изменения состояния.
- **История** (`RootHistory(тик, глубина)`): кольцо `RootSample(тик, корень)`, «последняя запись не позже тика», короткая —
  экстраполяция по скорости.
- **Проигрыватели** (`MotionPlayers(база)`): хранилище за хэндлами с поколением, `Reserve`, `Alloc/Free/IsAlive`, обход слотов;
  чтение — `State` (кадр, доля, переходы, есть ли выход, перенос корня последнего шага), `NearestFrame`, на сустав — смещения
  поворота и позиции и их скорости, скорости выхода, выход прошлого задания. Меняет его только задание пула.
- **Задание пула** `PosePool.Motion(поза, хранилище, проигрыватель, MotionStep(Advance, Dt, Transition, Halflife))`: в общей
  очереди по порядку; ссылки на хранилища — в отдельной таблице заданий тика (основное задание несёт её номер), таблица
  очищается после `Tick`; проигрыватель, освобождённый до `Tick`, — `Stale`; выполненные — `PoseTickStats.Motions`. Порядок
  внутри шага (8г): продвижение по графу → затухание смещений → сэмпл кадра с долей и смещения → скорости выхода → запрошенный
  переход (выход этого тика не меняется — разрыв берут смещения).

### Решения и почему

- Проигрыватели привязаны к базе хранилищем, задание берёт базу у него, а не отдельным параметром: номера кадров имеют смысл
  только в своей базе — перепутать нельзя; хранилище и пул — одной библиотеки клипов (проверка при постановке).
- Итог поиска — значение без ссылок, цены по группам — `InlineArray` на 16 мест: его можно хранить в компоненте (компоненты ECS —
  `unmanaged`) и отдавать виду, 0 Б; отсюда предел 16 групп. Равенство `MotionGroupCosts` — своё (встроенное у `InlineArray`
  бросает исключение).
- Признаки хранятся только нормализованными: вдвое меньше памяти; сырые нужны лишь виду и оверлею — `RawFeatures`. Запрос
  копирует признаки суставов текущего кадра как есть — самопопадание без ошибки округления.
- Суставы контактов — в схеме: кинематика меряет их вместе с суставами признаков; контакты — байт на кадр.
- Модель предсказания — дискретная по тикам, как контроллер ядра (`min(1, k·dt)`): предсказание = n шагов той же модели, а не
  непрерывная экспонента (при k = 14 и 120 Гц старт с места на бег 4,2 м/с — положение через 1/3 с расходится на ~3,5 см, 3 %).
- У движка нет умолчаний параметров MM (постройка, контакты, веса поиска): одно место умолчаний — модуль (двойные умолчания —
  хрупкое место SWORD). Типичные значения — в документации типов.
- История — по номерам тиков (`long`), а не по накопленному времени: без дрейфа float.
- Клипы базы — по возрастанию номера в библиотеке: номера кадров и отпечаток не зависят от порядка списка постройки.

- `MotionDatabase.Build`: кинематика кадров базы (`ClipKinematics`, по клипам параллельно, итог побитово как последовательно) →
  признаки по видам групп → нормализация позы по всем кадрам (цена шва) → граф → траектории → нормализация по искомым кадрам
  (среднее по признаку, разброс группы — среднее разбросов, не меньше `MinStd`; суммы в double) → общий конструктор.
- Корень кадра — `Pose2(RootMotion, RootYaw)` в системе первого кадра клипа; скорости — разность соседей в системе кадра, у цикла —
  через шов по оборотам (скорости первого и последнего кадра равны), у края нециклического — односторонняя.
- Контакты — `ContactDetector`: гистерезис по высоте над «полом» клипа и горизонтальной скорости, внутренние серии короче
  `MinRun` переворачиваются (у краёв клипа — нет; шов цикла не сшивается).
- Граф: внутри клипа f → f + 1; цикл — последний кадр во второй, не ищется; у нециклического ровно одно ребро: вход — ценой шва
  среди кадров кандидатов политики (у цикла — кроме последнего, у нециклического — до его окна выхода: вход никогда не бывает
  выходом, поэтому граф не зависит от порядка клипов), ранний выход в окне `ExitWindow` — только если шов заметно дешевле; ничья —
  доля `SeamTie` от max(цена, 1), меньший номер кадра (без пола 1 граф на паке менялся без AVX2). Хвост после раннего выхода не
  ищется (на паке ~6 % кадров — в основном копии циклов).
- Будущее — композиция `Interval` по графу; без полного горизонта кадр не ищется (признаки у него конечны). Прошлое — в клипе
  (цикл — по оборотам), до начала нециклического — по политике.
- Тела циклов постройки по кадрам — `AggressiveOptimization` (раз на процесс; `AGENTS.md`). Пак, 444 клипа `locomotion` с
  тестовой политикой: 51 844 кадра, искомых 48 492, 415 рёбер, 351 ранний выход; Release ~0,1–0,16 с, Debug ~0,5–0,8 с; граф тот
  же без AVX2 (отпечаток — другой: признаки расходятся в последних битах).

**Агентский доступ (постройка):** сводку, отпечаток, хеш графа и разброс групп печатает тест на паке (`MotionDatabasePackTests`); в
игре — строка старта базы в журнале и `Describe` участника `locomotion` модуля.

**Проверки (8б):** `ContactDetectorTests` (гистерезис, шумовые серии, пол клипа), `ClipKinematicsTests` (скорость корня цикла,
непрерывность на шве, поворот без ложного сдвига, параллельно = последовательно), `MotionDatabaseBuildTests` (синтетика
`MotionBuildFixtures`: граф не зависит от порядка клипов, выход становится входом и ребро одно, ранний выход, горизонт 1 с у
искомых, хвост без продолжения не ищется, `MinStd`, два построения — один отпечаток), `MotionDatabasePackTests` (категория Content:
постройка на паке, сводка в вывод, отпечаток при любом порядке клипов).

### 8г: проигрыватели и задание пула

- **Проигрыватели** (`MotionPlayers`): слоты, номера, поколения и порядок свободных — как у `PosePool`; `Reserve` логики не меняет;
  новый проигрыватель не начат (кадр −1). Чтение: `State`, `NearestFrame`, на сустав — смещения поворота (W ≥ 0) и позиции (только
  `MovingJoints`) и их скорости, скорости выхода, выход прошлого задания. Меняет состояние только задание пула (`internal SlotAt`).
- **Шаг** (`PosePool.Motion.cs`): продвижение на `Advance` × частота по графу; перенос корня — композиция долей `Interval`. Пришёл в
  кадр выхода или по ребру в другой клип — сразу вход с инерциализацией от выхода в точке ребра, затухание делится в момент ребра
  (иначе скорость нового смещения действовала бы и на часть тика до ребра — скачок 0,059 рад против обычных 0,037). Кадр без
  следующего — проигрыватель стоит; не больше 1024 интервалов за шаг и 16 входов подряд (конструктор базы циклы входов не
  запрещает). Дальше: затухание (`AnimMath.DecaySpring`, хвост < 10⁻⁶ обнуляется ровно — без денормализованной арифметики на долгом
  стоянии), сэмпл кадра с долей только внутри клипа (смещение · кадр; без смещения — кадр побитово), скорости выхода разностью за
  `Dt`. Затем запрошенный переход (цель — через `Entry`): смещение = выход ∘ conj(вход), скорость = скорость выхода − скорость клипа
  во входе; выход тика не меняется.
- Скорости клипа — во времени игры (× темп `Advance/Dt`). Не начатый: переход сразу ставит кадр и выход без инерциализации (`Advance`
  этого тика не учитывается, `RootStep` — тождество), скорости — клипа в кадре; без перехода — ничего (задание считается в
  `Motions`). Ребро и запрос в одном тике — два перехода, выход тика — с ребром.
- `NearestFrame` при доле ≥ 0,5 перед кадром выхода может вернуть сам кадр выхода — вызывающий решает, считать ли текущим кадром
  его вход (модуль Locomotion считает: `MotionMatchRuntime.CurrentFrame`).
- **Память:** `PosePool.Reserve(позы, задания)` заводит и таблицу заданий MM — 0 Б с первого шага. **Стоимость** (Release, 161
  сустав): ~4 мкс шаг без смещений, ~9 мкс со смещениями и переходом.

**Агентский доступ (проигрыватели):** методы чтения (слоты, поколения, свободные, `State`, 8 массивов суставов) хеширует и
описывает участник `locomotion` модуля; число шагов MM за тик — `PoseTickStats.Motions`.

**Проверки (8г):** `MotionPlayersTests` (поколения, свободные слоты, `Reserve` без выделений и с той же логикой), `MotionJobTests`
(скачок позы на переходе и ребре ≤ обычного за тик + допуск, затухание, продвижение аддитивно, вход ровно раз, цикл, не начатый,
Stale, 0 Б с переходами, два пула — побитово одно, порядок в общей очереди, ребро посреди тика = два шага с разрезом где угодно,
предохранители); помощники — `MotionPlayerFixtures` (гладкие клипы).

### 8в: поиск, запрос, модель, история

Тела `MotionMatcher.cs`, `MotionQuery.cs`, `TrajectoryModel.cs`, `RootHistory.cs` готовы.

- **Поиск.** Одна арифметика на цену кадра, нижнюю оценку блока и цены групп: внутри группы — сумма квадратов по порядку
  признаков, цена группы — вес × сумма, цена кадра — группы по порядку схемы (вес 0 — группа пропускается). Поэтому нижняя оценка
  не больше цены любой строки блока и во float, а отсечение блока и ранний выход из строки (частичная сумма не меньше лучшей)
  выбора не меняют: итог побитово равен `SearchBruteForce`, сумма `Groups` — ровно `Cost`. Продолжение соревнуется со скидкой,
  только если текущий кадр искомый (у неискомого нет полного будущего — поиск уводит из него); `ContinuationCost` — у любого
  текущего; в переборе текущий кадр не участвует. Окно пропуска — кадры своего клипа ближе `skipFrames`; у цикла — по кругу с
  периодом «кадров − 1» (последний кадр = первый, его место 0), через шов; у нециклического — без заворота; соседних клипов не
  задевает.
- **Запрос.** Будущее — `TrajectoryModel.Predict(состояние, FutureTimes, тик истории, …)` одним проходом из скорости × kv и цели
  × kg; прошлое — `RootHistory.At(now + round(t / тик))` в системе корня × kv, пустая история — текущий корень, сдвинутый назад
  по скорости; скорость корня — скорость × kv в системе корня; ω — следующего шага модели, зажатая `maxYawRate`; суставы —
  нормализованные признаки текущего кадра как есть (без кадра — нули, то есть средние). `DataYawRate` — 99-й перцентиль (ближний
  ранг) |ω| искомых кадров по сырому признаку `RootYawRate`, без этой группы — по повороту за интервал графа × частота; не меньше
  1 рад/с.
- **Модель.** Шаг — выражения и порядок контроллера игры (`RootSteerSystem.Steer`, затем `RootControlSystem.Move` без действия и
  рывка): поворот `clamp(IEEERemainder(цель − курс, 2π), ±TurnRate·dt)`, затем `v += (цель − v)·min(1, Rate·dt)`, Y = 0, корень
  на новую скорость·dt; курс не заворачивается. Остаток — именно `IEEERemainder`, как у контроллера: ровно на полуобороте (−π) он
  поворачивает к −, а `Pose2.Wrap` повернул бы к + — предсказание ушло бы в другую сторону на весь горизонт. `Predict(t)` —
  побитово `round(t / dt)` шагов `Step`; перегрузка `Predict(состояние, моменты, dt, итог)` (добавлена в 8в, прежнее не меняет) —
  все моменты одним проходом, побитово как по одному. Равенство шага системам игры движок проверить не может (игры не видит) —
  это тесты игры (8е: параметры — компонент ядра `SteerModel`; `MotionMatchTests.Prediction_EqualsRealController_NTicks`,
  `SteerModel_EachTick_IsTheControllerStep_WithStrikes`).
- **История.** Ёмкость — `ceil(глубина / тик − 10⁻⁴) + 2`: на полной истории самый дальний момент запроса — настоящая запись
  при любой частоте тика, записан ли уже текущий тик или нет (кольцо постоянной длины при частом тике короче глубины — прошлое
  всегда экстраполировалось бы); `10⁻⁴` — чтобы 1/3 с при 120 Гц (39,999999 во float) не давала лишней записи. «Последняя запись
  не позже тика» — двоичным поиском; все записи позже — старейшая, сдвинутая назад по скорости.
- Неверный вход — `ArgumentException` с причиной (длины, не конечные числа, вес меньше 0, кадр вне базы, скидка вне [0, 1], окно
  меньше 0, моменты убывают, dt ≤ 0, темп или предел поворота меньше 0, тик не позже последней записи). 0 Б: `Search`,
  `SearchBruteForce`, `Cost`, `Fill`, `Step`, `Predict`, `YawRate`, `Add`, `At`. Правило OSR: блок поиска — `ScanBlock`, шаг
  модели — `Advance`.
- **Бенчмарк** `MotionSearch` — `dotnet run -c Release --project tests/Sword.Benchmarks -- --motion`, итог
  `artifacts/bench/motion.json`; в полный прогон (`-Bench`) не входит — замер себе, не цель. База — синтетическая размера пака
  (440 клипов, ~51 000 искомых кадров × 45 признаков, из массивов: постройки 8б ещё нет), запросы — `MotionQuery.Fill`; время
  поиска p50, p95 и максимум, доля осмотренных блоков, полный перебор для сравнения; код выхода — 0 Б и «поиск = перебор». На базе
  пака — после 8б.

**Агентский доступ (поиск):** значения без ссылок — `MotionMatch` (кадр, цены, по группам, блоков и кадров) хранит компонент
игрока `MotionMatchState` (виден `entity.get`), `MotionQuery.Raw` — запрос в единицах данных (для оверлея траекторий), записи
`RootHistory` — в хеше участника `locomotion`; бенчмарк `MotionSearch`.

**Проверки (8в):** `MotionMatcherTests` (поиск = перебор на случайных запросах, весах, продолжении и окне, итог — лучший по цене
каждого кадра; нижняя оценка отсекает блоки и при лучшей цене больше 0; самопопадание; ничья — ранний кадр, продолжение
сохраняет ничью; окно через шов цикла; скидка; цены групп; неверный вход; 0 Б), `MotionQueryTests` (на ровном ходу запрос
совпадает с кадром синтетического цикла и находит его; масштаб данных; ω; прошлое из истории; суставы; `DataYawRate`; 0 Б),
`TrajectoryModelTests` (предсказание = n шагов побитово, одним проходом — тоже; кратчайший путь, полуоборот; разгон по тикам;
неверный вход; 0 Б), `RootHistoryTests` (ёмкость от тика, дальний момент — настоящая запись при 30…1000 Гц, «не позже»,
экстраполяция, переполнение; 0 Б); данные — `MotionSearchFixtures`.
