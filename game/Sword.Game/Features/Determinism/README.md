# Детерминизм и реплеи (этап 3)

Симуляция воспроизводима: одни команды по тикам дают одно состояние бит в бит. Отсюда реплеи, сверка `Game.App` и
`Game.Headless`, эталоны SWORD2 для регрессий и эксперименты агента (раздел 7 и 8 плана). В игре этап ничего не меняет —
проверяется автоматически.

## Откуда логика

Новое: в SWORD реплеев и хеша состояния не было. Правила — раздел 7 плана («Детерминизм, реплеи, эталоны»).

## Устройство (3а)

- **Хеш** — `Simulation.HashState(parts)` между тиками, без выделения памяти: хеш каждого участника по Id и итог — хеш
  их хешей. Раунд — как у xxHash64.
- **Участник `ecs`** (Runtime) — всё, что мир переносит из тика в тик: живые сущности по возрастанию индекса (индекс
  и поколение), у каждой — компоненты по стабильному имени; ресурсы-значения по имени; слоты — поколения свободных и
  порядок свободных номеров (от них зависят номера будущих сущностей, как у пула поз); журналы по имени — записи
  последнего оборота тика с возрастом в барьерах (их ещё прочтут системы следующего тика); регистрации систем в
  порядке исполнения — включена ли и сколько записей каждого журнала не прочла. Номера записей и барьеров не входят:
  одинаковое состояние после разной истории даёт один хеш. Ресурсы со ссылками (пул поз, ассеты) не входят: их
  авторитетное состояние — у своих участников; у записи журнала со ссылками хешируется только возраст.
- **Поля, а не байты.** `FieldLayout` один раз на тип строит листья (примитивы, перечисления, `Entity`, встроенные
  массивы) со смещениями — их считает среда (метка в упакованной копии), не раскладка вручную. Хеш и описание идут по
  одним листьям: padding не участвует, `-0` → `+0`, любой NaN → один, bool → 0/1.
- **Участник `animation`** (`Sword.Game.Animation.AnimationState`): по слотам пула — поколение (у свободного — со знаком
  минус), у живой позы — локальные повороты, смещения и модельные матрицы; порядок свободных слотов (номера будущих
  поз), заданий в очереди. Регистрирует ядро (`GameCore.Configure`).
- **ГСЧ** — ресурс `SimRandom(Seed)`, зерно `sim.seed` (по умолчанию 1): число — чистая функция (зерно, поток, тик,
  сущность, выборка). Сейчас игра случайности не использует; первым пользователем будет ИИ врагов (этап 4).

## Настройки

`sim.seed` — главное зерно ГСЧ (пойдёт в реплей, 3б).

## Зависимости

`Sword.Engine.Runtime` (хеш, участник `ecs`, ГСЧ), `Sword.Engine.Ecs` (обход сущностей и ячеек без копий —
`WorldReader.EntityAt`, `TryRead`, `TryReadResource`), `Sword.Engine.Animation` (`PosePool.HandleAt`, `FreeSlots`,
`GenerationAt`), `Sword.Engine.Agent` (инструменты).

## Ограничения

- Хеш — только между тиками (в точке обслуживания или владельцем симуляции); посреди тика — с `time.break` (3в).
- Внутреннее состояние систем (поля классов систем) не хешируется: правило — системы его не держат, всё авторитетное —
  в компонентах, ресурсах или у участников. Состояние самого мира помимо данных (свободные номера, журналы, курсоры,
  включённость систем) хешируется участником `ecs`. Очередь команд будущих тиков — вход, а не состояние: она пойдёт
  в реплей (3б).
- Стоимость хеша растёт с числом сущностей и поз (обход всех листьев); реплей будет хешировать раз в K тиков (3б).

## Агентский доступ

Анализ по чек-листу раздела 8:

| что появилось | чем агент это видит и проверяет |
|---|---|
| хеш состояния по участникам | **добавлен** `state.hash` (итог и участники шестнадцатеричными строками, с квитанцией тика) |
| состояние подсистемы вне ECS (пул поз) | **добавлен** `state.describe` — ровно то, что участник хеширует; отбор и страницы; больше 60 тыс. знаков — в файл артефакта |
| состояние мира помимо данных (свободные номера, журналы, курсоры, включённость систем) | `state.describe ecs` — части `slots`, `journal:…`, `system:…` (отбор по id части) |
| новая подсистема-участник | `IStateContributor.Describe` у `animation` — позы по суставам (`filter` `2v1:foot`) |
| ГСЧ | состояния нет; зерно видно ресурсом `SimRandom` в `state.describe ecs` и `world.types` |
| детерминизм без агента | `Sword.Headless --json` → `stateHash`; `verify.ps1 headless-smoke` гоняет прогон дважды и сравнивает |

Инструменты: `state.hash`, `state.describe` — тесты `CoreToolsTests.StateHash_MatchesSimulation_DescribeByParts`,
`StateDescribe_LargeAnswer_GoesToArtifact`, `DeterminismTests.AgentQueries_DoNotChangeHash_StateToolsWork`; строки в
`docs/agent-playbook.md` («Проверить детерминизм»), проверка в `verify.ps1` `agent-smoke`.

## Проверки

- `tests/Sword.Engine.Runtime.Tests/StateHashTests` — листья и смещения (bool, перечисление, `Entity`, `Vector3`,
  `[InlineArray]`, `fixed`), мусор в padding и `-0`/NaN не меняют хеш, два прогона с ГСЧ совпадают тик в тик, другая
  команда или зерно — другой хеш, участники по Id и раздельно, ошибки регистрации, описание `ecs` с отбором и
  страницами, 0 байт на хеш, ГСЧ — чистая функция и равномерность; `EcsPart_SeesFreeIndexOrder_AndFreeGenerations` —
  те же живые сущности при другом порядке свободных номеров или поколении свободного слота — другой хеш;
  `EcsPart_SeesJournalsAndSystems` — непрочитанная запись журнала и выключенная система меняют хеш, после оборота тика
  состояния снова равны.
- `tests/Sword.Engine.Ecs.Tests/InspectionTests.SlotsAndInPlaceReads_WalkLiveEntitiesByIndex`,
  `FreeIndices_Journals_Cursors_BetweenTicks` — обход для хеша.
- `tests/Sword.Game.Tests/DeterminismTests` — две игры с одним сценарием совпадают 400 тиков (поза меняется — участник
  `animation` её видит), запросы агента между тиками хеш не меняют.
- `verify.ps1`: `headless-smoke` (два прогона — один хеш по участникам), `agent-smoke` (`state.hash`, `state.describe`).
